# 0008. Updating the core

- Status: Accepted
- Date: 2026-10-11
- Code: `hided/src/core_update.rs`, `hided/src/node_role.rs`, `hided/src/started_cores.rs`

## Decision

### Updating the core

A node newer than its core updates the core to its own build before it says hello (PRD core-host-node-move B10, D-10; `update_core` in `hided/src/node_role.rs`, `hided/src/core_update.rs`), over SSH alone, so nothing is asked of the older core.
It signs in twice: the attach that found the older core ended its `ssh`, so the update opens a second one, which installs the build, runs `hided core-update` and stays for the attach that follows (`Upstream`).
This build goes into a version folder beside the core's under the same install root (`Upstream::install_build`: the device install's verified, resumable upload without its first-install checks), whole: the pane holder and its runtime go with the programs, as a device's kit and an app's own update place them, since the core that starts there runs its own panes from the holder beside it and is another Hide's guest only as a whole build.
Then that build's own `hided core-update --previous <program>` replaces the core through its starter: the login item is replaced in place, which ends the old job, so a machine that restarts midway starts one of the two builds at login.
The new core has 30 s to take links; one that does not is replaced by the previous build again, which takes links on the same folder.
Either end leaves the install's `current` at the build that runs and keeps the other one for the next connection, so no more than two builds are ever kept there (`hide_host::kit::adopt_build`).
After an update the node's placement record names the new program and its next dial goes at once; its health says `updating` while one runs.
A node tries once per connection (B20): a failed update keeps its reason, the node's dials go on and are refused as older (`update_failed`) without trying again, and the host shows the update-failed page with both builds; `hide connect`, from a launch or that page's Retry, gives the next connection its one attempt.
Agents keep running in their pane holders throughout, and the core runs one of the two builds at every moment but the restart.
No link forms across builds, so a failed update does not reattach the window to the older core: a node's screens run the node's own build of the web shell against the core's snapshot and events, a wire with no version of its own (`SCHEMA_VERSION` has not moved while its shape has), so B10's "the window reattaches" holds after a successful update or once the core's machine is updated, never across builds.
A fixture HOME can name a build whose daemon fails at its start (`hided::env::FIXTURE_FAIL_BUILD_FILE`), which is how the journeys prove the way back.

The app on the core's own machine never stops the core its starter runs (Q13; `update_started_core` in `hided/src/cli.rs`).
A core `hided core-login` started (the login item's, and the fixture starter's, which runs the same command) names its program in `/health` (`starter.program`), and a bundled `hide connect` of another build reads it before it would replace the daemon: stopping that core would leave the login item to start the old build again at the next login beside the app's own.
The app replaces it as a node's update does, with its build placed in the same install root on this machine (`HelperPackages::install_here`) and the same `hided core-update`, which runs in its own process group so a host that gives up on the connect never cuts it short; the app the operator put on the machine is the build the machine runs, as it is with no login item, so a newer core is lowered to it and a build neither orders is replaced by it rather than the app being told to update.
That core runs from a copy of the app's build in the install root, so the app can be replaced under it, and on a state folder the app opened (`hide_kit::app::package`) it is the app's own core: it answers as the app's installation and installs the app's kit from the package (`always_on::adopt_core_kit`, read once at the core's start), so a pane the app's own daemon started keeps reaching it, and a pane it starts reaches the app's daemon after it (with-hide/hide#2876).
A core run from the install root also answers the panes that name the install root's installation, whichever of the two it starts panes under (`hide_host::kit::also_answer_for`): the app's package can come or go between two starts of the same login item, and the panes, which outlive a start, keep the name they were started under; their hook entries, each kept by its own installation while its helper is there, keep acting in them.
Each connect is one attempt, so a failed update shows the same update-failed page and its Retry is the next attempt.
Under the login item the starter asks launchd once a second whether the new job has exited, so a build that cannot start is known in about a second rather than at the 30 s bound, which keeps the way back inside the host's 25 s connect wait.
A paired machine's core is run by the same kind of item from the same install root, so an app update reaches it the same way; `hided/tests/it/always_on_update.rs` runs that journey, an update and a way back, on every system with the fixture starter.

A Hide that runs with no app on its account is updated by the machine that reaches it through a login (PRD device-connect-iroh B23).
A helper device that was switched, or a WSL distribution, runs a Hide of its own from the programs the switching machine had installed there, and no app there updates it.
The switching machine keeps the login its switch went through with the host's record in `peers/known.json` (`Host::started`, an SSH alias or a distribution's name, saved first like the rest of the record) at every switch it is admitted on, whichever switch started the Hide, so the record does not depend on what one run of `hided` remembers; a machine it only paired with has none and is left to its own app.
Each time such a host connects, or cannot because the two builds share no number, the pairing compares the build the host named in its hello with its own (`build_order::may_be_older`, which only rules out a later release) and, once per build the host names, runs one raise (`hided/src/started_cores.rs`): this build goes into the helper root there over the login (`Upstream::install_build` over SSH, `WslAccess::install_build` through `wsl.exe`), and that build's own `hided core-update`, run with no `--previous`, decides the rest on the host.
A raise runs with nobody at the row, so its SSH login asks nothing, and it never starts a distribution that is off (B43).
One raise runs at a time on a machine (`Pairing::raising`), and on the host the command holds the folder's update lock (`hide_kit::layout::core_update_lock`), so two machines that raise one core do so one after the other and the second finds what the first left: a core of the same build is left as it is (`current`), a newer one is never lowered (`kept`), and builds neither key orders are refused (`other_build`).
A core a desktop app opened is that app's to update from then on: before an older core is touched the command asks `hide_kit::app::present` and answers `left_to_app`, because a core raised past the app's build would refuse the app's own connection.
The app says so itself: its packaged `hide connect` notes the package it runs from in the state folder it opens (`hide_kit::app::note`, `layout::app_note`), before anything can end that connect, and the note counts while its package is still there.
Nothing else can say it: on a machine whose core a login item runs, the app's `hide connect` updates that core and no daemon runs from the package, so no kit is ever applied as the app's, and the account's `hide` command stays a device helper's while the helper's own command is there.
The note is kept by state folder, so an app opened on a folder of its own says nothing of the account's other cores.
An older core is replaced as a node's update replaces it, with this build put beside the one its starter runs (`always_on::install_this_build`), and a new build that takes no links gives way to the one that ran.
The core `hide connect` started before the account was paired runs on under no starter until it ends, which on a server can be weeks: its build is put in the starter's root for the way back (its own program is in `/health` as `program`), it is stopped so the new core's start does not wait on its lock, and the login item starts one of the two builds.
Every refusal comes before that stop: the two builds are of one install (`replaceable`), so a raise that ends refused leaves the core that ran.
A core nothing would start again, such as one in a WSL distribution systemd did not start, is not replaced (`core_not_kept`): a start that failed would leave the account with no core.
The raising machine asks first whether the target is on (`Login::on`), since a raise may have waited its turn behind another and any command run in a distribution that was turned off meanwhile would start it (B43), and then asks a distribution whether systemd started it, before it copies a build there; it stops at either no.
The row of the machine shows the raise in place of who has to update (`PeerUpdate::Updating`, then nothing, or one of four failures: the login did not reach it, the new build did not start, another update runs there, or a reason the diagnostic log holds under `started_cores`), and the row's Retry, which is `hide device retry`, asks again.
An account left to its app and a core nothing would start again are not failures and show nothing on the row: the operator has nothing to do there, so each is one diagnostic (`core_update`'s `raise.left_to_app`, `started_cores`' `raise.not_kept`).
After a raise that replaced the core the connection is made again at once (`network_changed`).
`hided/tests/it/always_on_update.rs` runs the command against a core the fixture starter runs (raised, then left alone by the same build and by an older one; and left to the app once the packaged `hide connect` opened the core, while a helper's `hide` holds the command name), `core_update`'s unit tests hold each decision, `started_cores`' the reading of each answer, and `hide-node`'s `a_build_is_put_in_a_distribution_s_install_root` the copy through `wsl.exe`; no test runs the two halves together across two machines.

### A paired machine's core stays on

A machine that has finished its first pairing, either way, stays reachable with no window open (PRD device-connect-iroh D-41, B30): the account's login item runs its core from a build Hide placed in the install root `~/.hide/core` (`hide_kit::layout::core_root`, `HelperPackages::install_here`, the pane holder and on Windows its ConPTY runtime included), and once the last paired machine is gone the item and its marker are removed.
A machine that never pairs gets nothing.
Nor does a core whose HOME is not the account's own home as the system names it (the user database on macOS and Linux, the profile folder on Windows): the system's login items are the account's whatever HOME says, so a test's HOME or an isolated candidate's would load its core into the account's real ones; `UserAgents::of_home` in `hide-platform` is that rule, `always_on::agents_for` and the starter of a core (`core_install::starter`) take their items from it, and a paired core it keeps from an item logs `always_on.declined` with the reason, once.
Paired means confirmed (`peer_host::pairing_confirmed`, beside the endpoint's own `peer_host::endpoint_wanted`, which also opens for a pairing that still waits): a grant this machine gave that the guest confirmed (active or paused), or a host this machine is a confirmed guest of; a pending grant counts as none, so a pairing that is declined or expires never leaves an item behind.
`hided::always_on::reconcile` is the one decision: it reads the folder's peer records and puts the item in or takes it out; the daemon runs it at its start, and the pairing after every change to the machines this one is paired with (`Pairing::paired_changed` through `always_on::Follower`), on a thread of its own, since placing a build copies it.
Before the item is put in, the program it will run is given the app's name for macOS's consent when the system says it is the app's (`login_item::name_core`, `hide_platform::privacy::give`, one `login_item.identity` diagnostic): the item's core is the program macOS holds responsible for what the core itself reads, and a file written once the core runs would change nothing for that run ([The platform layer](0005-platform-layer.md#the-platform-layer)).
The item runs `hided core-login --state-dir <folder>` and its marker is `<state>/keep-alive` (`hide_kit::layout::keep_alive`); `core-login` ends at once when the marker is gone, and otherwise waits on the folder's instance lock while another daemon holds it, so the item's core takes over when the app's daemon ends rather than fighting it.
A core the item started forgets its item rather than unloading it when it is the one removing it, since unloading would stop it midway.
Putting the item in never stops the asking core either (`login_item::adopt`, `UserAgents::adopt`): the definition is written and loaded when the system does not hold it, and a run going on, the asking core's own under an item it forgot included, goes on; only a starter replacing a core (`login_item::start`) ends the old run, and never its own process.
The item is kept only while it can run the core: one whose definition is there but which the system no longer holds (a failed load, Hide turned off in the login items, its task deleted in Task Scheduler) is loaded again (`login_item::hold`, `UserAgents::load`), and a `hide connect` whose item cannot start the core logs `core.item_unavailable` and starts the core itself, so the app still opens.
A paired core never ends for idle, since the pairing counts as work (`server::watch_idle`).
`hide connect` starts the core through the item when the item is installed, waits up to 30 s for it to answer, and updates it when it runs an older build ([Updating the core](#updating-the-core)); `hide stop` removes the marker first, so the stop holds through logins until the next `hide connect` puts it back.
On Linux the item asks for linger, and when the account may not turn it on itself the outcome names the `sudo loginctl enable-linger <user>` command, in the diagnostic log (`always_on.reconciled`).
A machine that is asked to switch a device there reads the same thing first (B30, [Switching a helper device to its machine's own Hide](0045-helper-to-own-hide.md#switching-a-helper-device-to-its-machines-own-hide)): it asks the target's `hide always-on unattended --json` on the same SSH login, which changes nothing there, and for a Linux account that does not linger a switch then asks `hide always-on linger --json`, which turns linger on when the account may and names that command when it may not; a Mac without automatic login is switched with the warning that it needs one login after a restart, and a WSL distribution systemd did not start (no `/run/systemd/system`, `sd_booted`'s own sign) has nothing that starts its Hide again (B43).
A machine the rule leaves is not switched, and `pairing_ssh::Condition` carries where it stands, with the one thing to change, in the read's answer and in the switch's `left` answer: the core keeps none of it, and the device's opened row draws it while it is open.
On Windows the window asks Windows once for the firewall rules when the operator shares this PC or allows a pairing (`askForFirewallOnce` in `web/src/settings/firewall.ts`, through the desktop host's `hide always-on firewall ask-allow` and the permission prompt), never at login; while they are missing and the PC is shared or paired, Settings › Devices shows that the connection goes through the relay with [Allow] under the share row, and the uninstaller removes the rules with the item.
`hide always-on status --json` says whether the folder is paired, whether the item and marker are in place, the folder's UDP port and the firewall rules' state; `hide always-on remove` takes out the item, the marker and the install root; `hide always-on linger` asks for linger as the item does and says what came of it; `hide always-on unattended --json` only reads, for the rule above.
