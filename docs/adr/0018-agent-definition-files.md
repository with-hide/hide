# 0018. Agent definition files

- Status: Accepted
- Date: 2026-11-02
- Code: `hide-agent-adapter/agents/`, `hide-agent-adapter/src/definition/`, `hide-agent-adapter/build.rs`, `hide-screen-rules/`, `scripts/check-agent-screen-rules.py`

## Decision

### Agent definition files

Every agent Hide knows has one definition file, TOML of schema 1 (PRD engine-bundle-3-core-owns D-16): `id`, `name`, `executables`, optional `packages`, `aliases`, `home`, `hooks`, `[account]` (where an account keeps the agent's folders, [Agent profiles and accounts](0019-agent-profiles-and-accounts.md#agent-profiles-and-accounts)), `[start] args` and `ready` (the id of an idle `[screen]` rule a start waits for, [Agents on the core's own engine](0013-core-own-engine.md#agents-on-the-cores-own-engine)), `[resume] session` (one `{session}`) and `last`, `[screen]`, the screen rules in Herdr's agent detection grammar, and `[answer]`, the keys that answer the agent's own question and approval screens from the phone; `based_on` is for the operator's files only.
The built-in files are `hide-agent-adapter/agents/*.toml`: the seven agents with Hide's own features and the sixteen others Herdr v0.9.5 had screen rules for, their rules copied unchanged but for `asks` (omp has none; its extension reports its state).
`hooks` names which of Hide's own code reads an agent (`claude`, `codex`, `grok`, `opencode`, `pi`, `omp`, `agy`), or `none` for an agent whose state only its screen shows; a new value comes only with the code for it.
The seven agents' identity is the file's: `hide-agent-adapter/build.rs` turns each built-in file into constants, `AgentAdapter`'s `id`, `label`, `aliases` and `executables` and `LaunchDialect::resume_flag` read them, and its account's places come from the file's `[account]`, and a built-in file goes through the same field checks as the operator's (`src/definition/file.rs`), so one that fails a check fails the build, while its screen rules are compiled at first use and a built-in that fails to compile is caught by the crate's tests; everything else on the adapter row is Hide's own feature, kept in Rust.
`hide_agent_adapter::definition` is the one reader of a definition, for built-in files and the operator's alike: it parses a file, checks every field it carries (an id of lowercase letters, digits and dashes; programs that are file names, the first a plain command name; start and resume words without control characters or apostrophes, at most 63 words and 8 KiB, the resume command limits; a home under `~/`), and compiles its rules with `hide-screen-rules`.

`hide-screen-rules` is Herdr's `src/detect/manifest.rs` cut to the grammar, its limits (128 rules, 512 gates, 1024 matchers, 32 per gate, 512 characters each, gates eight deep), the compiler and the evaluator; its `ENGINE_VERSION` is Herdr's 3, and a rule set that asks for a newer one is refused.
Rules are a value the caller hands in, never a file it finds or a download: the screen rules are the app's built-in ones and the operator's own `[screen]`, and Hide asks the network for none (D-19).
It depends on no workspace member and stays off the shared feature set, because the pane holder will link it to evaluate a pane's own grid; in this bundle the definition reader compiles with it and the holder does not evaluate yet.
A change to a built-in `[screen]` raises its `version` and is proven against a captured screen of that agent (`scripts/check-agent-screen-rules.py`, [TESTING.md: Agent screen rules](../TESTING.md#agent-screen-rules)).
One key of Hide's own sits beside the copied grammar: a rule's `asks = "folder_trust"` says its screen is the agent's question whether to trust a folder, read only by Hide's folder trust contract ([agent-hooks.md](../agent-hooks.md#folder-trust-for-the-folders-hide-starts-agents-in)), never by the evaluator, and left out of the rules a pane's holder is handed, so a holder of an earlier build reads the same rules; adding it is no rule change.

`[desk] left_out` names the commands Desk keeps from that agent ([Desk's commands](0032-desk.md#desks-commands)), each as typed after `/`, a name and at most one argument (`logout`, `session delete`), at most 32, and `[desk] compaction_meta` the JSON pointer where its ACP adapter tells a compaction's end outside the reply (OpenCode's), at most 128 bytes; only the built-in files carry it, as with `[answer]`.
`[switch]` names how a running session changes its model and its effort ([A session's model and effort](0026-session-threads.md#a-sessions-model-and-effort)): `model` and `effort`, each one line of at most 128 bytes naming `{model}` or `{effort}` (an effort line may name `{model}` too), `efforts`, the 1 to 16 efforts the effort line takes, and `model_resets_effort` for an agent whose model line puts the effort back to the model's own; only the built-in files carry it, as with `[answer]`, each line checked in the agent's own terminal.
`[interrupt]` names the keys that stop the agent's turn as its own Esc or Ctrl+C does (`keys`, one to four of the engine's key names), which ■ on a session input and on the phone types while the agent works ([The operator's waiting line](0026-session-threads.md#the-operators-waiting-line)); only the built-in files carry it, each key checked in the agent's own terminal, OpenCode's two Escs included.
The web contract says which agents carry it (`interrupt` in `contracts/agent-adapters.json`).

`[answer]` holds up to three tables, one per kind of ask ([The mobile companion](0059-mobile-companion.md#the-mobile-companion)): `question = { down, pick }` (the screen opens on the first choice), `plan_approval = { approve, keep_planning, approve_label? }` and `permission = { allow, allow_always?, deny }`, each choice 1 to 8 keys, a key a name the core's own engine presses (`enter`, `esc`, `tab`, `up`, `down`, `left`, `right`) or one printable ASCII character typed as a key, never pasted (Grok's plan screen takes `a`).
Keys other than `esc` and a character count from the row the screen has highlighted, so a table that uses them says how to see that row: `marker`, what the screen draws before the highlighted row (Claude Code's `❯`, Codex's `›`), and each kind's `row`, the text after the marker that names a row by its place, `{n}` (`{n}.`, 1 for the first), or, in a question, by its choice's label, whole (omp's `○ {label}`).
A `row` without a `marker`, without exactly one place, or with keys other than `down`, `enter` and `esc` is refused at the build, since the core follows the highlight only down; a kind whose keys need the highlight but has no `row` is answered in the terminal (OpenCode and Grok's question mark the row by colour alone, and omp's plan and permission rows are fixed words).
A `plan_approval` table names by `approve_label` the words of the row `approve` picks where the menu offers more than one way to approve, and the core types the pick only while the highlighted row reads them: Claude Code's first row switches it to auto mode, so its approve goes down to `Yes, manually approve edits`, and a phone's press never widens what the agent may do.
A `permission` table with a `row` names how its dialog draws a one-line command, `command = { title, separator }` or `command = { title, prompt }`: under the dialog's `title`, either the first line that begins with `separator`, the command on the next line with no border or gutter before it, and that same separator line again, letter for letter (Claude Code's `Bash command` and its `╌` lines), or the lowest line that begins with `prompt`, the command after it and only blank lines between it and the rows (Codex's `$ ` under `Would you like to run the following command?`); without it the build refuses the table.
A dialog that marks no end under its command has no such shape, since a command of more lines, or one with an empty or a separator line among them, could not be told from one: Antigravity's permission has no `row`, so it is answered in the terminal.
A `permission` table says `by_hook = true` for an agent that records a tool call only once it is allowed (Codex): its session names no call while the operator is asked, so the card's command is the one its permission request hook gave (`HookStatusReport::asked`, laid on the row as `asked` for such an agent only), and the keys are typed only while the dialog's own command line shows that same command, so a command left from an earlier dialog, one whose report was dropped or a dialog of another shape types nothing; a request that named none is answered as it stands, and a patch, whose lines the dialog draws and the card does not, is answered in the terminal.
Each table is checked on that agent's own screens in a real pane before it ships, so only the built-in files carry one: an operator's file that names `answer` is left out, and a copy (`based_on`) takes its agent's.
A core test types every built-in table's keys through the engine's key parser, so a misspelled key fails the build, not a phone's answer.

The operator's files are `~/.hide/agents/*.toml` (`hide_kit::layout::agent_definitions`), read after the built-in ones in name order by `hide_kit::agent_definitions` (D-17, B1).
A file with a built-in agent's id may only replace that agent's `[screen]`; a new id names its programs and `hooks = "none"`, or copies one built-in agent with `based_on` and changes the fields it writes, keeping that agent's hooks and what Hide does with them; a copy of a copy is refused.
A program or package another agent already claims, or a name (`id` or alias) another agent uses, leaves the later file out, so one process is read as one agent.
`packages` holds at most 16 full npm package names of at most 214 bytes, optionally `@scope/name`, in lowercase letters, digits, dashes, dots, underscores and tildes, with neither part starting with a dot or underscore.
Paths, version ranges and empty parts are refused; these identities, like aliases, are not inherited through `based_on`.
Native executable names and runtime script names take precedence; only an unrecognized name falls through to an exact full package match, keeping its scope.
Detection reads only these definitions; a contract test compares the seven adapters’ npm and Bun install routes with their definitions so installation metadata cannot drift.
The folder is capped: the first 64 `.toml` files are read, each at most 256 KiB, and a file past either limit is named as left out without being opened.
A file that fails any check is left out alone, with one line that starts with its name, and the rest are used; a folder that cannot be listed leaves the built-in agents and its reason.
The daemon reads the folder at start and on every `hide agent catalog`, on its own thread, and the core's worker reads it again when Settings › Agents opens (`agent_definitions_read`); the core only swaps the result in under its lock (`runtime/agent_definitions.rs`), logs each file left out once per reason (`agent_definitions.file_left_out`), and publishes them in `status.agent_definitions`, which Settings › Agents draws as one dimmed line per file.
There is no watch: an edited file is read on the next ask.
The catalog adds every other definition with `source`, `based_on`, `hooks`, `screen` (its source and version) and `spawn: false`, since starting such an agent comes with the new engine's agent start, and `definitions_rejected` beside the items.
