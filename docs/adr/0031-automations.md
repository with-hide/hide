# 0031. Automations

- Status: Accepted
- Date: 2026-11-19
- Code: `hide-core/src/automations.rs`, `hide-core/src/automations/`, `hide-core/src/runtime/automations.rs`, `hided/src/automation_cli.rs`

## Decision

### Automations

An automation starts an agent on a schedule with no person present (PRD automations).
The core of the machine it runs on owns the book: each automation's name, task, schedule, agent choice, folder, pause, next time, its last 50 records and the closes it still owes.
The book is saved off the lock to `automations.json` in the state folder (`hide_kit::layout::automations_store`, a `LatestFile`); a run's agent is named by its ledger id.
Each automation keeps the machine whose core made it or last turned it on: a core of another machine that reads it (a book an earlier build's core move carried) stops it as `machine_changed` with its own Needs You line, unless the operator had paused it themselves, and a person's resume runs it there from then on.
A run that was going when an earlier build moved the core does not go on: it ends stopped with the code `automation_machine_changed`, and what it or a finished run left open is kept in the book as a close of the machine it ran on, which this machine's engine never judges.
A book that cannot be read is set aside beside the store as `automations.json.unreadable-<unix ms>` with a diagnostic, and the core starts with an empty book that names the set-aside file (`Stored::unreadable`, the section's `unreadable`, one line above the table) until the operator makes an automation again; the caps on what is written (100 automations, 50 records each, 1,000-character answers, 400 owed closes, 32 results per automation across its runs, one attempt start and one opening start per automation) fit inside the 96 MiB read cap (`READ_CAP`), which a test holds at every cap: 91,466,700 bytes with every cap full of the widest text JSON writes, 64 MiB being too small once a run keeps results.
`hide-core/src/automations.rs` holds the types, the caps, a run's prompt and the snapshot; `automations/schedule.rs` holds the choices and a five-field cron, read in the machine's zone with `jiff`, and refuses a schedule that can run two times closer than five minutes (`schedule_too_often`; the choices are every 5, 10, 15 or 30 minutes from each hour's start, `every_minutes`, beside every 1 to 12 hours); `runtime/automations.rs` drives them.
A once schedule (mission-104) is one wall date and time, `{"kind":"once","date":"YYYY-MM-DD","time":"HH:MM"}`, read in the machine's zone like every other, with no period, so the five-minute floor does not apply; it has no next time after it, and it is refused when past (`schedule_once_past`) or more than 366 days ahead (`schedule_once_too_far`, `ONCE_HORIZON_DAYS`).
A call may name it from now (`automations::Asked`: `once_in_days {days, time}`, `once_in_minutes {minutes}`), which the core reads against its own clock and zone when it makes, edits or previews (`Asked::resolve`), so only the date and time are kept and read back.
A run's first prompt is the task, then one fixed line (`result_line`, in the operator's language like the last-run line after it and the line a retry resumes the conversation with) that asks the agent to show its result in a View, a page (an HTML file or a URL) with `hide browser open <path>` so it is drawn rather than shown as its source and any other file with `hide file open <path>`, which is how a View becomes the run's result, and otherwise to just end, then the last finished run's time, result and answer.
The line is a reminder in the prompt, not a check when the run ends, so every agent on every system reads it the same and no `Stop` hook has to carry it.

The clock is the local coordinator's tick (about 250 ms, wall-clock milliseconds; `tick_automations`): a time that came is taken once, so a sleep or a core that was off is noticed at the first tick after it.
The machine's zone is read again on a worker every minute, and a changed zone moves every next time.
Times that passed while the core was off (the first tick) or the machine slept (a gap over 60 s), or one noticed more than two minutes late, become one missed line and one run (D-15).
Runs are followed at most once a second.

One run goes at a time: a time that comes while the automation's run is starting or running is a skipped line (D-14), and a finished run whose terminal is still open does not hold the next time.
Times skipped in a row for the same reason (the run still going, or the same agent at its limit) are one line with their count and first and last time (`Automation::skip`; the record's `count` and `last_unix_ms`), as the missed times are, so a five-minute schedule's skips do not push the runs and their answers out of the 50 records; a run or a missed line between starts a new line.
Before a run starts, the account its agent runs in is judged from the usage the core already reads: a profile's own account, or the agent's default account when the profile shares it (`UsageModel::account_limits`).
Not installed stops the automation for a person (D-12, D-17), and 100% before its reset skips a scheduled time; an account read signed out, or one it cannot read, runs (D-16).
A signed-out read is a guess from what `/usage` printed, so it stops nothing by itself: once the agent itself fails an attempt (it exits, never shows, is refused, or stops with no answer) while its account reads signed out, the sign-in that ended stops the automation with no retry (`Failure::Agent`).
A login a machine cannot read for an agent whose program it does not find either reads as not installed, not signed out: Claude's reader asks its CLI, and Codex's (`hide-host` `codex_missing_or`) asks the account's search for `codex` when its `auth.json` cannot be read, so a missing Codex CLI stops as `agent_missing`; a search that cannot be read proves nothing and leaves it signed out, and a login the server refused is signed out either way.
A run asked for with run now, the first run of an automation made with it included, is judged the same, except for the limit.

A run's agent starts under Hide's own identity `hide:automation` with no parent (`coordination::run`, `Command::Spawn` with task kind `automation`), on a worker with the lock released.
Its intent carries the automation, the run and the attempt (`automation-<id>-r<n>-a<k>`), so a start asked again after a restart converges on one agent (B36).
An attempt and an opening of a finished run's conversation are both a start under its intent: the start (`automations::Ask`, the spawn command whole, its first prompt included) is made once and kept on the run or the opening until its agent registered, so every ask of it, after a restart too, is the same spawn, and an edit or the last run's whole answer read meanwhile changes only the next start.
A start that stopped after its pane was made (`coordination::INCOMPLETE_SPAWN`, such as `native_identity_unavailable` or `agent_not_started`) is asked again under the same intent every 10 s, which continues that start in its pane, until three minutes from the first ask by this core (for an attempt, from its first look, the folder's wait included); past it, the pane goes to the close and an attempt fails as a transient failure, an opening as a conversation that could not be opened, which a person can open again.
The attempt count moves only when a start ended, and one opening of an automation starts at a time.
A start refused for something it needs and has not got yet started nothing: another start holding this machine's start line (`spawn_busy`), asked again under its intent a second later, a tab asked of a folder whose last terminal is still closing, as the last run's is right after its close (`workspace_closing`, the engine's refusal the spawn passes on by name), asked again a second later, or a Codex start on a machine whose kit has not read its Codex (`codex_capability_unknown`), asked again after 10 s; the wait counts nowhere in its three minutes, and only 15 minutes of it fails the start, so automations due at the same time each start their agent in turn.
A start whose spawn command the book holds in a shape this build cannot read (`Ask::command` is none, written by a build whose spawn differs) ends alone, not the whole book: an attempt fails as `start_unreadable` and is tried again as a new start, an opening ends.
From the moment a start's pane exists its row is the run's (`started::StartingPane`, while the book still asks that start), so it never stands as the operator's row in Needs You before its agent registers.
Each start first asks this machine's node whether it finds the agent's program (`Call::AgentInstalled`, the program the engine starts the agent by), since a spawn types the program whether or not it is there; one not found is `agent_not_installed`, and a node that does not answer lets the start go on.
A start refused because the agent is not set up on the machine (`agent_not_installed`, `agent_hook_off`, `agent_not_set_up`, `agent_hook_missing`, `agent_hook_untrusted`) stops the automation as `agent_missing`.
A run works unattended, so its spawn (`TaskKind::Automation`) reads its folder as its machine has it at that moment, not as the catalog's path facts read it up to a minute ago: off the lock, on the start's worker, it asks the node (`Call::Directory`) before anything is reserved or made and again before its start is typed (`executor::folder_there`), since a pane asked for a folder that is gone opens in the home folder instead (the pane holder's PTY start, `vendor/portable-pty` `as_command`). A folder gone at either moment is `spawn_folder_unreadable` (`coordination::FOLDER_GONE`), which stops the automation as `folder_missing`; nothing is typed, the unused pane closes, and a machine that does not answer fails the attempt to be tried again.
That ask, not the catalog, judges whether a registered folder is there: a project folder the catalog's path facts last read as gone (`CheckoutKind::Unreadable`) still starts the run (`drive_start`; the run's spawn, made by the core itself, never goes through `spawn_place`), since the catalog may still read it so for minutes after the folder is back, and a run started then would stop as `folder_missing` for nothing. The same stale read makes a Git project's row look plain, so the automation's own choice says where that run works: a new worktree when it asked for one, else the folder itself. A chosen folder no project row holds still stops as `folder_missing`.
Its row leaves the operator's lists as a Hide AI task's does, and a View it opened reaches Needs You as well as a question or a block (`TaskHome::Automations`, `Ownership::HideAi { look_calls }`); a once automation's run's row says so (`HideAiSnapshot::once`), and a View it opened does not call, since its end does (below).
It works in the project the operator chose, in a new worktree per run (`automation/<id>-r<n>`) when asked in a Git project, or else on the branch the project's folder has out; a project folder with no branch out (a detached HEAD) stops the automation as `folder_detached`.
With no folder chosen, the core's own node makes `~/hide/automations/<name>-<id>` with the folders above it (`Call::AutomationFolder`, node protocol 99), and the core registers it, by the real path the node answers, as a plain folder project with no engine workspace and no pane (`register_without_workspace`), so the folder holds no idle exit (B32).
The form shows that folder before the automation is made from the core's preview (`automation_preview {schedule, name}` answers `own_folder`), named by the same rule (`own_folder_name`) with `…` where the id comes (`ID_TO_COME`), so the window keeps no copy of the rule; it is null while the core has no home.
The core marks that project's row `unlisted` in the snapshot (`WorkspaceSnapshot::unlisted`, absent while false), so no list shows it (D-08), a window that opens with no checkout chosen never opens on it (`resync_navigator_focus`), so a run's terminal never becomes the selected pane, and an edit that leaves the folder retires its registration.
The operator may follow a run's terminal there, and the Workspace and Changes then name that folder; once the engine has no pane in it (`CheckoutSnapshot::has_panes`), the same pass hands the focus back to the checkout last in front that a list shows (`ui_state.recent_checkouts`), else to the first one listed.
A default folder its machine reads inside a Git repository around it (a home folder that is a repository) is that repository's, not a project of its own, and stops the automation as `folder_in_repository`.

A run follows its agent's row.
A finished turn records the result at once: the state, the answer's first paragraph (from `request.answer`, then from the whole answer read on a worker) and the native session id.
A provider error, an agent that exited, a start that does not leave within three minutes, and a turn that stopped after work with no answer and no refusal (`stopped_without_answer`, how a refusal reads for an agent whose hooks do not name one) are transient failures, tried again in the same conversation up to three attempts (D-17).
A person ends a run only by [■ 멈추기] or by ending its turn while the automation screen shows its terminal (`automation_run_viewing`): it ends stopped (`stopped_by_person`), not tried again.
A turn refused for the account's usage limit is not tried again either: its run's record becomes the skipped line a time at the limit is (`Automation::skip_run`), so the screen and the phone draw both one way and the next run's prompt passes over both.
A sign-in that ended, a folder that is gone or an agent that is not set up stops the automation and ends the run failed, and the automation raises its own Needs You line (`Scope::automation_asks`, counted as a mission's own ask is), which turning it on again clears.

A once automation is done (`Automation::done`, the section's and the phone's `done`) once its time was taken and no scheduled or missed run of it goes: it never runs again on schedule, keeps its records, and `next_run_at_unix_ms` is null.
Every run of it that ends, whatever its result and unless an attached window shows it as it ends (the screen's word lasts after its window went, so it counts only while one is attached), or its failure stopped the automation for a person, whose own line says so, is kept as `Automation::look_run` (the newest one), which the record cap never drops; the core publishes each such automation as its own Needs You line beside the stopped ones (`Scope::automation_looks`, the phone's `looks`, counted alike, the first ended first; no phone push, which follows `automation_asks` only), and the section carries that run's answer for the line.
The line is the automation's, not its run's row, so the run's terminal closes on the rule below and the line outlasts it and a restart; the run arriving in the automation screen (`put_away_viewed_run`, which the event announces though the terminal is gone) clears it, and so does the phone opening the line (`automation_look_seen {id, run}`, `Call::LookSeen`), only while that run is the one the line names.
Its time is never skipped: at the usage limit it starts as a manual run does, a turn refused for the limit ends the run failed (`usage_limit`) rather than becoming a skipped line, and a run of it already going when the time comes is the run for that time (the time is a skipped line as above).
A failure a person fixes ends the run failed with its reason and stops nothing when the automation has no time left; with a time still to come it stops it as any automation.
It cannot be paused once its time was taken (`automation_done`); one paused past its time runs once as soon as it is resumed; an edit to a new time or a repeating schedule sets it going again on this machine (its `machine` becomes this one, as a resume makes it), and a manual run leaves it done.
Its time, once taken, leaves it none (`Automation::take_due`).
A zone change, and a core that starts in another zone than the book was saved in, read a waiting one's wall date and time in that zone (`Automation::next_time`, on `apply_zone` and on install alike), so it runs once, there; a past one then runs as missed, a paused one keeps no time until it is resumed in that zone, and a done one never gets a time.
At the cap of 100 automations a create drops a done one that is not in use (no run going or closing, no conversation opened again: `Automation::in_use`), one the operator opened before one that waits in Needs You, then the one done first, with its records and its closes (its folder stays), and logs `automation.cap_dropped` once it went; it is refused (`automation_cap`) when no done one is free to go.
The book keeps `SCHEMA_VERSION` 1: a book with no once automation is written as before, while an older build refuses one that holds the `once` kind and sets the whole book aside as unreadable, above.

Every close the core owes is one list in the book (`Stored::cleanups`), one entry per run naming the spawn intents to close and the run's worktree.
A close closes each intent's pane through its spawn record, only the pane that spawn made (`executor::close_spawn_pane`), then releases the run's worktree when nothing was left in it (`release_branch_worktree`); one that fails is tried again after 5 s, doubling to 10 min, by the next core after a restart too, and given up with a diagnostic after its twelfth try; a start for that run waits until the close it owes ran once.
Each close names the machine whose engine holds what it closes, and only that machine's core runs it.
A failed attempt, a run that ends failed or stopped, and the run of a removed automation owe their close at once, so the next attempt never opens beside the last one's terminal.
A finished run's close waits (`Run::closing`) until nothing in its terminal waits on the operator: no refusal it rests on (a question or an approval holds it until answered, read or not), no block, nothing in Needs You, not on the operator's screen (a window attached and drawing its tab; with no window attached nothing is on screen, whatever pane the core has selected; a project no list shows, an automation's own folder, is on screen only as far as the automation screen shows it, though the keys typed into a run's terminal there leave the focus in it, the same rule the sleep's on-screen check keeps, `Runtime::agent_sleep_on_screen`), not shown in the automation screen (`automation_run_viewing {id, run, on}`, held 30 min unless sent again) and no letter on its way (`agent_sleep::LetterWaits`); a row missing for under 30 s, as while the engine starts again, holds it as it holds a running run.
What holds it is logged when it changes (`automation.close_held`, with `hold` one of `refusal`, `blocked`, `needs_you`, `viewing`, `on_screen`, `letter`, or null once nothing does).
The automation screen draws a shown run as pair view: it moves the core's focus to the run's pane as it arrives, as a key typed there would, so the front Workspace's desk (`workspace_view`) is the run's tab's, and draws that desk beside the terminal with no screen of its own; the run's `answer` is in the section only for the runs `viewing` holds (`AutomationsSnapshot::of`'s `shown`), bounded by its 16.
The core places the run's summary on that desk each time `automation_run_viewing` says the screen shows the run and the run's tab exists (`place_run_summary`): a card display (`DetailItem::AutomationRun { automation, run }`, `Display::is_run_summary`) at index 0 of the tray's first area (`SplitTree::prepend`), in front only when the tray was empty, and then `gather_run_views` brings the run pane's waiting Views onto the desk while it holds no View but the summary.
The word can come before the run has a pane or a tab, so the focus the window moves to the run's pane (`focus_pane` with `reveal_unseen`) lays the same desk for a run the screen shows (`Runtime::lay_viewed_run_desk`).
The summary is fixed, each refusal with one owner: `AreaItem::pinned` makes `SplitTree` refuse to move it inside its desk or split it; `Runtime::refuse_fixed_view` refuses to close it (`close_view_display`, which the window's close reaches, and the `Close` action of `hide view close`, which answers `view_fixed`) and to take it to another desk (`bring_view_to`), each with a diagnostic (`view_layout.run_summary_refused`, naming the action); a tray retired drops it rather than inheriting or shelving it, and `save` and `load` strip it as an external display is stripped, so it is never stored.
It is a card, so no pane's Views list or Files strip lists it, and `hide view list` leaves it out because an agent can neither close nor move it; its owner pane for the desk is the run's pane (`detail_owner_pane_among`).
While the screen shows a run, the tray of its tab counts as in view for the agent's opens (`tray_in_view`, through `viewed_run_tab`) and an open on it does not ask for the lane (`workspace_control.rs`, the `run_desk` case), so what the run's agent opens lands beside the summary, in front.
What the run's agent opened is `Run::results` (`RunResult { display_id, at_unix_ms, kept }`, `KeptView` from `hide-core/src/view_layout.rs`, the record a mission's `ViewLink` shares): `stamp_control_opener` records it beside `link_mission_view` when the caller is a run's pane (`Runtime::run_of_pane`, by the ledger's pane of the run's agent), keeping no opener, since the run's agent is re-derived when a row is pressed; the same View again (kind and address) moves to the newest place once, an address past `RESULT_ADDRESS_LIMIT` (1,024 bytes) or one that keeps nothing (an outside file, a card) is not kept, and past `RESULT_CAP` (32) results of one automation, over all its runs, the oldest is dropped with a diagnostic (`automation.result_dropped`); a book read with more than the cap is cut to the newest; the save is the one the other run changes make, off the lock.
The section carries `results [{key, kind, label}]` newest first only for the runs `viewing` holds, as `answer` is; `key` is a short hash of kind, address and commit, never an index, and the viewing set is part of what `refresh_automations` recomposes the section from; the phone's projection carries none.
`automation_run_result_open {id, run, key}` (`Call::RunResultOpen`, a `Screen` event) opens a result on the run's desk in front through `open_kept_view`, the helper `reopen_linked_view` of a mission uses too (an open display by id, else the one `KeptView::shown_by` finds, else a closed one reopened by kind through `reveal_path`, `place_browser_as` or `reveal_in_checkout`), stamped as the View of the run's agent; a refusal logs `automation.result_open_refused` with its code (`automation_unknown`, `automation_run_unknown`, `automation_result_unknown`, `automation_run_no_pane`, `automation_run_desk_not_in_front`, `automation_run_checkout_gone`, `automation_result_not_kept`, `automation_result_open_refused`) and answers it; a mission's refusal codes are unchanged.
The window names, with the viewing-off, the pane the focus was on before it arrived (`automation_run_viewing`'s `restore`), and the core moves the focus back there only while the focus is still on the run's pane (`Runtime::give_focus_back`), so a press elsewhere, which reaches the core first, wins.
A tab whose panes are all automation runs' is marked on the catalog before each publish (`TabSnapshot::automation`, `Runtime::mark_automation_run_tabs`), left out of the shown layout and of every group's tab list (`Runtime::automation_run_tabs`), and the sidebar's tree and its numbers skip it with its agent, so a run never takes a place in its project; its desk is still drawn while the run is viewed (`drawn_tray_layout`).
The pane of a run the automation screen shows is on screen though no tab of it is in front: it counts with the shown tabs' panes for the attach window and the nodes' shown panes (`Runtime::viewed_panes`), so it is attached again if it was released and stays attached until the window looks away; at most 16 runs are viewed at once.
A finished run's conversation opens again in a new terminal on request (`automation_run_open`) under the run's next opening number (`automation-<id>-r<n>-o<k>`, `Run::opens`), so every opening starts its own, and the opening's terminal is closed the same way when its agent ends.
A run names its conversation from its start: the session its agent registered with (`AgentRecord::session`, when it is a native session id), so a run that ends before its row is read can still be opened again; the row's session replaces it once read.

The window events (`automation_add`, `automation_edit`, `automation_pause`, `automation_resume`, `automation_run`, `automation_remove`, `automation_run_stop`, `automation_run_open`, `automation_run_viewing`, `automation_run_result_open`, `automation_seen`, `automation_look_seen`) and `Core::automation` take the same `automations::Call`, and an automation is named by its id or its unique name.
`hide automation add|list|show|run|pause|resume|edit|remove|preview` is how an agent makes one when the operator asks in words (B9, B10): it reaches the daemon through the pane capability as a scoped `automation` request (`hided/src/automation_cli.rs`), which admits only these calls, never a window's own events, and gives an external tool's View the reads and Act the changes.
The daemon words the core's answer for the agent: after a change it reads the automation back, adds what its schedule reads as in plain words and its next time on the wall clock of the machine whose core reads the schedule (the daemon's own system zone), and gives each refusal and each stop for a person one sentence of what to change; `hide automation help` is the agent's guide, and the session-start table routes a repeated task to it.
The `automations` snapshot section lists each automation with its reading of the schedule, its next time, its pause, whether a run goes, its unseen count and its records newest first, with the pane of a run whose terminal is open.
A run carries what its conversation spent (`spend`: new tokens, the price in millionths of a dollar, and `unpriced` when some calls had no price, so the price is a lower bound), and its automation the total of the runs its records keep (`recent_spend`, with how many it counts): when the usage ledger's worker reports, the core joins the sessions it priced over the last seven days to each run's conversation by its agent and session id (`Runtime::price_automation_runs`), in memory under the lock with nothing read there, and keeps the value in the book; a reading replaces it only when it has at least the tokens kept, since the seven days are cut by day and a conversation whose first day left them reads smaller, so a run older than the seven days keeps it.
A run the ledger has not read has none, and the ledger reads new calls only while a window is visible and assigns them by the checkouts open then, so a run whose own worktree was removed before the ledger read it gets none; a retry that started a new conversation counts only the last attempt's, so the value is a lower bound.
`hided` skips its idle exit while any automation has a time to come or a run going (`Core::automations_on`, `Automation::waits`, read without the owner thread), so a time comes with no window open (D-19), and a done once automation holds nothing; after a reboot nothing runs until the app starts the daemon, which then takes the missed times as above.
