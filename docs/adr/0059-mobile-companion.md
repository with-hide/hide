# 0059. The mobile companion

- Status: Accepted
- Date: 2026-09-28
- Code: `hided/src/mobile/`, `web/src/mobile/`, `hide-relay-protocol/`

## Decision

### The mobile companion

On macOS, Windows and Linux, turn on Mobile in Settings and scan its QR with the phone camera to open `app.withhide.dev`.
No Tailscale installation, Hide account or payment is needed for the default relay connection.
The phone and the computer encrypt their messages before sending them through Hide's relay in Tokyo.
The relay passes those encrypted messages between them and cannot read conversations, commands or phone credentials; it sees routing identifiers, connection times and traffic sizes.
The computer must remain awake and connected; the relay stores no messages to deliver later.
Tailscale remains an advanced direct option, with its system support recorded in [INSTALL.md](../INSTALL.md#what-each-system-supports).

The shared relay library and its WASM boundary are specified in [RELAY_PROTOCOL.md](../RELAY_PROTOCOL.md).
The hosted phone uses its WASM initiator.
hided uses it for signed device admission, Noise responder sessions and QR v2; the phone credential is checked only inside the established encrypted session.

Phone transport, pairing, conversation reads and delivery live in `hided/src/mobile/`; status projection and notification transitions belong to `hide-core/src/agent_state/`.
The phone's own language and light or dark choice are the one exception to "the core owns the preference": they belong to that phone's browser, in `web/src/mobile/settings.ts` (storage key `hide.phone.settings`), and are never sent to hided.
The loader and the app read the same module, so the start page and every protocol bundle of an origin agree; the app's language is that choice, else the core's `interface_language`, else the phone's language, and `followPhoneTheme` is the one function that puts the `dark` class on the page.
The start page has no core to ask, so the app keeps the last core's explicit `interface_language` beside it (`hide.phone.macLanguage`, written only when an `agents` frame changes it, removed while the core follows its system) and the start page resolves its language from the same three in the same order (`startLanguage`).
Each row of the phone's `devices` carries `link` (`DeviceLink` in `hide-core/src/agent_state/tally.rs`: `ssh`, `wsl`, `peer` or `inbound`), read off the navigator's device row the registration made; it is optional on the wire, so a phone bundle that predates it ignores it and a phone against a core that predates it draws no mark.
Mobile is off until the operator turns it on in Settings › Devices' phone group (폰에서 Hide 열기, or Add device › 폰, which turns it on), and it is kept in `mobile.json` beside the daemon's state (the switch, selected method, last direct scope, push mode, owned serve entry, VAPID key, device signing seed and Noise static key), written through a temporary file at mode 0600.
An older file without a method keeps Tailscale when it has a Serve record or last tailnet; a new setup defaults to relay.
The relay keys are made when Mobile starts using the relay, and decoded once per daemon and shared by admission, QR and push payloads, so no notice waits for the relay's first pass to name its room.

The default transport is `mobile/relay.rs`: one outbound WebSocket to `wss://relay.withhide.dev/ws`, with the validated `HIDE_RELAY_URL` override for tests and development (plaintext `ws` is loopback-only).
The supervisor owns that socket and at most eight phone tasks; switching off, changing method, closing the move gate or shutting down cancels the link and joins its phone tasks.
Each peer has eight inbound frames, and the link has a shared 32-frame outbound queue; a full queue closes the affected peer with a content-free diagnostic.
Encrypted data and its routing close share that queue so the final refusal always precedes close.
Admission and sends have ten-second deadlines; each phone has one ten-second budget from arrival through Noise and its first credential message, and an unauthenticated connection never takes a paired-phone slot.
The link pings every twenty seconds and closes after sixty seconds without a response.
Each Noise receiver polls `check_timeout` once per second even without input; a ciphertext authentication failure, replay or unfinished chunk assembly closes only that phone and logs no content.
A lost link reconnects with equal jitter, from 0.5-1 second up to 15-30 seconds, with no retained transport retry queue.
The existing per-phone input request ledger survives link loss; input work runs beside the socket and is not aborted with it.
The blocking write itself owns a settlement guard, so cancellation of even its async waiter cannot leave a request permanently in flight; a panic settles uncertain.
The reconnecting phone reads the written, in-flight, refused or uncertain outcome without repeating an ambiguous write.
A method change waits for any Tailscale exposure in progress and its owned entry's removal before the relay can connect.
If the Tailscale CLI is gone, the obsolete ownership record is dropped and relay may connect, while the connection line retains the cleanup failure for the current daemon session.

Tailscale remains the advanced direct method, and `mobile/tailscale.rs` is the only file that knows its CLI.
It finds the CLI at `HIDE_TAILSCALE_BIN`, then the macOS app bundle's `/Applications/Tailscale.app/Contents/MacOS/Tailscale`, then `tailscale` on PATH, and reads `tailscale status --json --peers=false` for the backend state, `Self.DNSName`, `Self.HostName`, MagicDNS and `CertDomains`; every command runs with a fifteen-second bound.
The status is read without the peers because the full answer lists every peer at about 1.2 KB each (34 KB on a tailnet of 27, 3 KB without them) and would pass the 1 MiB a command may print on a tailnet of some 900, blocking Mobile; hided reads none of the peers' fields, and an answer past the bound is a failure that names the bound, never a cut one.
Every command carries `TAILSCALE_BE_CLI=1`: the app bundle's executable is both the app and its CLI, and it acts as the CLI only when its environment looks like a terminal (`SHLVL`, `TERM`, `TERM_PROGRAM` or `PS1`), which hided's never does, so without the variable every command started the app and timed out ([Tailscale CLI](https://tailscale.com/kb/1080/cli), macOS); the plain CLI on Linux and Windows does not read it.
Every command runs as an owned child under a 15 s deadline and a 1 MiB output bound (`OwnedChild::capture_until` in `hide-platform`, on a blocking task) and is answered when it has exited and its tree has ended, never when its output closes: on macOS a child another thread starts while the command's pipes are being made keeps the write end for as long as it lives (the platform layer's account of #729), and waiting for the output's end ran a command that had exited in milliseconds to the deadline, which failed a `status` read and, twice in a row, took the exposure down (with-hide/hide-private#524).
hided binds loopback as before and adds `tailscale serve --bg --yes --https=443 http://127.0.0.1:<port>`, then confirms the entry with `serve status --json` before a QR is shown.
It records the entry before running the add, so an add that took effect and then failed or timed out is still recognised as its own on the next pass.
It refuses to expose while `AllowFunnel` covers that HTTPS 443 name, in the saved config or a foreground session's, because Funnel would publish the address to the internet, and says so on screen; a Funnel turned on after exposure takes hide's entry down and closes every phone until it is off.
A change of hide's own settings (the switch, the method) and the start each owe one pass, and a pass settles every change it read, so two changes that arrive before a pass starts run one pass and never a second one against Tailscale as the first left it; Settings opening and the clocks below force a pass because they ask Tailscale again (`PassOwed` in `hided/src/mobile/mod.rs`).
Settings › Devices rechecks every three seconds while this machine's own window shows it, and with no one watching hided reconciles once a minute while Mobile is on, and while a removal is still owed after it was switched off, so a Tailscale that starts late is picked up and a failing command is retried at that pace; an exposed Mobile keeps its exposure through one failed Tailscale read and drops it on the second in a row, and a pairing code is minted only by `mobile_show_code` (the QR window Add device › 폰 opens), never by opening the tab, by a background pass or by a phone pairing; `mobile_hide_code` (the QR window closing), the last Devices page closing, and a pass that finds the code expired take it out of the frame.
It owns only the entry it recorded (`{dns_name, port, added_at}`): an HTTPS 443 handler it did not record is shown as the foreign target and left alone, an entry for its old port is replaced, and switching off or a clean exit removes it with `serve --yes --https=443 --set-path=/ off`.
Every start reconciles the record, so a crash's leftover entry is repaired or removed on the next start; `run_daemon` answers SIGTERM and SIGINT with the same shutdown, which removes the entry before the process exits.
A failed command leaves Mobile unexposed with the step that failed on screen, and its command line and stderr go to a `mobile_transport` record; a removal that fails at switch-off stays on screen and is retried until it succeeds, and shutdown waits for a reconcile already running.
While exposed, `https://<Self.DNSName>` joins the allowed WebSocket Origins, and only a phone handshake may use it; a desktop handshake from that Origin is closed with 4002.
A request that arrives through `tailscale serve` (a forwarded-for or Tailscale identity header, or a Host that is not loopback) reaches only `/m`, `/m/*`, `/assets/*` and `/ws`, everything else answers 404, and its `/ws` takes only a phone handshake from the Mac's tailnet Origin while Mobile is exposed, whatever other Origin it claims, with a 64 KiB frame limit.
Every handshake has ten seconds to send its first frame.

The core decides the phone list: `hide_core::agent_state::phone::project` returns the groups, and the phone draws them without sorting, nesting or cutting anything itself.
It reuses the sidebar's rules instead of a second set: the tree depth is `lineage::TREE_LEVELS`, a parent's children come from `lineage::children_in_order` (the parent's own child order, the most urgent `tree_rank` first, which the sidebar's `sidebar_tree` calls too, so the two cannot order siblings differently), the raised caps are `scope::RAISED_SHOWN`, and `lineage::SIBLINGS_SHOWN` is the five siblings per parent.
The core holds that last number once: it rides the snapshot as `navigator.siblings_shown`, and the sidebar, its popover and the Sessions tree in `web/` read it from there and raise when it is missing, so no TypeScript constant repeats it.
Groups stand in `turn::recent_first` order, the order `sort_agents` gives every surface.
`phone/tree.rs` builds each group from the rows of this Mac and of every connected device together, so one order covers them all, hangs a child under the parent that lists it (a delegated row whose parent is not listed is a root again; what lies deeper than the second level waits flat behind that row's `more_children`, so every agent stays on the phone to open or answer), and folds a group to its newest 5 (working and needs_you) or 3 (done and seen); the revisit group does not fold.
A group is `{group, count, rows, more, more_asleep}`: `count` is every top row including the folded ones, `rows` the shown ones and `more` the folded ones, each a tagged `agent` or `sleeping` row; a parent carries `children` (at most five), `more_children`, `children_open` (a descendant asks the operator) and `descendants {asking, working, done}`.
The frame also carries `devices`, this Mac and each remote with whether it is connected and its needs-you and working counts over top rows, which the header and the device sheet read.
A list frame (`agents`, `missions`) is one relay message, which `noise::MAX_MESSAGE` (256 KiB) bounds and past which the relay refuses it and closes the session, and both are in a connection's first frames, so a list that grew past it would close every reconnect again; each list therefore keeps within `phone::LIST_BUDGET`, the limit less 4 KiB for the frame's own fields, measured as the JSON it is sent as (`phone::FRAME_LIMIT`, which hided asserts equal to `MAX_MESSAGE` at compile time).
The agents frame's copy of the groups (`Projection::wire`) leaves rows out only when the whole list is over: folded top rows first, then the children of the rows left, then shown top rows, each the oldest first and group by group from the end of the drawing order, every other group before 내 차례, whose rows wait on the operator, so no row there goes while another group still has one; `count` stays every top row, `more_asleep` counts what `more` still carries, and the frame's `omitted` counts every agent left out, which the phone shows as one dimmed line under the list (`mobile.omitted`, the PR list's line) and hided records once per connection as `agents.capped`.
The projection itself stays whole, so notices and lookups never read the cut copy; a mission step whose worker's row was cut opens nothing, as one whose row the list does not hold.
The phone keeps only choices in its store (`childrenOpen` and `foldsOpen`, pruned to rows that still exist on each frame); it sends no event and moves no sidebar state.
The wire types are the `phone` module of `hide-core/src/agent_state/tally.rs`, `hided/src/mobile/phone.rs` puts them in the frame, `tally/phone/tree.rs` and `phone.rs` carry the tests that pin the shape, and the phone's `protocol.ts` mirrors it.

The phone app is a static shell and a data channel, kept apart.

`web/src/mobile/loader.tsx` is the small start page for `app.withhide.dev`; `web/src/mobile/main.tsx` is the same phone UI served directly at `/m/` and as a versioned relay bundle.
`pnpm --dir web build:phone` writes `web/phone-dist/`: the root `index.html`, `protocols.json`, root manifest and `/sw.js`, shared icons, and `/p/<PHONE_PROTOCOL>/index.html` with its own hashed assets.
`PHONE_PROTOCOL` is declared in `web/src/mobile/phoneVersion.ts` and, as the number the relay announces, in `hided/src/mobile/relay.rs`; the two are raised together, and only for a change an older side would misread.
It is 5: protocol 2 is the agents frame that carries the list as a tree (below), protocol 3 a page View's screenshot, protocol 4 the `prs` frame with the pull request requests (below), and protocol 5 the `html` kind of a View and its `look_head` mode (below).
A bundle opens only against a Hide that announces its own number, so every raise sends a phone whose Hide is a build ahead of the hosted site to the update screen until the next release candidate uploads that number's bundle; that is why an addition does not raise it.
An addition keeps the number and works in both directions:

- A new frame type is ignored by an older bundle (`applyFrame` in `web/src/mobile/store.ts` passes over a type it does not know), and a newer bundle draws the screen it feeds only once that frame has arrived, so against an older Hide that never sends it the screen stays away.
- A new field of an existing frame is optional: an older bundle ignores it, and a newer bundle reads its absence as this Hide not offering it.
- A new request is sent only from a screen or control drawn because of such a frame or field, so an older Hide does not receive it; one it does receive is answered `refused_request` with the request's type, and the connection stays open.

The number is raised when an existing frame, field or request changes shape or meaning: a field renamed, removed or retyped, a new value in a field whose older readers have no fallback for it, or a request whose older answer would be misread.
Each release candidate replaces its number's bundle with its own build, so the bundle under a number works against every Hide that announces that number.
Deployment retains older numbered directories and lists the available numbers in `protocols.json`.
Only main's release-candidate CI deploys that site, before preparing the desktop release; a failed phone upload or production check stops the candidate and therefore the private publisher.
[BUILD.md](../BUILD.md#the-hosted-phone-release) owns retention, deployment secrets, CSP and the production check.
The root reads only the relay's `phone_protocol` metadata and opens that exact supported bundle, never a closest or newest fallback.
A paired device that is offline can open its saved protocol bundle and let the shared connection retry; a changed version returns through the loader.
An unsupported number stays on the update screen with the phone and device protocol versions.

`hosts.ts` owns one bounded browser storage record: at most sixteen paired devices, each with its room, plain-text display name, QR-authenticated Noise public key, credential, last protocol and last successful contact.
Corrupt records and storage refusal are visible failures; QR codes and conversation content are never persisted.
The QR fragment is cleared synchronously before WASM initialization and relay access; its name is escaped React text that wraps on the landing screen.
`relaySocket.ts` is the socket boundary used by the existing connection and command code: the shared WASM crate performs Noise NK, then the first encrypted message carries `{client_kind:"phone", pair}` or `{client_kind:"phone", token}`.
This boundary compares the relay's phone protocol with its own bundle before starting Noise, for both the main connection and every presence observer.
A mismatch closes without a handshake, credential or app frame; the main connection returns to the loader, while a list observer stops retrying and gives its row both versions and a loader action.
The direct `/m/` socket keeps its existing handshake and UI.
A relay socket owns its handshake deadline, chunk deadline check, and Noise memory; closing disposes all of them, and the browser send buffer is capped at 1 MiB with no retained application send queue.
Reconnection keeps the existing command request identities and adds jitter; no action is automatically replayed by the transport.
The host picker opens at most one extra read-only connection per other saved device only while its list is visible; it authenticates for counts but never opens an agent detail or sends an action.
The gathered view (`web/src/mobile/Gathered.tsx`, its rules in `gather.ts`; PRD device-connect-iroh D-56, D-69) opens the same read-only observer (`presence.ts`) for each other saved computer only while 모두 is on screen and the page is visible, and keeps only each list's `needs_you` and `done` groups; it joins them newest first by each row's `changed_at_unix_ms` (a sleeping row's `since_unix_ms`), adds the groups' counts and keeps each core's own fold, so no phone constant repeats a core's cap.
A computer whose relay announces another phone protocol is never authenticated to, by the observer's existing check, and shows as `<컴퓨터> 업데이트 필요`; one whose socket is closed shows 연결 안 됨 and its rows leave the view.
The view is offered only when the open computer's `hello` carries `device_connect: true`, an addition every hided from 1.2.12 makes, so an older bundle ignores it and an older computer keeps today's list; the phone keeps that answer with the computer's saved pairing (`PairedHost.deviceConnect`) and reads it until this page's hello arrives, so a computer that is off from the start still gathers the others.
The observer also keeps each computer's automations that stopped for a person (`asksOf`) and the count its list left out, which the view adds to 내 차례 and says under the list.
The hello also names the computer's product device id (`machine`, its node id), which the phone keeps with the pairing (`PairedHost.machine`), and the `meta` frame adds `machines`, each other machine this computer opens that tells it work of its own (`navigator.peer_work`), by that id and the name `navigator.peers` gives it, sorted by name and at most 16 (`mobile::other_machines`, read by `Mobile::follow` from the follower's inputs, which carry only those ids and names (`projection::update_inputs`), so a count another machine tells rebuilds nothing, and published only when it moves); both are additions an older bundle ignores, and a computer that opens no such machine sends neither.
The phone hints once at the first of those it keeps under no saved computer, by that id, or by name while a saved computer's hello has not named one yet (`web/src/mobile/addHint.ts`, PRD device-connect-iroh B56, D-57); closing the hint or pressing [추가] records the machine in the phone's own storage (`hide.phone.add-hints.v1`, at most 16, oldest forgotten first), and it never shows again.
The in-app scanner uses bundled `jsqr`, one camera and at most 640 by 640 pixels at four scans per second; hiding or leaving it stops every track and timer.

The hosted manifest starts at `/` so an installed app can add another device in its own storage.
The same `/sw.js` is registered once at `/` for the shell and once at `/push/<room>/` per saved device for push, since each device owns a different VAPID key.
Removing a device unsubscribes and unregisters its exact push scope before removing its credential; it never unregisters the root worker returned by an ancestor-scope lookup.
A notification retains the registration's room and opens `/?host=<room>&open=<device_id>|<pane_id>`, which selects the correct bundle and agent.
Only static responses and translated notification words are cached, never device data; the shell cache is bounded to 128 entries and old shell versions are removed on activation.
The app build embeds a strict CSP allowing same-origin scripts and `wasm-unsafe-eval`, same-origin assets, same-origin frames and the declared relay WebSocket; there are no external scripts, analytics, login or payment paths.
The one same-origin frame is `look-frame.html`, beside the bundle's page (`/p/<N>/` hosted, `/m/` on the tailnet), where an HTML View is drawn (below); it keeps a policy of its own, and the service worker leaves a frame's navigation alone so it never takes the app page's place in the cache.
`VITE_HIDE_RELAY_URL` is the only public build override: a credential-free WSS URL, or a loopback WS URL for isolated development.
Physical iPhone home-screen storage, camera and multi-registration push delivery require device verification; emulated viewport and service-worker tests do not prove those OS boundaries.

The direct Tailscale shell remains as follows.
`/m/` serves `mobile.html`, and `/m/manifest.webmanifest`, `/m/sw.js` and the icons come from `web/public/m/` through the same static route as the desktop shell's `/assets`; the page, the service worker and the manifest are served `no-cache`.
The service worker caches only that shell, so the app opens without a network and shows its unreachable line.
Pairing, the agent list, an agent's conversation, a pane's rows, replies, keys, starts and the push subscription travel on `/ws` only; HTTP fetches carry only static shell assets and the hosted protocol manifest.
The first frame decides the client: `{client_kind: "phone", token}` for a paired phone or `{client_kind: "phone", pair, name}` to pair; a phone counts toward `MAX_CLIENTS`, and a refusal sends `{type: "refused", reason}` (`code_expired`, `phone_limit`, `revoked`, `mobile_off`) and closes with 4001.
Every application frame to a phone goes through `mobile::phone::encode`; on a relay connection this calls the shared Noise session's `send_message`, including refusals and pairing credentials, and only ciphertext reaches the routing queue.

A pairing code is sixteen random bytes, is accepted only while Mobile is on and exposed, lives only in memory for five minutes, is spent by the first phone that uses it, and is replaced only when `mobile_show_code` is sent again; opening Settings › Devices issues none and voids none (B58).
The relay QR is `https://app.withhide.dev/#pair=<base64url QR v2>`, carrying the device name, signing public key, Noise public key, derived room and code as specified in `RELAY_PROTOCOL.md`.
The advanced direct QR remains `https://<DNSName>/m/#pair=<base64url {v:1, endpoint, code}>`; neither code reaches a request line or a log.
A paired phone gets a 32-byte credential; `phones.json` (mode 0600) keeps only its SHA-256, compared in constant time, with the name it paired under, the name the operator chose for it (`chosen_name`, written only by a rename and read past by an older build, which shows the paired name), the last connection, the notification answer, the push subscription and its pairing scope (`PhoneOrigin::Relay` or the tailnet name); a rename is written before the frame shows it, and the frame's `name` is the chosen one with `own_name` the paired one beside it.
The phone keeps the credential in its storage and in its address fragment (`#k=`), because the manifest has no `start_url` and a Home Screen app starts from the address it was added from, whose storage iOS may keep apart from Safari's.
At most four phones pair in one scope; the limit is checked before the code is spent.
Only phones in the selected relay or tailnet scope count (PRD mobile-relay B7, core-host-node-move B17): they are listed in Settings › Devices' phone group, receive pushes and are let in, and the limit counts them; a switch-off or a failed check leaves that name as it was.
A phone paired at an address the core is no longer exposed at waits unlisted, and a credential of its is answered `mobile_off` (the phone stays paired and shows the core as unreachable); the seven-day rule below ends it otherwise, so no more than four phones per address of the last seven days are kept.
Switching methods hides the other scope's phones without revoking them; switching back restores them.
`mobile.json` retains the last verified tailnet name separately from its owned Serve entry, so removing that entry or an offline Tailscale does not erase the direct phone list.
A record from before phones kept their address reads as `Unrecorded` and takes the exposure `mobile.json` names at the first load, or the first exposure.
A phone keeps at most two connections, the oldest closed first, a connection that answers no ping for 45 seconds is closed and recorded as `phone.silent`, and one whose frame cannot leave within ten seconds is closed and recorded as `phone.stalled`.
A phone away for seven days is revoked at start, by an hourly sweep and when it next connects, and a revoke, manual or automatic, drops the credential and the subscription in one write and closes that phone's connection.

A phone's whole vocabulary is `open`, `view`, `older`, `more`, `close`, `input`, `look_open`, `look_ack`, `look_seen`, `start_sheet`, `start_agent`, `answer_mission`, `ask_mission_material`, `reopen_mission_view`, `read_pr`, `merge_pr`, `read_pr_feedback`, `delegate_pr`, `wake_agent`, `wake_sleeping_session`, `check_sleeping_session`, `push_subscription`, `apns_registration`, `fcm_registration`, `push_permission` and `ping`; anything else is answered `refused_request` and recorded as `scope.refused`, and a phone never receives a path, a setting or the core snapshot, and a file only as the content of a View that is open now and that it asked for by the View's id (next paragraphs); the one setting that reaches it is the interface language, which rides every `agents` frame as the core's stored value or null (the phone resolves it, and follows its own system language on null, before the first frame and when unpaired).
A phone looks at the Views of the agent whose detail it has open (`mobile/looks.rs`, PRD mobile-companion-ui D-06 to D-10, D-15, D-16).
The detail's task asks the core for the Views opened by that agent's session that are open now, in every checkout (`Core::agent_looks`, `view_sessions.rs::phone_looks`: newest first, one row per shown file, at most 64 with the rest counted as `omitted`), and sends a `looks` frame of ids, kinds by extension, names, whether each is unseen and when, and a web page's address, only when the list changed; a frame never carries a path, so a local page's `file:` address is left out.
`look_open` names an agent, a View id and a request id and nothing else; a View is found only among that agent's open Views, so the phone has no way to name a path, a root, another checkout's file or a View that closed.
A field beyond those, an agent the list does not hold and an id that is not open now are each answered `look_result` (`refused`, `gone`, `closed`) and recorded as `scope.refused` with `look_field:<name>`, `not_an_agent` or `view_not_open`; `phone.rs::look_scope` decides the first two and its unit test holds a path, a root, a checkout and a file among them, and `hided/tests/it/mobile.rs` sends the same over a paired phone's socket and sees no content come back.
The path stays in hided: the core's `LookView` carries it to the readers the desktop's `file_bytes` uses, `server::send_file_bytes` over this Mac's boundary and `server::stream_device_file_bytes` for a device's checkout (`device_root_known`, the same stamp checks), which write to a `FrameSink` so the one reader serves a socket and the relay's queue alike, and a path is confined to its checkout by the same checks for both.
A file outside every checkout that an agent opened (`outside_open.rs`) has no path in the core at all: its `LookView` carries the desktop window's grant, name and viewer kind (`ExternalFile`), and hided asks this Mac's registered window for the bytes by that grant each time the phone opens the View (`BrowserControl::external_read`, `POST /external-read` with the control token, answered by `ExternalFiles.readPart` in `desktop/src/main/externalFiles.ts` as the first bytes up to the cap with the file's size in `X-Hide-Total`, or a reason).
The window reads the file now, through the same physical-path and no-link checks its own tab's read uses, so nothing is copied, kept or marked as a copy; an HTML page's folder files come the same way, named relative to the page's folder, which is its grant's reach.
A grant lives in the desktop host's memory on every system (it is not sandboxed on macOS, so no security-scoped bookmark is involved), so after the app restarts an agent's View names a grant the host never had.
The window's reasons become states: `grant_expired` for a grant it does not hold, `not_found` for a file gone, `file_replaced` for one that became a link or something that is not a file, and `no_window` when no window is registered or its shell is not attached (`looks.rs::outside_state`).
The reply is `look_changes` for a diff (`changes::read` run on a blocking thread after `Core::prepare_checkout_changes` built its request in a short step on the owner thread; at most 200 files with their +/- counts and no code line; each row says `binary` when Git tracks the file and could not count it, and an untracked file, which the desktop's list shows no number for, has none), `look_result` `page` with its address for a web page whose screen cannot be taken now (the desktop's screen of it arrives as a `look_head` of mode `page`, below), `other` for a PDF, a video, another binary or a document that is not UTF-8 text, `too_large`, `closed`, `not_found` for a file the readers no longer find, `outside_roots` for one outside every checkout they read (`looks.rs::refusal_state`; a device's helper answers the same two refusals as this Mac's boundary, `server.rs::device_refusal`), `grant_expired`, `file_replaced` or `no_window` for an outside file (above), `failed` or `device_unreachable`, or the bytes of a text document or an image; a phone bundle that does not know a state shows it as `failed`, so the new ones need no protocol version.
Bytes travel as JSON text, because the relay carries nothing else: `look_head` (mode, size, chunk count, whether the cap cut it), `look_chunk` of as many bytes as one relay frame carries as base64 (`CHUNK`, about 48 KiB, from `hide_relay_protocol::noise::CHUNK_DATA`) and `look_end`.
A web page's screen is the desktop app's picture of it (`mobile/page_shot.rs`, PRD mobile-companion-ui B20-B22, D-11): the core lists the View's checkout as a checkout caller (`checkout_caller_id`, no pane) for the display's kind and area, and `BrowserControl::display_still` asks this Mac's registered window for its picture (`POST /display-still` with the control token and the display's scope, refused for an area the core no longer authorizes; a node's window is `window_elsewhere`), which the host takes with Electron's own capture of the page (`BrowserViews.still`, scaled to at most 1.5 million pixels, JPEG quality 70).
A still is a read and asks no `require_visible`: a display behind another tab of its area is taken as it draws there; a page the host let go (`not_loaded`) or never drew, laid out off screen and never shown (B32), whose capture is an empty image (`not_drawn`), has none.
Electron counts a page visible while `capturePage` takes it (`stayHidden` false), so a page behind a tab may see a `visibilitychange` on each phone refresh; that is likely why it draws where the debugger's capture does not, and capturing with `stayHidden: true` is not a safe change without measuring it again.
It is not the capture `hide browser screenshot` takes through the page's debugger, which answers only while Chromium draws the page on an unlocked screen (`docs/BROWSER_DISPLAYS.md`, the measurement beside the display rule).
Nothing in the chain selects a View, moves keyboard focus, raises a window or loads a page (B22), and the phone never asks the desktop to show a page.
It holds one of the browser control's request slots (`acquire`) for its whole life, as `hide browser connect` does, so a refresh storm is refused rather than queued, and refuses a picture over the 10 MiB image cap; the window's answer is bounded by the browser control's 8 s request (`REQUEST_TIMEOUT`), the host's capture by 5 s (`STILL_WAIT_MS`, answered `capture_timeout`, so a capture that never answers frees its gateway slot), and the whole still, the core's view list with it, by 20 s.
It leaves as `look_head` of mode `page` carrying `url`, `taken_at` (ms) and `taken_by` (the device id of the Mac), then `look_chunk`s and `look_end` like an image, one at a time; the phone shows a head that lacks any of the three as a failed read.
Every refusal (`not_loaded`, `not_drawn`, `window_elsewhere`, `no_window`, `browser_control_busy`, `timeout`, a closed display or an unavailable window) is one `look.page_unavailable` diagnostic with its reason and answers the phone `look_result` `page` with the address, and with `reason` for the three the operator can act on (`looks.rs::page_reason`): `no_window` when no desktop window is registered here or on a node, `window_elsewhere` when the window is a node's, and `not_drawn` for a page the host let go or never drew; a phone bundle from before `reason` ignores the field and shows the plain sentence.
A refresh is a new `look_open` for the same View id; the new one replaces the transfer in flight, so a repeated tap never runs two screenshots at once.
The wire of this is phone protocol 3.

An HTML file of a checkout is drawn by the phone itself, opened as a file or as a page (kind `html`, `mobile/html_look.rs`, with-hide/hide-private#689): a file View whose name the desktop's rule reads as HTML, or a page View whose `file:` address is such a file inside its checkout.
hided reads the page through the same readers, up to the image cap, then each file of the checkout it names by a relative address (`src`, `href`, `poster`, `srcset`, CSS `url(...)` and `@import`, found by a scan rather than a parser) and what its stylesheets name, while they fit under that cap and 64 files, and writes each back into the text as a `data:` address; an address on the internet stays as written, a file outside the checkout is never read, and what is missing or past a limit stays as its address and is counted once as `look.html_files_left`.
The folded document leaves as a `look_head` of mode `html` and its chunks like any read, `too_large` when the folded document passes the image cap.
The phone draws it in `look-frame.html` (`web/public/m/look-frame.html`), loaded `sandbox="allow-scripts"` without `allow-same-origin`, so its scripts run in an opaque origin that reaches none of the app's storage, credentials or connection; the frame says it is ready, the viewer posts it the document, and the frame writes it over itself.
The frame's policy lets a generated page run inline and CDN scripts, styles and fonts and its `data:` files, and refuses `connect-src`, forms, frames, workers and plugins, so nothing it runs talks back; the hosted release serves it with that policy as its header and `frame-ancestors 'self'` ([BUILD.md](../BUILD.md#the-hosted-phone-release)).
The wire of this is phone protocol 5.

Text is capped at 1 MiB (the first 1 MiB, with `truncated`) and an image or a folded HTML document at 10 MiB (refused from the size the first frame reports, so it is never read whole).
The relay drops a phone whose eight-frame queue fills (`hide_relay_protocol::frame::MAX_QUEUED_FRAMES`), so a transfer is paced by the phone and never by a timer.
The budget belongs to the connection, not to a request: one ledger per phone connection (`looks::Pace`, kept for the connection's life beside its transfer) numbers every View frame it sends, and a `look_ack` of chunk n of the current request, and only of a chunk that request sent, marks every frame up to it as gone, an earlier transfer's included, since the relay keeps a socket's frames in order.
A frame leaves only while fewer than `LOOK_FRAMES` (three: the socket's eight less the five relay frames of the largest frame a phone is sent, `FRAME_LIMIT`) are out, so a phone that opens one View at a time has room for a list or a conversation page of any size beside it.
The one exception is a new transfer's head and chunk 0, or its end when it has no chunk: the phone drops a transfer it gave up without confirming it, so only the new transfer's first confirmation can prove the old frames gone, and holding them back could wait forever.
A View opened before the last one's chunk 0 was confirmed therefore adds two frames: after one such reopen five are out and about 196 KiB is left for the rest, and only a phone that opens three Views in a row without receiving anything can fill the queue (`a_phone_that_reads_nothing_never_fills_its_relay_queue` seals each frame in a real session and holds the bound, `LOOK_FRAMES` plus two for each reopen).
One transfer sends at a time, a new `look_open` replaces it, and it ends with the detail or the connection.
The phone puts the chunks back in order and refuses a head over its cap, a chunk out of order or more bytes than the head said (`web/src/mobile/lookContent.ts`).
`look_seen`, sent once the phone drew an answer about the View (its content, or a name, a kind, an address or why a file cannot be read (`not_found`, `outside_roots`) where there is none to show; not a loading, closed, failed or unreachable screen), marks the View seen through the Desk's own seen-by-id event, `desk_output_seen`, dispatched on a blocking thread like every other phone dispatch, since a dispatch waits on the core's owner thread, the same one its lane sends (D-15); the core accepts that one event while Desk is off, because a View's seen state is the core's and not Desk's.
A document or image on a device is read only while the device's helper is linked (`CoreHandle::node_link` first): a device that is not answers `device_unreachable`, as its change list does, and a read that fails after the link was up answers `failed`.
The phone's list puts an agent with a View not seen in Needs You as the desktop's does (`PhoneAgent::group`), and notices keep following the group it would have without the View (`PhoneAgent::notice_group`, D-13).
A web page's screen is the web-shot node's work; until then its row opens to the address.
A page cannot see the protocol-level ping hided sends, and a Mac that went to sleep leaves the phone's socket open until the phone's operating system gives up on it, which can take minutes, so the phone checks hided itself (`web/src/mobile/connection.ts`, `phone.rs::liveness`).
A slow pane write (a reply or key to a device pane can wait out an SSH channel open) runs beside the socket loop like a start, so a `ping`, an eviction or a revoke is never held behind it: one input per connection is written at a time, a second is answered `in_flight`, and the write is not aborted when the connection ends because its request id must still be settled (`phone.rs::spawn_beside_loop`).
`ping` carries a number and hided answers `{type: "pong", id}` from one in-memory admission check, with no core lock, no engine call and no read of the list; a phone no longer let in is sent `refused` with its reason instead, and a `ping` without a number is refused and recorded as `scope.refused`.
The phone keeps one timer per connection and counts any frame from hided as proof it is there, so a phone that is receiving never pings: after 20 seconds of silence it sends `ping` and gives hided 10 seconds to send anything, then closes the socket from its own side, without waiting for the browser's close, shows the unreachable state and retries as for any loss.
A silent hided is therefore shown as connected for at most 30 seconds after its last frame; returning to the foreground or regaining the network sends a `ping` at once with the same 10 seconds, and a hidden page asks nothing.
A new socket that says no `hello` within 15 seconds is given up the same way, so a retry toward a sleeping Mac does not wait for the browser's own connect timeout.
A phone starts an agent through the same `agent_start_in_checkout` event as the desktop (`mobile/start.rs`, PRD home-device-rail D-24, D-25), marked `stay_behind`.
`stay_behind` is the one word that tells the core the start did not come from the operator's own screen: the task slot keeps it (`TaskOperationSnapshot::stays_behind`, never sent to a shell), `ingest_task_operation_result` then leaves the terminal, the keyboard focus and `selected_pane_id` where they were, and the tab request asks the engine not to focus the tab it makes (`CheckoutTabRequest::focus`, the same `focus: false` a branch migration sends).
The tab is made and listed as for any start, so the new agent appears in the sidebar and in the phone's list, and the phone opens its detail from that list; ⌘N, New worktree, an issue's Start and the desktop card's pull request hand-off send no such word and keep bringing their tab forward; the phone's hand-over of a pull request sends it (below).
While its start sheet is open (`start_sheet`), hided sends it a `start_catalog`: every device's checkouts as targets named by id, each with its place (`project · branch`), and apart its project's name and id, its branch (none for a folder) and `main` on the project's main checkout (the one the core marks primary, else the first it lists), the core's machine's system (`core_platform`, from its device row's `host.platform`) for the phone to name that machine in its language, `claude` and `codex` with the models the provider catalog lists, and the choice the last start remembered; the sheet counts as a start surface for the catalog demand, and the folder a target id leads to stays in hided.
Past 256 targets (`MAX_TARGETS`, `hided/src/mobile/start.rs`) the catalog keeps the ones whose project was used last, in the order it lists them, and `omitted` counts the rest, logged once as `start.targets_capped` when a build first crosses it; the field is optional, so an older phone bundle reads the frame as before and `PHONE_PROTOCOL` stays.
The project fields are additions of the same kind: an older bundle names each target by its place, and the phone reads a target without them, from an older Mac, as a project of its own; at the cap the frame stays far under the relay's 256 KiB for names of ordinary length.
`start_agent` carries a request id, the text, a target id, a kind and an optional model; it is refused before anything is dispatched when the phone is no longer admitted or the target, kind, model or text is not one the sheet could have sent, and otherwise answered with `start_result` once the core's task slot or last error carries that request id, or `timeout` after 90 seconds (`start::ANSWER_LIMIT`, the core's own limit for a start).
A request id the phone repeats is started once: the repeat gets the first answer, joins it while the first still waits, or, after a `timeout`, follows the same start again without sending it; one connection waits for one start at a time, and a second is answered `in_flight`.
The list is `agent_state::phone::project` over the snapshot's `rest` section (`agent_state/tally.rs`, called by `mobile/projection.rs`): the local navigator's agents and every connected device's, in the desktop's four groups, each keyed by device id and pane id with its lineage root.
The core supplies each phone group’s order and count; the phone renders both without recounting.
Sleeping conversations are separate safe rows in that projection, carrying only their `SleepId`, provider, title, canonical group, phase, age and action availability.
They carry no native session, cwd, former pane, close key or lineage, and can never open a pane detail or receive input.
A phone may wake or inspect only a currently projected local sleep intent, with an exact-key payload and renewed phone admission before dispatch.
Its correlated `sleep_result` acknowledges dispatch only; the core-owned row supplies progress or refusal, and a lost answer never triggers an automatic resend.
hided follows the core only while Mobile is on with a phone paired or a desktop window has agent notifications on, reads the snapshot off the core lock with its own cursors once per notification burst, and republishes the list only when it changed.
A detail shows the agent's conversation (`mobile/conversation.rs`) or its terminal, as the phone chooses with `open` and `view`, and hided reads only the one shown, once a second and only while it is open.
Claude Code and Codex draw in the alternate screen, so the pane holds no scrollback for them and a pane read returns only the screen; the conversation comes from the agent's own transcript instead, found through `hide-session` from the session the engine reports for the pane.
Only a pane on this Mac with a reported session whose adapter supplies conversation has one: a device's transcript is on the device, and the newest transcript in a pane's folder may be a neighbour's, so every other pane sends `{type: "conversation", state: "none"}` and shows its terminal, and so does a pane whose session has written nothing yet.
An operator's message carries the number of images the agent recorded with it and the names (the last part of the path only) of the files it recorded beside the words by their paths, such as Codex's image wrapper (`ConversationEvent::attached`), never the image bytes or the folders; a message of images or files alone is kept with no words, and a phone finds its own sent files by the upload id in those names or in the paths at the front of the words.
A page is the newest 30 messages, or 256 KiB of their text, before a byte cursor, read backwards in 512 KiB windows (`hide_session::read_page_before`) and never more than 8 MiB a request; the offset of its oldest message is the cursor `older` sends back, and the phone keeps at most 300 messages.
What the agent appends is read the same way down to where the last read ended, when the file's length changed, so a transcript line of any size is passed over rather than stopping the reader; a catch-up past 8 MiB, or a file that shrank, sends the newest page again.
Cursor pages follow native turn and step references backwards under the same 30-message, 256 KiB text and 8 MiB read limits; polling follows its graph checkpoint rather than database length, so a same-length native append is observed and a rewritten prefix resets the page.
An older Cursor pager requires its retained source stamp to remain current, and every page and idle poll repeats native owner and checkout proof.
Only the operator's prompts, the agent's text and an interruption leave hided, each cut at 20,000 characters and marked; tool calls, tool output and injected context stay on the Mac.
Three things of a call are the exception, all only to a phone whose open detail is that agent's, and only from a computer whose `hello` carries `answer`: the kind and start of the command that runs now, never what it runs, the first of the command a permission waits on, and the id of the call an approval is tied to.
hided follows the agent's open calls in its session's thread (`mobile/calls.rs`, through `hide_session::thread`, the desktop conversation's reader), only while the agent works or a tool call waits for its permission: the first read takes the newest page, each later one reads forward from where the last ended, at most eight pages before it starts over from the newest, and it keeps at most 32 open calls, an operator's message ending every call before it; past 32 a new call is not kept and none open is dropped, and the list is marked full, with one diagnostic (`calls.full`), until an operator's message or a read from the newest page.
A `conversation` frame of `reset` or `append` then carries `running`, `{kind: "command", since_ms}` while the agent works with a command open (from the later of the call's record and the agent's last change of state, so a command allowed after waiting counts from the allowing) `{kind: "unknown", since_ms: null}` while the list is full and none of the calls it kept runs a command, since one it did not keep may, and `null` otherwise, and a change of it with no new message is an `append` of no message; the phone counts the clock (`명령 실행 중 · 0:42`), and for `unknown` shows neither that line nor the thinking one.
The waiting command reaches the phone in the `ask` frame below, its first two lines and at most 200 characters, marked when cut; the rest of it, which may name a secret, stays on the Mac.
A device's pane has no conversation here, so it has neither: [INSTALL.md](../INSTALL.md#what-each-system-supports).

While a detail is open hided also sends `{type: "ask", device_id, pane_id, ask}` when what the agent asks changes, `null` once it asks nothing (`mobile/ask.rs`); the list frame never carries it.
`ask` is the agent's own question, from its session's record (`user_turn`, with what the agent wrote under each choice, `UserTurnContent::note`), its plan waiting for approval, or, while the agent waits on approval its record does not name, what its session's open calls say it waits on (`Calls::pending`): with one call open, Claude Code's `ExitPlanMode` (`ToolKind::SwitchMode`) makes it the plan's approval and any other call a permission tied to that call, with the command it waits on where the call runs one; with none or several open, or the list full, a permission tied to no call. An agent whose table says `by_hook` (Codex) takes the command of its permission request hook instead (`asked`, `hide_agent_hooks::report::HookAsked`: `tool_input.command` cut to 1024 bytes, `apply_patch: <files>` for a patch), never the session's open calls, which are other commands that run; it ends with the session's next hook report of any kind.
Its fields are `kind` (`question`, `plan_approval`, `permission`), `turn` (the agent's last change of state, as a notice's Reply names it), `since_ms`, `text` and `truncated`, `call` (the call it is tied to, which the phone tells asks apart by), `command` and `command_truncated`, `choices` (`{id, label?, note?}`) and `answerable`.
A permission tied to no command is answerable only from an agent whose table says `by_hook` (Codex); any other lists no choices and sends the operator to the terminal, since its screen cannot be checked against the card and it may be a plan's, whose choices differ.
So does a permission whose command is more than one line or is cut (`command_truncated`): the phone allows only a command the operator saw whole, and only one line can be told on the screen from another command that shares its first line.
A question whose words the record does not hold is not an ask; it is answered with a reply as before.
A choice is never typed as its words: pasted, it is read as text, and the Enter after it picks whatever the screen has highlighted, which on an approval is nearly always the first, Yes (live-checks, 2026-11-23, on the seven agents).
The phone sends `input` with `turn`, `kind` and `choice` instead, and the core types the keys the agent's own screen takes for that choice, from the agent's definition file (`[answer]`, [Agent definition files](0018-agent-definition-files.md#agent-definition-files); `operator_input::choice_keys`): a question's choice by its place (`down` that many times less one, then `pick`), only when the record asks one question of one choice (`UserTurnContent::pick_one`); a plan's `approve` or `keep_planning`; a permission's `allow`, `allow_always` where the agent offers it, or `deny`.
The keys go through the same operator write as a quick key, each a key press with 80 ms between them, after the permit and the gate's admission, one key write in a pane at a time (`PaneInputGate::hold_keys`; another, from a second phone or a quick key, is refused `in_flight`).
The choice is checked against the ask the phone's open detail last showed (`ask::Shown`) when it arrives and again at the write's last step, with the live list: `stale` when the agent no longer asks that turn, or the ask shown is of another kind, call or command than the choice was made on, and `unknown_choice` for a choice the table does not reach or an ask that is not answerable.
The core then reads the pane's visible screen before the first key and before each key that counts from the highlighted row (`Typed::Choice`, `operator_input::Screen`): before the first key, an `esc` included, the lowest line that begins with the table's `marker`, past a box's border, must be one of the ask's rows and the agent's approval dialog must be drawn as for a one-line command (`permission.command` in its table: under the dialog's title nearest above the ask's first row, a separator line, one command line with no border or gutter, the same separator line again), its shape read before any of its text is taken for the command, and that line must be the whole of the one-line command the card showed, every space as it is and nothing beside it but its indent, so an Esc never reaches a command the operator allowed already, whose approval the agent holds open until it ends (Claude Code), and an allow never reaches another command that starts the same way, adds a command, an argument or a line after it, or differs by one space, nor one whose dialog names the card's command only in its note, in output outside the dialog or inside quotes; a dialog of any other shape types nothing; a command the screen wraps, cuts or scrolls off cannot be told from such a command, so it is refused too and answered in the terminal; before each key that counts from the highlight, that line must be the row the key expects, the first for the first key and one lower after each `down`, read up to six times 80 ms apart after a key this write typed; a read that fails after such a key leaves that key landed, so the write is `uncertain`, never refused.
Anything else stops the write before that key and is refused, `ask_not_shown` when the screen showed none of the ask's rows before the first key (answered already, or its allowed command runs) and `screen_differs` otherwise, so a highlight moved in the terminal, or another command's ask, never turns a refusal into an allow, and the phone sends the operator to the terminal tab.
What is left is an accepted limit: a key typed in the terminal in the few milliseconds between a read and the key after it, or one the program has not read yet when the screen is read, is not seen, since the write reads the screen rather than holding the terminal's keyboard; it needs the operator to press a key in the terminal at the moment they answer from the phone, and the next key's read stops most of it.
A window answers the same ask the same way (PRD desk-2-ui B14, `hided/src/mobile/screen_ask.rs`): `pane_ask` {device_id, pane_id} answers a `pane_ask` frame with the phone's `ask` body (`ask::of`), and `pane_choice` {request_id, device_id, pane_id, choice, ask} goes through `ask::keys` and the same operator write, refused with the phone's reasons.
A window is pushed nothing, so its choice carries back the `ask` body its card drew, untouched, which names its turn and kind, and is `stale` unless the agent asks exactly that at the press and at the write's last look, the same call, command, words and choices, since two asks can share one turn.
The phone's follower keeps a list only while a phone is paired, so both read the core when asked, one read per press and again at the write, on the blocking pool, one request at a time per connection (choices first, in order, eight at most waiting; the newest ask of each pane); a second press of an answered choice finds the screen no longer showing the ask and types nothing.

It remembers 256 answers (`ANSWERS_KEPT`) and lets one go only once its ask has certainly ended: one tied to a call when the agent asks on another call, since an ask names its call only while that call is the only one open, and one known by its turn once the agent's turn is later, since no ask can carry that turn again; an agent that asks nothing ends no ask, because the same call's approval can leave the screen while the agent works a moment and come back under a new turn.
At the limit an answer refused before anything was typed goes first, oldest first; when every one may still hold its ask, the new choice is not sent and the phone says to answer it in the terminal tab (`answers_full`).
An agent, or a kind of ask, with no table, or whose keys need a highlight its table cannot read, is drawn with its choices and `answerable: false`, and the phone sends the operator to the terminal; no path types a choice's words into such an agent.
The terminal reads the pane's rows through the engine (`read_rows`), 200 lines at first and 200 more per pull up to 1000, with soft wraps joined ([The pane holder](0010-pane-holder.md#the-pane-holder)), so each line wraps at the phone's width rather than the desktop pane's; it sends rows only when their text, truncation, last reported screen mode or the asked count changed.
The own engine reads that cached fact with the styled rows as `PaneRows`, without another holder connection, PTY read, worker or timer per phone poll.
The optional `rows.alternate_screen` field is sent only when true, before measuring the frame's byte budget; older phones ignore it and newer phones read its absence as false.
It explains why a full-screen program has no terminal history and offers Conversation at the output's top when there are no older rows to load, independent of the agent kind ([UI_BEHAVIOR.md](../UI_BEHAVIOR.md#the-phone-app)).
A `rows` frame stays within one relay message (`FRAME_LIMIT`, the relay's `noise::MAX_MESSAGE`): what the text takes as JSON, where an escape byte takes six, is measured against what the frame's other fields leave, and whole lines are kept newest first, an older line that does not fit what is left going whole (`hide_holder_protocol::styled::newest_lines`, `phone::rows_frame`).
The one exception, an operator decision on with-hide/hide#2439: a single line that alone takes more than the whole frame keeps its newest part, by the holder's cut rule (whole characters and sequences, its color opened again).
`more` offers older rows only when the engine reports it cut some (`truncated`), the 1000-line cap is not reached and the frame left nothing out, so a phone at the budget or the cap shows that nothing more is above and asks for nothing.
A holder that cut its read to its byte bound answers more than a frame holds, so that read always leaves something out here and offers nothing more (`HOLDER_CUT_KEEPS`): this build's holder keeps within `CUT_SLACK` of 1 MiB, and a holder built before it cut at a row's start, giving up at most one row (1024 columns of a 65-code-point cell, 260 bytes, in its longest style), so it keeps more than 600 KiB.
Every frame to a phone is measured once more as it leaves (`send_frame`): one past the limit is never handed to the relay, which would close the session and the phone reconnect into the same frame; it is logged `phone.frame_too_large` and the connection stays, and a frame whose request has a failure the phone already reads is answered with it instead, `rows` as `unavailable` and `look_changes` as a `look_result` of `too_large`, while any other kind is only logged.
A reply, a quick key and a choice go through the desktop conversation's own write (`operator_input::write`, above): a reply is typed as a letter's bell is, through the engine's `prompt_agent` (one paste where the program takes bracketed paste, then Enter after the prompt's gap), so an agent reads a slash command from the phone as the command (#2354); typed as the operator's (`PromptBy::Operator`), it also goes into a question or form waiting for text, and an engine refusal, which typed nothing, answers `input_refused`. The quick keys are `enter`, `esc`, `up`, `down` and `ctrl+c`, each typed as a key press.
Before that write the phone asks the pane's node for `input_permit`: the same creation request holds its byte reservation, so a fork's 64 KiB and 30-second caps include phone input and desktop keys together, with no second fork lookup in the core.
A permission waits behind earlier desktop input in the pane hold and controller writer before the phone can write.
A pane without a control attach is allowed: the permit changes neither attachment, grid nor focus, and the existing engine write still decides whether that pane exists and can take the input.
Permission is not delivery acknowledgment: `input_result.ok` becomes true only after the engine has taken the write; a discarded holder, a refused permit or a permission wait past 35 seconds returns `input_refused` before any write, keeps the phone's text and releases its request-id claim for a deliberate retry.
A failed engine write retains the existing uncertain-outcome rule, so a repeated id never sends it twice.
At most 64 permission callbacks wait per node or device link; the existing holder timer expires reservations in every creation or pane holder at 35 seconds (`INPUT_PERMIT_MAX_WAIT` in `hide-node-link`, which the core's and the phone's waits share), shutdown drops waiters, and the device writer wakes at that deadline to forget unanswered callbacks even without further input.

The callback only hands its answer to the waiting phone worker or device uplink; it never calls back into the node, takes the Runtime mutex or performs I/O, and adds no resident worker or timer.

After permission, the write goes to the engine directly, so the rule that a pane whose agent ends, sleeps or wakes takes no input is the core's input gate (`hide-core/src/input_gate.rs`), which the runtime keeps equal to its sleep records (an `Ending`, `Sleeping`, `Waking` or `Failed` record closes the pane; a refused end, a woken agent or a closed pane opens it).
A writer that bypasses a node's terminal (a phone's `input`, the agent's find keys) takes an admission from the gate immediately before its write and holds it until the write returns; a closed pane refuses it (`asleep`), never judged from a list read earlier, and the worker that ends the agent closes the pane first and waits for the admissions already held before it signals the agent, so a write admitted before the end lands in the agent and none lands behind it.
A write still held when the worker's six seconds pass is not waited out and not ended under: the worker signals nothing, logs `agent_sleep.drain_stalled`, and the sleep fails like an end the agent refused (the agent stays awake, the pane reopens, the pane backs off for an hour), so that write lands in the agent.
The gate is a flag and a counter behind its own small lock, taken by the runtime without waiting and by the end worker off the runtime's lock; nothing holds `Mutex<Runtime>` across a write.
A node's terminal drops a key, a paste and the bytes a screen answers its terminal with for the same panes (`TerminalControl::Asleep`, which the core sends from the same records); a paste already held for a pane that sleeps waits with the keys typed behind it.
That path is not behind the gate, because the node can be another machine, so a key or paste the node accepted before it heard `Asleep` can still land in the shell once the end has begun.
The window is bounded: automatic sleep never takes a pane on screen (`SleepStore::due` skips every pane of `agent_sleep_on_screen`, the core's shown tabs and a node's `shown_node_tabs`, less the tabs of a project no list shows and with the runs the automation screen shows), and a key reaches only the keyboard's pane, which is always shown; so only an operator who picks Sleep agent on a pane they are typing into, or a paste stalled at that moment, can meet it, and only for the time the node's `Asleep` takes to arrive.
