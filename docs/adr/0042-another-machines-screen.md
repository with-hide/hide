# 0042. Another machine's screen

- Status: Accepted
- Date: 2026-11-22
- Code: `hided/src/remote_screen.rs`, `hided/src/screen_net.rs`, `desktop/src/main/remoteScreens.ts`, `desktop/src/preload/remote.ts`

## Decision

### Another machine's screen

A guest's rail tile for its host shows the host's own Hide screen, the page and socket the host serves, drawn in the guest's window (PRD device-connect-iroh D-53, D-67, B17, B20, B63; with-hide/hide-private's `docs/device-connection-security.md` 8.3).
It travels the one connection the two paired with, on stream kinds of its own: `screen` (priority 0) carries the socket's control and terminal frames, `screen_bulk` (-100) carries the page, its assets and file bytes, which the host writes from a task of their own, so neither a page load nor a large read holds the screen's loop, and the questions of where the screen's browser pages load from (`/page-route`), and `page` (-100) carries each connection of those browser pages to the host's network ([BROWSER_DISPLAYS.md](../BROWSER_DISPLAYS.md#a-page-in-another-computers-screen)).
Splitting the socket's control and terminal frames over a further stream would take only 31 ms off the control's p95 and could reorder them, so there is none.

**The host's side.**
`hided/src/remote_screen.rs` registers both kinds at start, with the guest nodes, and each stream it is handed serves HTTP/1.1 over the stream's two halves: on `screen`, the upgrade to `/ws`; on `screen_bulk`, `/`, `/assets/*` and the upgrade to `/ws/bulk`; and nothing else, so `/health` and every route a token opens are not there. A connection holds two `screen` streams (a view, and the one taking its place) and eight `screen_bulk` (six page and asset requests at once and the two views' file sockets).
The stream says which machine opened it and under which grant and generation, read from the host's grants at that moment, and the view's socket ends with that generation ([Streams](0041-peer-connection.md#the-peer-connection)), so a pause or a removal ends the view.
A guest holds one view at a time: the second one it opens replaces the first, and the host holds four in all (`MAX_VIEWS`), apart from the eight seats of this machine's own windows (`MAX_CLIENTS`), so a view never takes a window's place and a window never takes a view's.
The view's socket asks for no token: the stream already proved the machine, and the page it serves holds none.
It is a `remote` connection ([Which connection may send what](0041-peer-connection.md#which-connection-may-send-what)), drawn as a window but never sent what only this machine's own windows get: no `pairing` frame, no `window_call`, no core move, and a `mobile` frame without the phone's QR code and pairing code.
What the view chooses of the operator's look (a pane, a tab, a device brought forward) is chosen in that machine's view, which hided says as it dispatches the view's events, and it counts only while that machine shows the view: each time a view is seated or ends, `RemoteScreens` tells the core the whole list of machines whose view is seated (`remote_views`, under its seats' lock so the changes arrive in order), so the view's end, whether its tile was hidden, its socket closed or its window went, ends that look on this machine, and its next view starts it again ([status-model.md](../status-model.md#hide-owns-the-read-axis-at-pane-level)).
Its terminals follow the hub's remote limits (`terminal_hub::Limits::REMOTE`, D-84): 64 KiB of unsent output per pane where a window has 1 MiB, frames of at most 32 KiB, a longer chunk cut on a base64 boundary, the pane that last took a key sent first, and a pane past its limit drawn again whole; a view that comes back is always drawn again rather than resumed, since what it missed may be past those limits.
A file read the view asks for is answered on its own `screen_bulk` socket, at most four at once (`VIEW_READS`), and a view whose bulk stream is not open is answered `bulk_missing`.
Assets are kept by the host's key, its build and the path, never by the build alone, since a paired machine could name another's build and have its file run as the other's page; at most 32 MiB each and 48 MiB in all, each entry counting its names and 256 B beside its body so empty answers fill the bound too, the oldest dropped first.
A guest asks each host for at most six pages and assets at once, waits at most 15 s for one of that host's places and 60 s for the whole answer, so a host that answers slowly or stops holds only its own places.

**The guest's side.**
The guest's daemon answers its own desktop at `/peer-screen/<device>/` and `/peer-screen/<device>/assets/*` with its own token, and `/peer-screen/<device>/ws` merges the host's screen and bulk sockets into one for the desktop; it opens them only when the host is a machine it opens with an active pairing and an active grant, and answers 503 with `not_paired`, `not_connected`, `paused`, `paused_there` or `no_grant` otherwise.
Each of those requests names the key the page was opened for (`?key=<64 hex>`, 400 without it), and one whose device is paired under another key now is `not_paired`: a device id names a machine, a key names the Hide on it, and a machine set up again after it lost its key is another host, so a page the earlier one loaded never reaches the later one.
The desktop draws the page in a sandboxed `WebContentsView` on its own origin, `hide-remote://<device>/`, in an in-memory session of that machine and key's own (`desktop/src/main/remoteScreens.ts`); the shell names the key it shows a machine under, and a page kept under another key is closed before that machine's page loads anew: the page's loads are fetched from the guest's daemon with the token the page never holds, and only `/`, `/index.html` and `/assets/*` are fetched; every other request, a navigation away, a new window, a download and every permission are refused and logged.
Its preload (`desktop/src/preload/remote.ts`) is bridge v1 and nothing else: the one socket, which the main process opens only while the tile shows and closes when it is hidden (close code 4012), and closes at once when more than one largest frame and 8 MiB wait unsent on it (a host that stops reading; the page connects again), a clipboard write while the view holds the keyboard, the app menu's commands while it shows, whether it shows, what this window calls the machine (the name the shell's show carries, one short line or none) with the language this window resolved and this window's View menu choices (the agent logo mode and the pane turn row mode the show carries, none when either is not a mode the build names), told once the page loaded and again when any changes, which the preload keeps from its start and hands at once to a listener that comes later (`onViewer`), and what the guest's operator asked of it (PRD device-connect-iroh D-73, D-78): one work to show by its pane, or a start to make there, handed once the page loaded under the key it was asked under, the latest ask only, and dropped after 30 s or when the page fails to load (`go` in `remoteScreens.ts`); the page does it as its own (`web/src/computerWork.ts`), so a start there is that computer's work and no core-to-core call carries it.
Every start ends with one answer to the window that handed it, by its request id: the page's (started, refused, failed, not added, late, no answer, agent failed) through the bridge, which the main process passes on only from the page it handed that start to and only once, or the main process's own `not_shown` for a start that never reached the page; the shell's start panel gives the operator's words back on any of them but `started`, or when none came within the sum of the three waits.
Only the page's latest ask not made yet waits, and one it replaces is answered `late`; a start the page made is followed to its own end whatever is asked after it, and a `starting` before that end says its tab exists and its agent is coming up, which ends the shell's wait for silence, as the panel follows a start of its own core's (`agentAnswer` in `web/src/startAnswer.ts`, the one rule for both).
A show asked with a request is the guest's own work that runs on the host (D-55): the guest names the pane by the address the host gives it (`guest:<guest device>:pane:<its node's pane id>`, `guestPaneAddress` in `web/src/guestWork.ts`, the row's `device_pane_id`), the page opens it on its guest pane page and answers `shown`, or `not_listed` when the host lists no such pane, and the main process carries that answer as it does a start's, answering `not_shown` for one that never reached the page and `unconfirmed` for one whose page went; the shell opens the pane in its own tile on any answer but `shown`, or when none came within 10 s (`SHOW_ANSWER_MS`), which is how it learns the host's page is of a build that answers none, and asks for an answer only from a desktop app that carries it (`remoteScreens.showAnswers`).
A start the page made can lose its end: when the page goes (closed, evicted, crashed, loaded again) or past the 16 starts the main process keeps owed, the main process answers each `unconfirmed` and logs `remote.work_unknown`, and the page answers each of its own `unconfirmed` once it loses its core; the panel gives the words back asking the operator to check that computer's screen first, and nothing is sent again on its own. A page following eight starts answers a ninth `busy` without making it.
The page in such a view (`web/src/remoteView.ts`) opens its socket through the bridge, asks no `/health`, draws no rail, counts nothing on the host (`product_analytics_connected` is the guest's), says nothing of its focus or of the screen it shows (`window_focus`, `window_screen`), and opens again at once when its tile shows, from the revision it drew.
The device chord (⌥⌘n) pressed in the view goes to the guest's rail, every other key and menu command to the view.

**Its browser pages.**
The preload adds a `browser` member beside `bridge: 1`, the five calls this window's shell makes of its own pages, which the guest's desktop app answers from the screen's top frame alone (`RemoteScreens.screenOf`): `BrowserViews` keeps the screen's pages as a source of their own, cut to the tile, held to bounds of their own and drawn by the guest, with no CDP and no off-screen load.
Before each load the guest asks the host's core where the page loads from: the guest's daemon carries `POST /peer-screen/<device>/page-route?key=` over a `screen_bulk` stream to the host's `POST /page-route`, naming its view open now, and the host answers from `browser_route_source` only while that view lives and is the guest's, refusing a device's loopback page (`remote_device_page_unavailable`).
For a `file:` page of its own node or of a device it answers a route its `BrowserRoutes` builds for that view (`resolve_for_screen`, `Owner::Screen`): the file route its own window uses for a device's file page, on the host's `127.0.0.1`, read through the node that holds the checkout, which the guest loads through the proxy below; such routes are the admitted view's own (its seat: `RemoteScreens::admitted`, one per view's lifetime and generation, never reused; 8 a seat, built with 4 slots every guest shares, apart from the host window's 12 routes and 4 builds), end with the seat (`ScreenViews`), the display's next load or the guest's `DELETE /page-route`, and load in an in-memory session apart from the screen's logins (`remoteFilePartition`), whose requests no page owns are refused.
Every request of those pages leaves through the host (`hided/src/screen_net.rs`): their session's proxy is a listener the guest's daemon keeps on its loopback for the desktop process that asked (`/peer-screen/<device>/net?key=&owner=`), whose connections need its secret and each ride one `page` stream under the grant's generation to the host's HTTP/1.1 forward proxy, which dials on the host's network with its resolver; the host registers the kind at start beside the screen kinds.
The guest's answer names the pairing (a hash of the host's grant), and the desktop names the pages' login storage by machine, key and pairing, so storage an ended pairing filled is never read by a later one, whatever its clear left.
A listener outlives drops and pauses, a pair has 16 tunnels with a quiet one giving its place, and on the relay a pair's page bytes are held to 2 GiB a UTC day: a tunnel reads only while the day is under it and counts each read before writing it, so the day passes it by at most one chunk per copy.
The page's handshake says `draws_pages` when the guest's app draws them, and the host counts such a view beside its desktop windows (`page_renderers`) for `hide browser open` and a pane's page states, while page control and the gateway still need a desktop window of the host's own (`desktop_renderers`).
The guest keeps at most three machines' pages loaded, the one hidden longest closed first, and every view closes when its window or its daemon goes.
