# 0030. Conductor missions

- Status: Accepted
- Date: 2026-10-22
- Code: `hide-core/src/missions.rs`, `hide-core/src/mission_store.rs`, `hide-core/src/runtime/missions.rs`, `web/src/MissionScreen.tsx`

## Decision

### Conductor missions

A Conductor's mission (PRD software-factory-conductor) is a core-owned record, `hide-core/src/missions.rs` for the model, `mission_store.rs` for its files and `runtime/missions.rs` for the commands, admissions and wakes; the Conductor's own judgement (what to start, retry or ask) stays in its conversation, and the record holds only what the map shows and the contracts Hide enforces: one Conductor per mission, no worker before the plan is approved, a worker only on the project's machine, and the mission's cap.
Each `hide mission` command is one typed event applied under `Mutex<Runtime>` ([delivery.md: Missions](../delivery.md#missions)).
Each mission is saved alone in `state/missions/<id>.json`, a schema-4 book of one mission, with `missions/index.json` holding the next id and one metadata line per mission (`hide_kit::layout::{missions_dir,mission_file,mission_index}`).
`mission_events::MissionEventStore` owns the one writer, saves histories before their missions, atomically replaces private files through `hide-platform::fs`, and rewrites only changed bodies and index lines.
A closed-to-open transition first marks its existing index line open; other index changes follow their bodies, including a change of Conductor.
On restart, every open line causes a body read, the body decides the restored state, and the index and shelf bounds are repaired before use; a failed repair keeps the store unavailable and its files intact.
The old 128-mission admission and load limit is gone; each mission still has at most 64 nodes and its own 7 MiB write budget below its 8 MiB read cap.
The runtime holds every open mission, every closed mission still asking someone, and the newest 128 other closed bodies and histories; older closed missions keep only their metadata in memory, with their files intact.
The shelf retains at most 2,048 older closed records; excess records lose their oldest closed row, body and owned history after the new index commits, with a diagnostic.
Startup streams index rows, retaining only the newest 128 + 2,048 resting closed rows before reading bodies; open or still-asking rows are retained.
The writer retains at most 32 unsaved shelved bodies and their histories, counted across its queue and active write until the book and histories are durable.
At 32, creation returns `mission_save_pending` with a storage-retry message and a diagnostic; existing live missions may still close and stay loaded until shelving can resume, preserving unsaved data.
The ordinary loaded body/history bound is open or still-asking work plus 128, with at most 32 pending shelves; existing live bodies retained during storage failure are not discarded.
The CLI list includes shelved metadata, filtered by project and device, with `shelved: true`; explicit `show` and `reopen` read one body off the runtime lock after preceding saves finish, with reopen also restoring its history and enforcing the existing Conductor, cancellation and open-mission checks.
The first migration can temporarily retain additional legacy closed bodies while the 32-slot writer drains; that source book retains its existing 8 MiB read cap, and later saves or a restart finish shelving.
No body cache is kept: snapshots, Missions screens, chips, saved map cards, cost attribution and PR-driven reopening consume only loaded bodies.
With no index, launch reads the old schema-4 `missions.json` (`hide_kit::layout::missions`), preserving the existing schema-1/2/3 conversions and first-copy backups; the first save writes all bodies before installing the index, so a partial failure leaves the old file authoritative on the next start.
The old file is retained and never updated by this store: a downgrade sees the missions at migration, and a later upgrade uses the existing index and ignores changes the downgraded build wrote to `missions.json`.
An unreadable index is never replaced and mission commands answer `mission_unavailable`; an unreadable body is logged and left on disk, retaining its line for explicit access.
A change of a machine's id maps each mission's machine, Project registration (`workspace_id`) and Conductor's pane and session machine in the mission folder, its index and the legacy book as it maps the ledger's (`node_migration::KEYS`, `devices`), and keeps its paths, which sit beside its machine.
It is published as its own revisioned rest section, `missions`, made on the snapshot read (`refresh_missions`): with no mission that read does nothing, and otherwise it compares the book's change count, the count of pull request answers, the ledger it last read, each open mission's Conductor presence and each mission's device answer, and makes views again only when one moved or a worker still being made stops counting against its cap; a closed mission's view is made again only when the book, its pull requests or its device's answer moved, and the worker registrations are read in one pass over the ledger for the nodes that name one.
The map is drawn from that section in two places: as a card tab on an Agent tab's desk (`DetailItem::Mission`, opened by `detail_open` and kept, saved and closed like every card, its tab kept when its mission is deleted, though a deleted mission has no events to send), and on the page's mission screen (`web/src/MissionScreen.tsx`, PRD mission-screen), a screen of the page's own like the Overview and Desk, for which the core holds no state beyond which mission's events to send (below).
A lane saved on the retired Mission tool loads with no tool column (`workspace_views::Tool`).
Settings › Mission, and the agent list in Settings › Models by purpose (`conductor_settings.candidates`), are `ui_state.conductor_settings`, saved in `core-state.json` as a plain value, so a stored value this build cannot read or refuses loads the defaults (`ui_state.conductor_settings_unknown`) and the rest of the saved UI state still loads; each edit sends only the fields it changes (`conductor_settings_set`). The cleanup switch `clean_merged` is read live by every mission, and a stored value from before it reads as on.
The agent list is advice, not admission: `hide agent catalog` and `hide mission settings` answer it as `candidates` (`Runtime::candidate_items`), `hide guide agents` (which the session note sends an agent to before its first spawn), the spawn, task and mission help and Desk's instructions send an agent to it before it starts another, and no plan or spawn is refused for being outside it.
A mission keeps no copy of it; a missions file written while one did loads with the copy left behind.
The map's direction `map_flow` (`down` or `across`, set from the map's own ↓ and → rather than the settings page) is one value for every mission's map; it is written only once it is `across`, so a build from before it still reads a file where no map was turned.
Fields a value kept by an earlier build may carry are left behind on load by `ConductorSettings::from_stored`, the one place any is still read, and the next save writes none: `checkers`, the review and verify defaults from before verification strength, so such a value reads as `normal`; `warn_review_fails` and `warn_quiet_minutes`, thresholds no edit could change and which are now fixed; and `other_vendor`, the switch for a checker of another kind of agent, which the Conductor now always prefers by `hide mission help`.
The cap is enforced where a spawn is reserved: `prepare_delivery` computes the spawn's `MissionAdmission` from the caller's open mission, and the ledger's reserve counts that mission's live workers under the same lock, so two spawns at once cannot both pass.
A take hands the mission's workers to the new Conductor in the ledger (`Mutation::AdoptMissionWorkers`), queued on the delivery worker before the take answers, so it lands before any command the new Conductor sends next; a mission spawn's reserve makes the same handover first, for a Conductor that registered only to start it.
The former Conductor's registration is the one the mission names, else the ledger's for its pane and session (`Runtime::registration_of`), since a Conductor registers at its first start, after it made the mission.
A mission that follows its Conductor's conversation to another pane (`Runtime::follow_resumed_conductors`) hands the workers over the same way (`Runtime::hand_over`): to the pane's own registration when it has one; when it has none, to a registration made for it in the same change of the store (`Mutation::AdoptMissionWorkersAsHeir`), built from the session the engine published (`coordination::executor::registration`, `native_session`), so the pane's first `hide agent end` holds; and while a wake, an archive resume, Reopen closed or a store move is carrying the former registration to that very pane (`Runtime::registration_continues`), it waits for that carry, in a memory-only map read only while it holds an entry, and hands over once the carry has landed or ended, or after an hour without it, the hour a woken sleeper gets to bind (`HANDOVER_WAIT_LIMIT_MS`, `Runtime::settle_waiting_handovers`), logging each outcome as `mission.handover` and `mission.handover_settled`, and a wait that leaves unmade, because the mission moved again, was taken or is gone, as `mission.handover_dropped`.
Pull request wakes are decided on the GitHub ingest, compared with each of a node's pull requests' last seen head, review and merge, and recorded on the mission, as are the raises, warnings and closes Hide tells the Conductor of: they are never letters but the node's one status cell (`runtime/status_cells.rs`, [delivery.md: Hide's notices are status cells](../delivery.md#hides-notices-are-status-cells)), at most one standing and one news fact per node and 32 nodes per mission, where a raise outranks the node's other standing facts and a passed CI or a merge resolves a failed CI or changes requested.
The Conductor reads the cells that changed at its turn start or in `hide inbox`, which drops the news it read; nothing is sent, so nothing is tried again.
A fix Hide records for a node's worker (at most 16 per mission) is that worker's cell, and a new one wakes the worker asleep once, as the `request` it replaced did (`agent_sleep::letters`, `cell_wakes`, `cells_woke`): a refusal that can pass is asked again, and a wake that fails for good raises the node to its Conductor as `wake_refused`.
The mission's safety net counts each node whose standing fact only its Conductor moves (`mission_health::held_of`): a raise (a waiting node's failed wait among them), counted from the raise or from the stopped worker's warning it took over; and the stopped warning itself, counted from the later of the warning and when its cell began (`PendingWake::since_unix_ms`, kept while an update replaces it); a failed CI, changes asked for and a failing review at its round limit are the working worker's and hold nothing, so a cell that began with one counts only from the stop or the raise; its card's row is the typed fact (`mission_health::HeldReason`).
A command whose change would take one mission past its 7 MiB write budget is undone and answered `mission_full`; deleting other missions does not make room in that file.
Deleting a Conductor's archived session deletes its missions in the same transition.
The book is schema 2 since node finish lines (PRD mission-map-git-criteria): `hide-core/src/mission_criteria.rs` holds the lines and their rules with no I/O, `runtime/mission_criteria.rs` the gates on a node's done and a close, the owner checks and the CI read, and `runtime/mission_outside.rs` the outside nodes ([hide-private missions.md: Finish lines](../delivery.md#missions)).
A schema 1 book is converted as it is read: each mission becomes `exempt`, so nothing made before the gate is held by it, and a node's old one-string `criteria` becomes its one line; the read copies the file it read to `missions.v1.json` beside it (`hide_kit::layout::missions_before_criteria`) before anything saves schema 2, never replaces a copy already there, and logs `missions.converted` with whether the copy was written, so a build from before can be put back on it; a copy that cannot be written leaves the book unreadable and unchanged so the next start can retry the conversion.
A schema newer than this build stays unread, as any unreadable book does.
The book is schema 3 since PRD mission-node-simple: a node is `planned`, `working`, `done` or `dropped`, holds a list of pull requests with GitHub's last answer for each, and may carry one attention, the causes already raised, Hide's last act, the wakes it sent its worker and what became of its worktree.
A planned node that a `hide mission node` patch names a worker, pull request or branch for has started (`MissionNode::started`) and becomes `working` in the same patch (`apply_patch`), so the map, the warnings and the stalls, which read a node's work from its status, never see a started node as planned; a node an earlier build left planned with its worker named stays as read and moves at its next `hide mission node`, since a book reads back exactly as it was written.
A node's `launched` (`missions::NodeLaunch`) is an optional field of schema 3, which a build from before ignores and drops on its next save: `Runtime::record_node_launches` fills it from the pane launch records (`ui_state.pane_launches`) on the agent pass that settles them (`apply_pane_launches`), right after the settle, for any node whose worker has none, a closed mission's included so a mission that closed before its worker's proof still gets it, when the pane record's conversation is the worker registration's own; it looks again only when the launch records (every write counted in `launches_edit`, a wake's or a resume's as much as a settle's), the ledger or the book moved since it last looked (`launch_proof_made`), compares in memory under the lock and saves through the book's save thread, so it adds no read, process or timer.
A schema 2 book is moved as it is read (`convert_before_simple`, after `convert_before_criteria` for a schema 1 book) and the read copies the file to `missions.v2.json` beside it (`hide_kit::layout::missions_before_simple`) before anything saves schema 3, never replacing a copy already there, as `missions.v1.json` is kept; the event files read their old node statuses the same way without being rewritten.
The book is schema 4 since PRD mission-human-gate: a node's line may be its gate (`human`, below), with where its pass came from (`via`) and the decision that asks it (`asked`); a schema 3 book reads unchanged, with no gate, and the read copies the file to `missions.v3.json` beside it (`hide_kit::layout::missions_before_gates`) before anything saves schema 4, never replacing a copy already there.
A build from before gates finds schema 4 newer than itself and leaves the book unread, every mission command answering `mission_unavailable`, so going back to it means putting `missions.v3.json` back as `missions.json`, which loses what the missions did since.
The book is schema 5 since PRD core-wait: an outside node is a waiting node, `kind: wait`, whose `wait` names its target (`waits::WaitTarget`: a pull request's merge, its CI, a branch's arrival in the destination, another mission of this core, or a node of one) and which carries a deadline (`wait_until_unix_ms`, 1 hour to 30 days, 7 days unless the plan says `for`) and, once it failed, how (`wait_outcome`).
A schema 4 book is converted as it is read (`convert_outside_nodes`): `external` reads as `wait`, as a plan's `external` still does, and a waiting node with no deadline is given 7 days from that first read (`waits::settle_wait_deadlines`, which the install runs too); a build from before finds schema 5 newer than itself and leaves the book unread, as schema 4 did to the build before it.
A mission's `destination` (`Mission::destination`, PRD mission-destination) is an optional field of schema 4: the branch its results go to, the one its checkout was on when it was made (`Runtime::checkout_destination`, read from the worktree catalog under the lock, with no Git call) or the one its plan names (`PlanInput::destination`, `mission_destination_invalid` for a name Git would not take as one branch).
A book written before it has none and reads as it did, against the project's default branch, with nothing rewritten; the schema number does not move, since a raise would leave every mission unread by the build before.
The snapshot's `MissionView.destination`, which the map and the phone draw, is the branch the core judges the mission against (`Runtime::judged_destination`): the recorded one, else the project's default branch the worktree catalog lists (`project_default_branch`, the one the outside read uses), absent only while neither can be read; the record and a command's answer, `hide mission show` among them, keep saying a mission records none.
An outside node's `NodeView.outside` says where its work goes for its branch line, read off the lock like the rest of the view: its pull request's base and state as GitHub last answered, or for an outside branch the same default branch its read judges it against; its done stays the merge or landing it waits on.
A waiting node's view adds its target, deadline, outcome, another mission's progress (`wait_progress`, its nodes done of all) and, for a pull request or its CI, the code host's own name and address for it in `outside.reference`, made as every number a mission node holds is (a `code_host::ChangeRequestRef`, `#12` on GitHub and `!12` on GitLab), so the screens never spell a pull request themselves.
This is a downgrade limit: a build from before destinations ignores the field and drops it on its next save of that mission, so the mission goes back to starting from and being judged against the default branch.
A node's `operator_merge` (`MissionNode::operator_merge`, PRD mission-destination D-10) is the same kind of field: the one-line reason a plan gives the operator a node's merge in a mission whose scope goes through it (`mission_operator_merge_invalid` on any node but a `change` by pull request, or with scope `pr`), absent from every node recorded before it and from every other node, and dropped by a build before it on its next save, so that node goes back to the Conductor's merge.
Who merges is one rule, `Mission::operator_merges` (scope `pr`, or the node's own value): the done check finishes such a node on a ready pull request, and the view's `NodeView.merge` (`mission_landing::node_merge`) says who and where the merge stands (`ahead`, `due`, `merged`, `mission_merge_by` and `mission_merge_step` in `contracts/snapshot-wire-enums.json`), `due` only for the node's own value while the mission is open and GitHub last answered its pull request ready; `publish_mission_asks` counts a due merge as the mission's own Needs You item, and the shell's `turnItems` and `missionAsks` read the same state.
What a mission does by itself and what it raises is one pure function, `hide-core/src/mission_health.rs`: it reads a mission and the facts beside it (GitHub's list when fresh, each node's worker life, the pull requests the worker's row lists as its own, the lines still open, whether the device answers) and answers acts, with no I/O.
`runtime/mission_health.rs` is its driver: it gathers those facts and applies the acts under `Mutex<Runtime>`, which costs a few comparisons and no process, read or write beyond the book's own save thread, and it runs from the coordinator's tick only when a fact it compared with the last evaluation moved, so it adds no watch loop.
What is slow stays off the lock: the project's pull request read the evaluation waits on is the ordinary GitHub read, asked again at most once in its own thirty seconds.
A done node's merged worktree is retired by `runtime/mission_cleanup.rs` while Settings › Mission's cleanup switch (`clean_merged`) is on: the evaluation chooses the worktrees under the lock from the book and GitHub's fresh answer, and a done `direct` change's from the book alone once its branch was read in the destination (`node_landing`, PRD mission-destination D-48), which an upgrade applies on its first pass to missions closed before it, and one worker thread at a time retires at most 16 off the lock through `runtime/worktree_retire.rs`, the retire Hide AI's attempts share, which removes a worktree only when it is clean and holds no agent pane or running program and keeps the branch ([hide-private missions.md: What Hide settles in a mission by itself](../delivery.md#missions)); off, the mission deletes no file.
A mission that closes as done or `merge_wait`, or turns done from waiting, owes its operator's checkout one pull (`runtime/mission_pull.rs`, PRD mission-destination D-26 to D-31, D-43, D-47): each close path (`close_mission_with`, `close_if_landed`, the GitHub read's close) calls `owe_folder_pull`, a cancel never does, and the choice is made under the lock from the book and the worktree catalog alone (no change of the mission landed in the destination, or a project on a connected device, is a skip with no call).
The pull runs on one issue worker at a time, off the lock and after the close has answered, on the project's own node: `Call::FetchRemote` once, whatever the project's `auto_fetch`, then `Call::CheckoutGit` on the checkout the mission was made in, then `Call::BranchCatchUp` from the `HEAD` just read, only when the branch that read finds out is the destination (never the catalog's branch, which may be older than a switch), it tracks `origin/<destination>`, is behind and has no commit of its own; the catch-up is told that branch, and the host refuses a `HEAD` that moved, has another branch out or holds a change the fast-forward would overwrite, so the only write is a fast-forward of the destination's own branch.
It is the one write any part of Hide makes to the operator's own checkout.
What came of it is one diagnostic, `mission.folder_pull` (mission, outcome, reason, commits), and for an outcome the operator acts on one line at the end of the mission's `report`, kept as `Mission::folder_line` so a later close replaces it, except that a later close finding the checkout current keeps a line that says the checkout was brought to or found at the destination (a Conductor's own close after Hide's, for one); `folder_line` is an optional field of schema 4, which a build from before ignores and drops on its next save, leaving the line in the report and a later close adding a second.
A branch with no upstream, or one that tracks another branch, is skipped rather than compared with `origin/<destination>` directly, since the catch-up follows the configured upstream only and setting one would be a write to the operator's Git configuration.
A raise is its Conductor's to settle unless its reason is one the operator settles first (`AttentionReason::operator_first`: a gate with no Conductor, a Conductor's failure); what only a Conductor moves and it has not resolved, a raise (a waiting node's failed wait among them) or a stopped worker's warning, is one derived safety net per mission (`mission_health::safety_net`, from the book, whether a Conductor is present, since when it has been, since when it rests, and the clock), drawn at once with no Conductor and with one only while it rests, once the latest of the oldest fact, its arrival and its rest stood 20 minutes, never a stored state.
A Conductor rests (`Runtime::conductor_rests`) when its row's turn ended and it asks the operator nothing and waits on no task of its own; unlike a worker's stop, its descendants at work (`AgentWait::Children`) do not hold it, since they are the mission's workers, not the Conductor's move on what it owes.
The time a Conductor came back and the time it was first seen resting (`conductor_seen`, `conductor_rest_seen`, one entry per mission, followed by the health pass each tick, the rest's coming and going made views again through `rows_and_holds_digest`) are kept in memory only, so a daemon restart counts them from the restart.
A raise to the operator is laid on a row by the same path as a plan review and a mission decision; when no row shown carries it, whether its owner is gone, working or registered with no row, the mission's view says so (`on_row`, read from the rows laid, and the notice claim lays them first) and the shell draws the mission itself in Needs You, and it is told once by a notice; the operator's choice is one typed event, `mission_attention`, applied under the lock.
A `check` line is judged against the commit the node's worker's checkout is at, read from the catalog Hide already holds for its pane, and a `ci` line against the pull request's head in the GitHub answer, so the gate starts no git or `gh` process under the lock.
The outside nodes are read off the lock on an issue worker, one read per project out at a time, after the GitHub ingest, the background fetch's answer and a change in the local worktree catalog; an outside pull request is a `gh pr view <n> --json state` allowlisted by `hide-node-link/src/gh.rs`, and an outside branch a few fixed git commands (`RefCommit`, `CountCommits`) on the project's node, against the default branch resolved to one commit, locally and as last fetched, once per read and after every branch head it compares.
A done `direct` change's branch is read the same way against its mission's destination, the default branch for a mission that records none: each ask carries its base as owned data copied under the lock (`Watch::Landing::base`), the heads GitHub merged into each base are copied with it (`Bases`), and the read resolves each distinct base once, two git calls a base however many missions and nodes name it, so a project whose missions all go to the default branch reads what it read before.
An answer asked against a destination the plan has since replaced is dropped, and a destination that resolves neither locally nor as last fetched answers unread (`Found::BaseUnread`), which keeps Hide from closing that mission by itself (`Outside::lost`, memory only) until a read finds it or the plan names another; no letter is sent for it.
Two limits stand: a force-push of the destination is not noticed, since a `direct` change read in it stays in while the local branch or its last fetched copy still holds the commit and a pull request node follows GitHub's merged state alone; and a destination deleted only on the remote reads as present while the local branch exists.
Waits (PRD core-wait) are one model for a mission's waiting node and for an agent's own `hide wait`: `hide-core/src/waits.rs` holds the targets, outcomes, deadlines and the agent's `WaitStore`, and `runtime/waits.rs` judges them, with no I/O under the lock.
An agent's waits live in `ui_state.waits` and are saved with the rest of the UI state (`core-state.json`), never on the wire: at most 8 open per agent and 256 per core (`wait_agent_full`, `wait_full`), a repeat of the same target by the same agent answering the open one (`existing: true`), and an ended wait dropped at once once its notice was seen, so it counts against nothing.
A wait is refused when it is made, never left waiting silently: a mission of another machine or one this core does not hold (`wait_mission_unknown`), the agent's own mission or a cycle of waiting nodes (`wait_self`), a target the project's code host does not declare (`wait_unsupported`), a project with no code host (`wait_project_unknown`); a plan's waiting nodes take the same check (`mission_wait_unknown`, `mission_wait_self`, `mission_wait_unsupported`).
The judgment is a re-read, never a list of events: the coordinator's 250 ms tick calls `Runtime::tick_waits` for the core's own target, which runs at most every 10 s and passes deadlines, ends the waits of agents that ended (`wait.agent_ended`, B20), and judges mission and node targets against the book, which every save of the book judges again too (`judge_book_waits`); a code host target is judged from the pull request list the project's read already holds, read alone by its number (`Watch::ByNumber`) only when the list does not carry it, and a host whose rate limit stands below its floor (`WatchAnswer.resting`, `missions.hosts_resting`) is asked again at the next read.
A deadline that passed fails a pull request, CI or branch wait only once a read it asks for, every ask read with no list (`follow_outside_read`), answered that wait with the target still open, or half an hour after the deadline with no such read (`Outside::deadline_read`, a device away), counted from the end of the host's rest at its rate floor when it rests then, which holds the read back, so a target met in the last look's gap is met and no wait outlives its deadline for good; a read that came back failed counts as that read; a stored list no read replaced within 10 minutes answers no look, so another machine's list kept from before the window closed does not hide a merge; a CI wait on a pull request the list's 200 newest no longer hold is read by its number as the list would hold it (`ByNumber::as_listed`, its rollup and the runs on its head), and a CI wait whose checks cannot be read, on either path, is unread: its failure stands and it carries the unread mark, never reading as open.
With no window attached, the core still reads the code host for the projects of open waits only (`github_wait_request`, `ingest_github_part`) on the code host read's own clock, keeping the other projects' answers as they were.
A waiting node met is done and wakes its Conductor as a merge does; failed or past its deadline it stays working and raises its reason to its Conductor (`ci_failed`, `mission_cancelled`, `node_dropped`, `wait_expired`, beside `pr_closed`), and a plan that gives the node a new target or a new `for` clears the failure and starts its deadline again.
An agent's wait that ends is told to it as one Hide notice (`wait:<id>`, [delivery.md: Hide's notices are status cells](../delivery.md#hides-notices-are-status-cells)) that wakes it asleep; the operator's Needs You is never told.
A mission's events (PRD mission-plan-visibility D-15, D-22) are kept apart from the book, so its 7 MiB budget never counts them: `hide-core/src/mission_events.rs` holds the model and `MissionEventStore`, one save thread that writes each mission's file under `missions/events/` (`hide_kit::layout::mission_histories`) off the lock, collapsing a burst to one write per mission, deletes a gone mission's file, and is joined when the store drops; `runtime/mission_events.rs` decides which command makes which event under the lock.
The first migration reads the legacy `mission-events/` once and writes its histories into the folder before installing the index.
A failed history copy holds the index back; retry starts from the unchanged legacy histories.
Once the index exists, the old event directory is neither read nor swept, so a downgraded build can sweep or reuse an id without changing the folder book's history.
The lock hands the store only a change's new events: the thread keeps its own copy of each log, starting from the logs read at launch, and extends, encodes and writes it off the lock, so an event never copies or encodes a mission's history under `Mutex<Runtime>`.
The core holds each history as a shared list of shared events (`History`), so publishing the open mission's copies a pointer, and a change made while a published list is still held copies pointers, never the events.
A mission keeps at most 500, the oldest dropped and counted; the files are read back with the book at launch, and a file that cannot be read is logged and replaced on its mission's next event.
The events are published as their own rest section, `mission_events`, for one mission only: the one the mission screen's detail shows, which the page names with one typed event, `mission_shown` (`missions.shown`, held unsaved, only for a mission the book holds, and cleared when that mission is deleted; the page sends it again on every reconnect, and between windows the last word wins, PRD mission-screen D-16), else the one whose card is in front of the active area of the front Agent tab's drawn desk, which the core reads from its own desk (`refresh_mission_events`), made again only when that mission or its events changed, so a mission's history never rides every frame; the section shares the core's list and is encoded with the rest of the frame off the lock.
A node holds two more optional fields of schema 3, which a build from before ignores and drops on its next save: `steps`, the few lines its Conductor wrote with the plan (`NodeInput.steps`, at most 8 of at most 80 characters, refused as `mission_steps_invalid` with the node's key and a next action, never cut; a replan that leaves them out keeps them, an empty list clears them), and `brief`, the first prompt its worker was spawned on.
The node keeps `brief` because the delivery ledger lets a finished letter go a day after it ended (`delivery::RETENTION_MS`) and a mission lasts days: `mission node --agent-id` copies it from the spawn record whose child is the bound worker (`runtime/mission_brief.rs`, `worker_brief`), and a worker whose spawn kept none leaves the last one, as does a worker bound only after it ended, whose spawn has let its brief go by then (`delivery.md`, launched brief); a mission started before this build has none for its running nodes.
The map's `NodeView` carries `steps` and only the brief's size (`brief_bytes`), so a mission of sixty-four nodes never sends sixty-four briefs of up to 16 KiB; the text rides its own rest section, `mission_brief`, for the one node whose folded box the operator opened (`mission_brief_read`, one typed event that copies that node's text into the section, which the next read replaces), and the screen draws nothing for a node with no brief.
How a node's work goes is one source on the screen: the worker's own plan (`NodeView.plan`) once it exists, else `steps`; a worker step whose title is not one of `steps` is marked changed, and nothing writes the Conductor's steps into the worker's plan (`web/src/missions.ts`, `nodeSteps`).
The operator's answer to a decision is kept on the mission (`Answer`, keyed by the question it answers) and typed into the Conductor's conversation by the doorbell's thread (`delivery::doorbell`), which judges the Conductor's pane as it judges a letter's recipient, releases a draft by the same composer read and reads the composer again right before typing (`clear_to_type`, shared with the bell), and types off the lock; what it waits for (`AnswerHold`) and whether the operator pressed `지금 보내기` for it are memory only, so a restart shows it as sending until the next pass.
Once the prompt operation (`prompt_agent`) is asked, a failed, timed-out or unreadable reply may follow a typed answer, so the book holds the answer as `unconfirmed` before the prompt is asked (shown as sending until the engine replies, memory only) and no pass, and no restart after a stop in between, types it again; only the operator's `resend` from the banner makes it due once more (engineering principle 11).
What a decision shows the operator to look at is linked from facts the core already records, never guessed from a name or a time (`runtime/mission_views.rs`, operator decision 2026-11-09).
`stamp_control_opener`, the one path an agent's `hide file|diff|browser open` takes, hands the View to `link_mission_view`: a View the mission's Conductor opened is kept on the mission (`conductor_views`), and one opened by a working node's worker or an agent under it, found by walking the ledger's parents at most 32 deep, is kept on the node with its attempt and what the View is (`views`, with `ViewLink.kept` as a question's link keeps it), each list capped at 16 with the oldest dropped (`missions::VIEW_LINK_LIMIT`) and saved with the book, so a restart loses none and no agent runtime reports its turns.
The list is made when `decide` runs and kept on the question (`Question.views`): the Views `decide --show` names in the Conductor's checkout, in their order (the CLI opens a path as a View first and sends its id; an id no View there has is refused `mission_show_unknown`), then the Conductor's kept Views and the stopped node's Views of its current attempt that are still open, newest first, at most 16 in all; it empties the mission's list, so the next question starts from what the Conductor opens after this one, and the same question asked again with `--show` puts the named ones first.
The mission's list is the mission's and not one agent's, so a Conductor that takes the mission over asks with what its predecessor opened; nothing opened after `decide` joins the question.
Each of the question's links keeps what its View was when it was linked (`ViewLink.kept`: kind, name as its tab said it, address, and a diff's Changes group), read with `serde(default)` so a book written before reads with nothing kept and no schema raise; a name is cut at 256 characters, an address past 4096 is not kept, and an outside file, which only a window's grant names, keeps nothing (PRD mission-human-gate D-20).
A done node lists its current attempt's links the same way on its view (`NodeView.views`, its `결과`, with-hide/hide#2637): one row builder (`view_rows`) makes a decision's rows and a node's from their links, with `by` always the worker on a node's, and a node not done lists none.
A node also keeps the first line of its worker's last `report` letter to the mission's Conductor (`MissionNode.reported`, at most 600 bytes, cut at a character boundary, read with `serde(default)` so an older book reads with none): `note_reports`, which already reads each new ledger letter for a child's report to its parent, records it on every node that worker works and the next report replaces it; the panel shows it as the conclusion while the Conductor's `line` is none.
`decision_views` lists every link of the question on the mission's view (`MissionView.decision_views`, with who linked it, `mission_decision_view_by`, and the opener's pane for the phone) until the question is answered or cleared: an open one from its View, the one the link names or, after it closed and opened again, the last-focused one showing the same document or page; a closed one from what the link kept, `closed`, under the link's own id; a closed link from a book that kept nothing is not listed.
`refresh_missions` compares, per mission, the View layouts' and the presses' change count as one more input only while its open decision or a done node links any (`mission_views_generation`), so a mission with none pays nothing for a View's change, and a closed mission whose done node links one is made again with its rows rather than kept; the Conductor row's decision ask carries the count of the open ones (`views`), so a View closing changes the eye and nothing else.
Each link keeps the agent the View was open for when the decision linked it (`KeptView.opener`, by machine, engine terminal and session, never a pane id), and every row names its link by `view`, a token that tells two checkouts' Views apart without saying either path.
Pressing a row is one event, `mission_view_reopen` (the mission, the question's `key` or, for a done node's row, the `node`, exactly one of them, else it opens nothing and logs `mission_view_owner_invalid`, the row's `view` and, from the phone, a request id; a node that is gone is refused `mission_node_unknown`): an open View takes its area, and a closed one opens again from what the link kept, as the View of that agent if it had one, so it is in that agent's Files strip and phone 볼 것 again and is not raised as new.

A question that changed, a link that kept nothing, a checkout no longer listed, a reveal refused as it was asked or a file that could not be read opens nothing and goes to the diagnostic log (`mission.view_reopen_refused`).
A press with a request id keeps its outcome on the row (`LinkedView.reopens`, every kept press of that row, so two phones pressing it at once each find their own): refused, or still waiting until the row is open again; one still waiting after a device's answer and landing stages (20 s) ends refused, so no press waits for a View that never comes.

Linking marks no View seen or unseen and raises nothing: the row's read record, its descendant signals and the notices key on the row's state and the question, never on the count, so a View opened or closed while the question stands is no news.
With none linked the operator may ask for material once per question (`mission_material`, from the card or the phone's `ask_mission_material`): the core marks the question `material_asked` and records one `material_asked` wake keyed by the question, so a second press, from any surface, sends nothing, and the letter asks the Conductor for one page that opens with what changed, the 2-3 things to check and what good looks like, then to ask again with `--show`; the answer is never held back by it.
A node's gate (PRD mission-human-gate) is one more finish line, `human`, so the refusal of a node's done while a line is unmet holds it and every node behind it, and a mission or node without one is read, raised and settled as before.
The plan names it as the node's `gate`, one line of at most 80 characters (`mission_criteria::GATE_CHARS`), checked by `missions::check_gate` and kept by `mission_criteria::set_gate`; a replan that leaves it out keeps it and `null` takes it away, on a node not yet done.
`runtime/mission_gates.rs` owns it at run time, under the lock and from what the core holds: after each health evaluation `raise_gates` asks an end gate once its node works and either the Conductor showed it (`hide mission gate <node> --show`, `show_gate`, which keeps the Views it names on the gate's line, `Criterion::shown`, for its question alone, until the operator answers or the node goes back to work from a finish, refusing a gate that passed with `mission_gate_passed` and taking the Views the CLI opened for the showing out of the Conductor's own on every answer (a known gap: the CLI opens a path through the ordinary open, which links it as the Conductor's View, so a health pass that asks another gate between that open and the showing can still take it); the line's Views reach the screen only through the question, so the map's criteria carry none) or the lines its worker answers for are met (`own_lines_met`: the kinds `CriterionKind::worker_answers` names, its own, the check command and the defects), without waiting for its CI, review or verification (operator decision 2026-11-14: a look after the review sent the review round again), through the mission's own decision (`Question` with the node, the two fixed choices and the Views a `decide` would link), once the decision is free, and withdraws a question whose gate is no longer reached; with no Conductor present, a gate that waits is also the mission's raise to the operator (`AttentionReason::HumanGate`, with no choice of its own, since the decision card answers it), which a Conductor coming back takes off.
Its state on the map (`NodeView.gate`: ahead, open, passed, the waiting time and when it has waited 24 hours) is derived from the line and the decision, never stored apart, and the shell compares the long wait with its own clock, so no timer of the core's runs for it.
Every answer reaches `settle_gate`, the one entry, whether from the decision card, the phone (`MissionAnswerPayload.phone`) or the Conductor's pane (`hide mission gate --said`, `relay_gate`, the Conductor alone and only with the operator's words): a pass records the line as the operator's with where it came from and the words; a fix keeps the gate open, spends the showing, adds the words as a defect line with the same `via`, sets the node working, and wakes the Conductor and the node's worker with them (`WakeEvent::GatePassed`, `GateFix`).
The Conductor's pane pass is also taken before an end gate asks, while its node works in a running mission and the line is open: the operator's OK on screens shown while the node still works, after which the gate never asks and the node's other lines still hold it; a fix before the gate asks stays refused (`mission_gate_not_open`), since the Conductor sends those words to the worker as a letter.
The Conductor's `record`, `skip` and `decide --clear` on it are refused (`mission_gate_operator_only`); the operator's own `끝으로` on a raise, which goes past every line left open as their decision, passes the gate through `settle_gate` too (`GateAnswer::Past`, from the card with the words `운영자 판단`, `your decision` in English, in the operator's language), never around it.
A replan that changes a gate's words or takes it away takes, in the same change (`missions::apply_plan`), the question that gate asked and its raise, so the gate behind it, or the changed one, asks next; a question of the Conductor's own stays.
A node's `depends_on` entry (`missions::Dependency`, kept as the plan wrote it, so a plan of plain keys reads and writes unchanged) names another node, met once it is done, or one finish line of it, `<node>:<line>`, met once that line is met as its owner shows it (`Criterion::met` against that node's heads, read by `Runtime::lines_now`; a check passed on a commit the folder left is open again), a dropped node meeting nothing; `Mission::dependency_met` is the one rule `waiting_on`, `mission_health::could_start` and the line follower read, and a plan naming a line the node lacks, lines of two nodes, or a merge order that puts the stacked node first is refused (`apply_plan`).
A pull-request change that waits on a line of a pull-request change stacks on it until that node's work is in main (`Mission::stacks_on`, `mission_landing::stacked_below`): its view carries the stack (`NodeView.stack`, the node below, its branch and pull request), and once its own lines are met it waits on the merge below (`WaitingOn::Below`) before its own.
`runtime::mission_health::follow_lines`, run first in each health evaluation of a running mission (which a move of those lines starts, `HealthMadeFrom::lines`), keeps the lines each node last saw met (`MissionNode::lines_met`, saved with the wakes it records), records one `line_met` wake when a line met lets a node start (not a held node or one behind a start gate, which those tell) and one `line_reopened` wake per line when a remembered line opens again after nodes on it started (a check line whose folder Hide cannot read keeps what was seen), stopping none of them, and sets a stacked node's `base_pr` to the pull request below once both exist.
A gate may instead ask before its node starts (PRD node-presets D-06, `when: start` on the line, `missions::GateWhen`; a line written before it asks at the end): `gate_reached` takes it as reached once the node could start (`mission_health::could_start`: not started, every dependency met by `Mission::dependency_met`), and it asks, waits and settles through the same decision, raise and entry, the Conductor's pane pass included once it is open (never before, unlike an end gate's); while it is not passed `MissionNode::start_refusal` refuses the node's worker as `mission_gate_before_start`, where `hide mission node` binds or starts it (`apply_patch`), at a spawn's admission and again where its place is reserved (`delivery::worker`), as a hold is refused; a fix leaves the node planned and its words a defect line for the worker it gets, and the gate asks again.
