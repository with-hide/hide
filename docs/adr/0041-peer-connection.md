# 0041. The peer connection

- Status: Accepted
- Date: 2026-11-19
- Code: `hide-peer-protocol/`, `hide-peer/`, `hide-peer-iroh/`, `hided/src/peer_host.rs`, `hided/src/peer_dial.rs`, `hided/src/peer_core.rs`, `hided/src/pairing.rs`, `contracts/peer-link.json`

## Decision

### The peer connection

Two machines that each run Hide keep one connection between them, and three crates hold it.
The core role opens this machine's end of it in `hided/src/peer_host.rs`, and only when it is needed: at the daemon's start when a grant, or a host this machine is still a guest of, is saved (`peer_host::endpoint_wanted`), and otherwise at the moment the operator shares this machine, adds one or acts on a machine the records name (`PeerHost::open`).
A machine whose every host dropped the pairing has nothing to dial and opens none at its start: its rows are read from the saved records (`PeerHost::recorded`, `Pairing::rested`).
A machine that is paired with nothing binds no socket, attaches to no relay and asks macOS nothing about the local network; once open the endpoint stays open until the daemon ends, which closes it.
Every stream a peer opens is handed to the one handler its kind's owner registered at the daemon's start (`PeerHost::handle`), each in a task of its own, and a stream of a kind no one handles is dropped, which closes it for the peer.
A connection's count of each kind is kept by the kind's place in `StreamKind::ALL`, never by its tag, since a tag is the wire's and need not follow the places (`core` is 11 and `screen_bulk` 12).
The `page` kind (tag 9, priority -100, 16 per connection, under the grant) carries the browser pages a guest draws of its host's screen, one connection each, to the host's forward proxy ([Another machine's screen](0042-another-machines-screen.md#another-machines-screen)); a build with no handler for it closes the stream unanswered, which the guest reads as a host to update.
`HIDE_PEER_DIRECT=<ip>:<port>` binds that one address with no relay and no local network search, for development and tests (`hided/src/env.rs`).
`HIDE_PEER_RELAY=<url>` keeps the product's endpoint but attaches it to that relay instead of the device relay, with no local network search, so a run can stop and start a relay of its own (the release A fault run, `docs/TESTING.md`); it takes https, or http on loopback, and is refused beside `HIDE_PEER_DIRECT`.
`HIDE_PEER_RELAY_ONLY=1` beside it keeps no IP transport on the endpoint, so every connection goes through that relay and a relay that stops stops everything between them, as between two machines with no direct way to each other.
A core moved before 1.2.0 that a node still dials is kept on (`always_on::paired`).
The note a packaged `hide connect` leaves of its app (`hide_kit::app`) is written by every build: a core is left to its app by what the app wrote before 1.2.12.
The security and ownership specification this connection is built to (the threat model, pairing, who owns a guest's work, the relay's limits) is with-hide/hide-private's `docs/device-connection-security.md`; this section is the runtime contract the code keeps.

| Crate | What it holds | What it may link |
|---|---|---|
| `hide-peer-protocol` | What the two say: the hello and its versions, the stream kinds and priorities, the pairing, revoke and management messages, what the two cores say to each other, the events one core hands another, a guest node's launch contract with its folder and socket names, the tap | `hex`, `serde`, `serde_json`, `sha2`, and no crate of Hide's |
| `hide-peer` | The connection above any transport: the machine key, the grant and known-host stores, each direction's gate, admission and the dial rule with its successors, the climb between paths, the event inbox, a loopback transport, the link multiplexer and the pipe transport that runs on it, and the ladder that chooses between the pipe's SSH carrier and the main transport | Hide's crates and tokio; no network transport |
| `hide-peer-iroh` | The transport: an iroh endpoint behind `hide_peer`'s seam, with no product state | iroh and noq, which no other member may name |

`contracts/peer-link.json` is written from `hide-peer-protocol`'s types (`contract::shape`), and a test fails when the file and the code differ ([contracts/README.md](../../contracts/README.md)).
`hide_kit::layout` names every folder below: `peers/` under the state folder for this machine's key, stores and inboxes, and `g/<first 16 hex characters of a guest's key>/` for a guest, short because a guest node's socket path has to fit a Unix socket address (a test holds the longest one inside 103 bytes for a 16-byte account name).

**The seam.**
`PeerTransport` (this machine's key, its address candidates, `dial`, `accept`, `close`) and `PeerConn` (the peer's key, which side dialed, the path's kind, `open` at a priority, `accept`, `close` with a code, how it ended) are all `hide-peer` asks of a transport, as generic parameters and never a trait object.
`accept` never waits on one peer's proof of its key: each proof runs in a task of its own, so a peer that starts one and never finishes it holds up no other connection.
`hide_peer::loopback` is the second transport: in-process streams between the `Peers` of one test, each end proving its key by signing the other's challenge, so pairing, grants and delivery are tested with no socket.
`hide_peer::pipe` is the third, for a WSL distribution and its PC (D-27, D-63) and for a machine reached over SSH: a connection is one byte stream, `wsl.exe`'s or the system `ssh`'s, with the link multiplexer's streams on it and the same proof of each key as the loopback's (`hide_peer::proof`), since a pipe authenticates nobody; the proof's dialer half answers a typed `Proof` (`Proved`, `OtherKey` with the other key once its signature verified under it, `NotProved`), which a dialed carrier's `told` hears once before the dial returns, and `PipeTransport::check` runs that proof on a carrier the caller holds, admits nothing and tells no one.
A pipe connection says the path its carrier came by: `PathKind::Ssh` for an alias's, `PathKind::Local` for a distribution's.
Neither admits a peer for free: at most `limits::MAX_ADMITTING` (16) proofs run at once and each has `limits::HELLO_WITHIN` (10 s), iroh's own admission caps, and a carrier that arrives past the count is ended unread.
`pipe::Beside` joins the pipe to the main transport as one `PeerTransport`: an address whose candidates name a distribution (`Candidate::Wsl`) is dialed through the pipe, an address that names an SSH alias (`Candidate::Ssh`) through the ladder ([A machine reached over SSH](#the-peer-connection)), and every other through the main one; both are accepted from, and `Peers` sees one transport, so the dial rule, the generation gates and which of two connections stays are the ones every pair has.
`PathKind::rank` is the one order of paths: a direct one (Tailscale's and one inside a machine included) ranks 3, SSH 2, the relay 1; `Beside` chooses between its carriers by it before anything is admitted, below the seam, and `Peers` still decides which of two admitted connections stays.
`PeerConn::chosen_path` is the path once the transport chose one, so a choice never takes iroh's "no selection reads direct" default for a direct path; `PeerTransport::route` and `route_fell` say where the other carrier's route stands and that a connection over it fell, and `dial_route` dials over it alone, each a no-op on a transport with no other carrier.
`scripts/check-iroh-stays-behind-the-seam.py` fails when a member other than `hide-peer-iroh` names an iroh or noq crate, when `hide-core`, `hide-node`, `hide-host`, `hide-holder` or `hide-agent-hooks` reaches `hide-peer-iroh` through any chain of members, when `workspace-hack` lists a crate only the transport reaches, or when iroh or noq is asked for by anything but an exact version without default features.

**One connection, two directions.**
A pair of machines keeps one connection whichever side dialed, and each direction has its own grant: A may be B's guest, B may be A's, or both.
`peers::decide` is the whole dial rule: a connection whose name is among those ended for another (`superseded`) is refused as `replaced`; with no connection held the new one is installed; a successor of the held one, which names it as the one it replaces or among those its dialer knew were, replaces it whichever side dialed it; a second connection dialed by the same side replaces the first, which closes as `replaced`; and when both sides dialed at once the one the smaller key dialed stays and the other closes as `duplicate`.
Between two builds that name `ssh_path` each connection's dialer names it (`Hello::dial`, random), a move or a keeper's redial names the connection it replaces (`Hello::replaces`), and the dialer's hello carries the names its end knows were ended for another lately (`Hello::supersedes`, at most 8); each end keeps those names, its own refusals and replacements and what the connections it installed say, for 20 s and at most 8 per machine, under the table's lock with the install, so a predecessor that arrives late is refused on either end whatever order the two ends' first exchanges finish in; between builds that name none every name is 0 and the rule is the one both share.
A dial waits its key's turn and for a closing connection to finish, never starts while a live connection exists, and ends early when the peer's own dial is admitted first.
`Peers::keep` dials again after a drop, 1 s later and doubling to 60 s; `network_changed` starts that wait over, and so does a connection that stayed 60 s, while one that was admitted and closed sooner is dialed as rarely as one that never answered.
A transport that cannot accept, as an endpoint that ended and cannot bind its port again, is asked again on the same wait, with one diagnostic when it starts failing and one when it recovers.

**The first exchange.**
Each side sends a hello first: the magic `HIDEPEER`, a length, and at most 16 KiB of JSON carrying the framing number, the oldest and newest link version it speaks, its capabilities, its build and its device id.
The two run the newest link version both speak and the capabilities both name; when they share none, the connection closes as `update_needed`, and `PeerEvent::UpdateNeeded` says which side is behind when the peer holds or is given a grant, while a stranger's leaves a diagnostic only.
A hello also says what the sender calls itself (`name`, `hide_platform::host::computer_name`: a Mac's computer name from System Settings, its host name without `.local` only when it has none, and the host name on Windows and Linux), read once when the daemon starts, so a name changed in System Settings reaches the other machine from the daemon's next start, and admission keeps it as the name of the grant that machine holds here and of the host record kept of it (`Grants::take_name`, `Known::take_name`), saved before the connection is announced, so a machine renamed since its pairing shows its new name from its next connection without pairing again.
What a machine calls itself replaces only that name, never the one this machine's operator chose (`chosen_name`, which every screen shows first through `shown_name`): a host this machine switched through a login keeps the name its device had here as that chosen name (B36), since a WSL distribution calls itself by its PC's host name; a host record written before `peers/known.json` version 2 kept a switched host's name by never replacing it, and reading such a record moves that name to `chosen_name` once; a build from before the field says none and keeps the name it paired under.
A hello can also ask the other side to update (`update`): two builds that share no number have no connection that lives to carry `HelloFrame::Update`, so the ask rides the one exchange they do share.
A machine sets it for a host it is an active guest of, once its operator asked (`Peers::ask_update`), in the first exchange of its next connection to that host, and the side that reads it while it is the one behind emits `PeerEvent::UpdateRequested` only when the sender holds an active grant there; any other sender's ask leaves `update.refused` in the diagnostic log, and a build from before the field ignores it.
`hided`'s pairing keeps who asked whom in memory, says the ask again on each dial until the two connect, and puts it on the machine's row (`PeerUpdate::{HereAsked, ThereAsked}`); the update itself is the desktop app's, which follows the row (`web/src/PeerUpdateNotice.tsx`): it looks for the official release and restarts into it, and the app's `hide connect` then replaces the core.
The core starts no app, so a machine whose app is closed updates when the app is next opened.
A machine runs at most 16 first exchanges at once, each bounded by 10 s, and a connection that arrives past that closes as `busy`.
A build that is not a release also sends the contract file's hash, and two such builds with different hashes refuse each other, so a contract change is never tested against a stale peer by accident.
The hello stream stays open for the connection's life and carries each side's grant state and generation as they change, and the request to update and its answer.

**Streams.**
The side that opens a stream writes nine bytes, the stream's kind and the generation it believes it holds, and the other side answers nine bytes, a status (`accepted`, `no_grant`, `stale`, `limit`, `unknown_kind`) and its current generation.
Hello, pairing and revoke need no grant; every other kind is refused unless the direction it serves has an active grant at that generation.
An accepted stream is bound to the generation it was accepted under (`gate::Guarded`): its next read or write after the generation moves fails, so a pause or a removal ends every stream it allowed without a list of them.
A connection carries at most 72 streams, and each kind has its own cap inside that (`limits::max_streams_of`), so a flood of one kind never takes another's place.
The transport sends by priority: keys typed into a pane first (100), then hello, pairing, revoke, management and the two cores' stream (75), the node link (50), terminal output and the remote screen's socket (0), and files, pages and the remote screen's page, assets and file bytes last (-100).

**Grants are saved first.**
The host keeps who may be its guest in `peers/grants.json` and the guest keeps the hosts it paired with in `peers/known.json`, private files of at most 64 KiB replaced atomically.
A change is saved under the store's lock, then the direction's gate moves (one atomic generation, where 0 is closed), then the peer is told on the hello stream: a crash between two of those steps leaves the saved state, which is what the next start enforces.
Pairing settles in two steps: the host saves a `pending` grant that opens nothing and answers `granted`, and the guest saves its side and sends `confirm`, which makes the grant `active`.
A confirm answers the same however often it is sent and never revives a paused or removed grant; a pause of a paused grant or a resume of an active one saves nothing and moves no generation, so a repeat ends no stream.
A pending grant its guest never confirms counts for nothing once 10 minutes have passed, on every read and not only when a later write drops it.
A removed grant leaves a tombstone for 30 days, 256 at most with the oldest dropped first, so its guest's next connection is told `revoked` rather than `none`; a host grants 32 machines at most and a guest remembers 64 hosts.
When no grant is left in either direction the connection closes as `no_grant`; a connection with none may stay 10 minutes, a pending grant keeps it only while that grant still waits, and the limit is read again each time a grant or a known host changes.
A machine holds 16 such connections at most and closes the next as `busy`; what it keeps for a connection, the inbound gate included, lives in that connection and goes with it.

**Pairing.**
`hide_peer::pairing::Pairings` is how two machines become a pair and stop being one, above any transport: the one link a host shares, the machines that wait for this machine's operator, the pairing this machine is joining, the request a guest sends to be let in the other way, and the confirm and the removal a guest keeps sending until its host answered.
A link is `hide://pair#...` with the host's connection id, its device id, the addresses it can be dialed at and a one-time secret; it opens a pairing for 9 minutes and for one machine, and a second share replaces the first.
Both screens show the same four words, read from a hash of the two keys and of one random value of each side in the word list the host named (`hide_peer::words`).
Neither side picks its value knowing the other's: the guest's first message carries only a commitment to its value, the host answers with its own, and the guest then opens the commitment before the host's operator is asked, so a machine between the two cannot search for a value that makes the screens agree; the link's secret says only that the guest holds the link.
Each operator has 2 minutes: the guest says the words match, the host allows, and anything else, a closed window included, leaves no grant that opens anything.
A machine that is already a guest asks to be let in the other way over the connection the two have, which needs no words since both keys are proved, and the answer there is the same allow window; at most 8 machines wait for an operator at once, and one machine's confirms, removals and requests are each held to 6 a minute.
The two directions are two records: pausing or removing one leaves the other and the connection as they were, and a guest that removes a host it cannot reach keeps the removal and sends it until the host answers.

`hided/src/pairing.rs` is the daemon's side: it starts the service with the endpoint, answers every ask about pairing, and after every change it reads the paired machines again in `Pairing::paired_changed`, the one place that runs after a pairing is saved, and hands them to the core as the daemon-only `peer_machines` event.
The core keeps them as a list of facts (`hide-core/src/peer_machines.rs`) and publishes them as `navigator.peers`: who opens whom, whether the two are connected and by which path, why not when the relay is unreachable or stopped for the month, and which side must update.
A machine this one opens becomes a device of the core once its host confirmed the pairing: `Runtime::reconcile_peer_devices` (`hide-core/src/runtime/peer_devices.rs`) registers it under its own device id with `LinkOrigin::Peer { key }` when `opens` turns `active`, keeps it through a pause, and removes it with what Hide recorded for it when the pairing ends; an id another registration already holds is left to that registration, with a `peer_device.id_taken` diagnostic.
Its connection is dialed by `hided/src/peer_dial.rs`, which has that machine run this core's node only under the active grant that machine tells it: a connection hears its grant in a frame after the hello, so a dial made as the connection comes up, as a daemon's start makes it, waits up to 5 s for that frame rather than read a machine that opened itself as one that did not.
A machine reached over the network whose connection is not up within the dial's wait (10 s) fails the dial as a connection the core tries again, from 2 s up to a minute (`not_yet`), since `hide_peer` keeps dialing it and nothing else tells the core when it is back; only a WSL distribution of this PC that does not run is stopped, until the operator opens it.
Before, a host that slept longer than the connection's idle time stayed failed beside a live connection (the release A fault run, [docs/TESTING.md](../TESTING.md#the-release-a-gate)).
One machine is one tile: the one place the web shell reads the rail's computer tiles (`computerTiles` in `web/src/computers.ts`, over `openedMachines` in `web/src/pairing.ts`) leaves a machine that is a device to that device's tile, which leads to its screen ([Another machine's screen](0042-another-machines-screen.md#another-machines-screen)), and gives a tile of its own only to one that is not a device yet.
The device's row says which pairing it is (`DeviceSnapshot::peer_key`, the registration's `LinkOrigin::Peer` key), and both lists go by that key, never by the id a machine says of itself: Settings lists a paired machine once, as its pairing's row, and its device gets no device row (`listedDevices`).
An ask names a paired machine by its connection id, its device id, its name or the start of its connection id; a device id is what a machine says of itself, so one that two paired machines share is refused as `device_ambiguous`, and a window always sends the row's connection id.
The relay's reason is asked in a task of its own, at most once in 30 seconds, so neither the loop that publishes the machines nor an ask waits on the relay.
A share a terminal holds (`hide device share`) ends 10 seconds after that terminal last asked for its status; the command keeps asking while its allow question waits for the operator, so only a terminal that went away ends it.
An ask reaches the daemon from a window as a `pairing_<verb>` event and from `hide device` over the bootstrap socket, and both are answered by `Pairing::ask` with the caller it came from: sharing, adding, comparing, allowing, resuming, asking back, naming an address and pairing over SSH are the operator's alone, refused to a Hide pane (by what the kernel says of the caller, and by the command's own environment before it is sent) and to an external tool, and every ask is refused to a screen that is not this machine's own window, which hears the refusal alone.
The pairings under way go to this machine's own windows as a `pairing` frame, sent when a window connects and when it changes, and the answer to a window's ask as a `pairing_result` frame to that window; neither is part of the snapshot, a relay connection is never sent either, and the link and the words are never logged.
A terminal outside Hide's panes reads the same pairings in the status `hide device` polls; a program in a pane reads the paired machines there and never the link or the words.
`hide phone` asks the same socket about the phones paired with this computer (`hided/src/mobile/command.rs`, PRD device-connect-iroh D-70): `list` and `remove` from a terminal or a pane, `pair` only from a terminal outside the panes, judged the same two ways, and a bot's ask by its mode, as `hide device`'s is.
`pair` turns Mobile on when it is off, waits up to 30 seconds for the relay, issues the code Settings' QR button would, and answers the link with a `code_id` (the start of the code's SHA-256); the command draws the link as a QR (`hided/src/phone_cli.rs`, `qrcodegen`), never prints it, and asks `pair_status` by that id once a second until a phone pairs with it or it ends, and `pair_end` takes back a code it could not show.
A screen another machine shows of this one gets the `mobile` frame without its `qr` and `code_expires_at_ms`, so only removing a phone is open there; its connection lets through only `mobile_revoke`, `mobile_retry` and `mobile_push_mode`, refuses every other `mobile_*` kind (a code's making and ending, and Mobile's switch and method, which end a code too), and does not count it among the watchers of Settings › Devices' phones, whose last one leaving ends the code (`server::mobile_event_reaches`); a phone's name (`mobile_rename`) is this machine's own window's too.
A pairing owes the phones already paired and those computers its notice; `Mobile::observe_loop` sends what is owed one batch at a time (`Mobile::tell_paired`) and joins the batch before it ends, and at most `MAX_PHONES` are owed, the oldest dropped past that.
Mobile's resident loops (the seven-day sweep, and once the core opens `observe_loop`, `follow` and the first reconcile) run in one task Mobile keeps, and `Mobile::shutdown` joins it before it removes the serve entry, so no notice batch or delivery pass outlives the daemon's stop.
A phone that pairs is told to the phones already paired as a `phone_paired` notice naming the computer and the new phone, outside the push mode's rest, since it is about who can reach this computer.
Reading opens nothing: only sharing, adding a machine, answering for an SSH pairing and acting on a machine the records name open the endpoint.

**Pairing over SSH.**
A machine this one reaches over SSH and that already runs its own Hide is paired with no words, because whoever signs in to that account already holds its authority (`hided/src/pairing_ssh.rs`).
This machine runs two commands there, on the session `hide_node`'s upstream signs in: `hide device look-ssh`, which changes nothing and says whether that account's Hide runs, when it does the running core's node, build and release, and when it is stopped whether a desktop app opens its state folder (`app`), and `hide device accept-ssh`, which has it save a `pending` grant and answer its ids and addresses.
This machine saves the host as confirming, with the address the SSH login reached at the target endpoint's own port first when the alias has no proxy command and no jump host, and the alias it signed in through as the host's SSH route (`Host::ssh`), and confirms over the connection; the same request run again within 10 minutes is answered the same there, so a session lost midway is asked again as itself.
`hide device add <alias>` reads first which machine the alias reaches (`look-ssh`'s node); a machine this one is paired with already gets the alias only once a carrier over it proved that machine's key (`PipeTransport::check` within `limits::CHECK_WITHIN`, on the add's own session and operator place), so a device id and an accept answer only choose which key is checked: another known key is checked next, an unknown one pairs as a new machine on a session of its own, and an add makes at most three sessions, answering `device_already_connected` with `ssh` `recorded`, `not_proved`, `check_timed_out`, `update_there`, `hide_absent` or `hide_not_running`.
A dial here asks nobody: a login that needs a password, a passphrase, a code, an unknown host key or a key touch ends as not reached, and at most four such `ssh` run at once.
The target's command is `hide` in its account's command folder (`~/.local/bin`, or `HIDE_HOST_CLI_DIR`), started from that account's own `HOME`.
Nothing is installed: a machine with no Hide of its own, one whose Hide is too old to know the command or is a 1.2.11 build, which refuses every verb that pairs with `device_connect_unavailable`, and one whose Hide is installed and not running are each told apart and none is paired, and a machine with no Hide is still added as an SSH device ([Device file hosts and document saves](0047-device-file-hosts.md#device-file-hosts-and-document-saves)), whose switch then puts Hide there ([Switching a helper device to its machine's own Hide](0045-helper-to-own-hide.md#switching-a-helper-device-to-its-machines-own-hide)).
An alias one of this machine's devices already dials is not looked at: its own helper would answer, and that device's switch is the way to Hide of its own there (with-hide/hide#3007).

**The machine key.**
`peers/machine.key` holds the Ed25519 secret a machine connects as, with the id of the machine it was made on.
A file that names another machine, as a copied or restored home folder would carry, is replaced by a new key; a damaged file is an error, never a silent new identity, and so is one that another account can read or that is not this account's own file.

**Events.**
An event another core hands this one is appended and synced to `peers/inbox/<host>/events.jsonl` before it is acknowledged, in the sender's own sequence: a repeat answers its old number, a gap is refused with what the inbox holds, and a full inbox refuses instead of dropping.
Events are applied one at a time with `cursor.json` saved after each, and one that cannot be applied is acknowledged and logged rather than blocking the ones behind it.
The file keeps at most 8 MiB of events recorded and not applied, what a sender's box holds, and a full inbox by bytes refuses like one full by count; the applied lines ahead of them are dropped when nothing waits and, while an event still waits, once they pass the same 8 MiB, so the file and the read of it at the next start stay under twice that (`hide_peer::limits::MAX_UNAPPLIED_BYTES`).
Recovery streams older files one bounded line at a time and reclaims their applied history before accepting more events; an unapplied tail over its byte or count cap is an error that preserves the journal, and a failed compaction blocks further appends past the file bound.
An append that fails partway is cut back to the last whole line, so the next event never joins a torn one.
An event whose target the core does not know yet (`Applied::Later`) stays recorded and holds the ones behind it, so order is kept; it is tried again until its caller says the wait is over.

**The iroh transport.**
`hide-peer-iroh` pins iroh 1.5.0 and noq 1.5.0 exactly, with `default-features = false` and `tls-ring`, port mapping off, the proxy read from the environment, and a relay that is either the one URL it is given or none; a release's is `DEVICE_RELAY_URL`, asked for its address discovery too, which is how a machine learns the address a peer behind another NAT can dial.
A path counts as idle after 3 s with a keep-alive every 1 s, and a connection that had a relay path and has been without one for 5 s while this machine is still attached to its relay closes as `no_relay_path`, so the keeper dials it again; one that never had a relay path, or whose relay is down, is left alone, because a new connection would get none either.
An incoming connection's handshake runs in a task of its own, 16 at once and 10 s each, and one past that is refused before it starts.
Among the addresses a machine finds for itself, one in 100.64.0.0/10 is ranked last (`addr::rank_self_discovered`); mDNS lookup is an option the caller turns on.
A connection's path (`PathKind`) is read from the address iroh sends to now: the relay, a Tailscale address (100.64.0.0/10), or another of the two machines' own addresses; `PeerConn::path_changed` resolves when that moves, and `hide-peer` turns each move into `PeerEvent::PathChanged`, so the device list and the Settings row say the path the connection takes now, not the one it connected on (D-86).
`PeerTransport::relay` answers what the transport knows of its relay when a caller has a machine it could not reach to explain: none, attached, unreachable, or stopped for the month, which the relay's host says with a 503 and the words "monthly limit reached" to one HTTPS request made then, never on a timer; iroh keeps its own relay failure as text to print, not to decide by.
An endpoint that ends without being asked is built again, and iroh's own spelling of a key never leaves the crate: a key is 64 lower hex characters everywhere Hide stores or sends it.

**The link multiplexer.**
`hide_peer::mux` carries many streams over a carrier that has one byte stream; it never runs over iroh, whose connection already carries streams of its own.
It has two forms on one frame (`[kind][stream][length]`, read with at most 64 KiB of payload, `mux::MAX_FRAME`; a peer stream's writer puts at most 16 KiB in one, `streams::MAX_CHUNK`).
The link form is the one the SSH and WSL helper links and the attach role run ([A core on another machine](0039-core-on-another-machine.md#a-core-on-another-machine)): stream 0 is the node's link and every other stream a TCP forward.
The peer form (`mux::streams`, `Pipe`) is what the pipe transport's connection is: each end greets with its version, the dialer opens odd stream ids and the acceptor even ones, and a stream is opened at a priority, half-closed (`FIN`), refused by its reader (`STOP`) and paid for with credit, as a QUIC stream is.
A sender may have 16 frames of a stream unread by the other end and gets credit back as they are read, so a reader that stops reading stops only its own stream; the outbox sends control frames first and then each priority class whole before a lower one, with 16 places per class, so keys never wait behind a file (D-62).
A class lives as long as its connection and the other end names a stream's priority, so a stream is opened only at a priority a stream kind has, or the proof's: an open at any other number is answered `STOP` like one past the cap, and this end's own is refused before it is told.
Each end opens at most `limits::MAX_STREAMS` (72) streams of its own and takes at most twice that from the other end, 16 of them unaccepted; a frame for a stream past that is answered `STOP`, never queued.
A close is one `BYE` frame with its code, written before the carrier ends and waited for at most 2 s; a carrier that ends without one reads as a lost connection on every stream.
Why a peer connection ended is its reader's to say: a write that fails, as one into a carrier the other end just closed does, stops the writing and leaves the end to the reader for those 2 s, so the other end's `BYE` is read with its code and not as a loss.
The code is the one word for a closed connection: it is recorded before the connection ends, a loss included, and no stream is opened from then on.

**A WSL distribution and its PC.**
A distribution with a Hide of its own is a paired machine like any other, and what differs is only the carrier (D-27, D-62; `hided/src/pairing_wsl.rs`).
The PC dials: `Carriers::carrier` runs `wsl.exe -d <distribution> --cd ~ -e sh -c … hide device carry` and the command's input and output are the carrier; a distribution never dials its PC, and `wsl.exe` exists on Windows alone, so only a Windows core holds carriers (`Settings::wsl` in `peer_host.rs`).
`hide device carry` asks its own account's daemon, on the bootstrap socket, to take that stream as a carrier (`Ask::Carry`, operator only and never from a pane), and from the daemon's answer line on every byte is the connection's: the daemon hands the stream to its pipe transport (`PipeTransport::arrived`), where the peer proves its key before anything else is read.
A core that account ran before and that is not running is started by the same command, as a login would start it: a distribution with no systemd has nothing else that does, so its core lives while the distribution runs, and the PC's `wsl.exe` holds the distribution up for as long as the connection stands.
Its end ends the command and what it started (`hide_platform::process`'s owned child), and what the command wrote to its error stream goes to the diagnostic log as `wsl.carrier_said`, last line only.
The PC saves the distribution's name as that machine's first address (`Candidate::Wsl`, in `peers/known.json` only): it is never told to another machine, a peer that names one in its own candidates has it dropped (`Pairings::adopt`), and iroh refuses to dial it.
A build before this one cannot read a `known.json` that holds such an address, which is the same one-way step every new address kind is.
Pairing and switching run the commands an SSH pairing runs, through `wsl.exe` in place of a login (`pairing_ssh::Login`, implemented by `Ssh` and by `pairing_wsl::Wsl`): `look-ssh`, `accept-ssh --wsl`, `connect` to start a core, and the same answers; `wsl_not_reached` is the one code that differs, and at most four such steps run at once, counted with the `ssh` ones.

**A machine reached over SSH.**
A host this machine keeps and reaches through an alias of its SSH configuration that signs in asking nothing is connected over SSH when no direct path opens, and over the relay only when SSH does not either (`hided/src/peer_ssh.rs`).
The alias is this machine's own fact: `Host::ssh` (`Alias`, or `Off` once it reached a Hide proving another key), else the SSH login a switched host was started through (`Host::started`), never in a link, an answer, a hello or the snapshot; `Host::dial_addr` puts it last as `Candidate::Ssh`, which serde never writes and iroh skips, and only the side that keeps the host (`Peers::keep`) dials it.
The first dial is a ladder (`Beside::ladder`): iroh at once, an SSH carrier from `limits::SSH_AFTER` (1 s) unless iroh showed a direct path by then, and at `limits::DIRECT_WITHIN` (4 s) the higher rank: a direct path, else a proved SSH connection, else iroh's relay connection, with a sign-in still running handed on for the climb to take (`limits::TAKE_WITHIN`, 5 s once proved); a connection not chosen is closed `probe` before its first exchange and drained before the machine is dialed again, and each SSH attempt is one task bounded, wherever it is, by the bound of the dial that started it: a dial is given up at `limits::DIAL_WITHIN` (30 s) and hands its bound down with it (`DialBound`), which records that it ran out before it drops what it limited, so the carrier maker reads why an attempt was given up from the bound, never from the moment its cleanup runs.
The ladder runs only for a route that is ready (its last attempt proved, or none since the daemon started); a waiting, due or parked one adds no wait, and a due one is dialed after iroh's dial failed or opened nothing within `limits::DIRECT_WITHIN`, since nothing else would carry the pair.
While the connection lives the keeper climbs (`Peers::climb`) between two builds that name `ssh_path`: a relay connection whose route is ready or due moves to SSH after `limits::RELAY_GRACE` (5 s) of reading the relay, at once when a handed sign-in waits, and an alias recorded while it lives is read from the records when they change and climbed to; the side that dialed SSH probes for a direct path after `limits::CLIMB_FIRST` (30 s, doubling to 10 min after a probe that found none, and at once on a network change); each move is a new connection through `dial_move`, in the key's dial turn, that names the one it replaces and is closed `probe` unadmitted unless its path ranks above the held one's, read again before its hello; however a move ends short of its install, its being given up included, its connection is closed `probe` and drained before the machine is dialed again.
Each end remembers the names of connections ended for another (refused, replaced, or named by a hello as replaced) for `limits::SUPERSEDED_FOR` and never less: at most `limits::MAX_SUPERSEDED` per machine, an install whose names would not fit being refused rather than a name forgotten early, and for at most `limits::MAX_SUPERSEDED_PEERS` machines, a new one taking the place of one with no live connection; a name heard again keeps the time it was first heard.
An SSH connection beats (`HelloFrame::Beat` every `limits::BEAT_EVERY`, 15 s) and is closed `lost` when its hello stream read nothing for `limits::BEAT_DEAD` (45 s), since the far `sshd` would hold a dead carrier for hours; iroh and WSL connections do not beat.
`hided`'s `SshCarriers` makes each carrier: one `ssh -T -a -x -k` through `Upstream`, asking nobody, in one of `limits::MAX_CARRIER_SIGN_INS` (2) places of its own, never the operator's four, and the start script's `carry` step, which execs the far account's `hide device carry --ssh` (`<home>/.local/bin/hide`, `hide.cmd` on Windows) in the script's place; the far command never starts a core and carries only to a daemon that echoes `over: ssh`, so an SSH connection's two ends both name `ssh_path`, and `Peers::establish` closes `probe` one that does not as a second wall.
Each known host has a route, in memory: ready, waiting after a failure `SshProblem::retried` names (30 s doubling to 10 min, due on a network change), or parked by `SshProblem::action` (`sign_in`, `check_host_key`, `reopen_hide`, `retry`), by a far Hide too old to carry (`update_there`, lifted when its hello names another build) or by a proof that did not hold; a far Hide that is not running makes it wait 10 min, an SSH connection that ended within 60 s makes it wait, as does a carrier that ended before its proof with no refusal or one that proved and was not taken, and an attempt given up because its dial's bound ran out before anything settled it (`timed_out`; given up any other way, because another path was chosen or the daemon stops, it leaves the route as it was, however late its cleanup runs), a parked route refuses at once without starting `ssh`, and `Ask::Retry`, the app opening (for `sign_in`) and the daemon's start try it again.
Each failure doubles the wait once (a sign-in's own failure is counted by its attempt, a move that proved and was not taken by the climb); a proof keeps the wait, and only an SSH connection that stayed 60 s, a retry or a network change starts it over, so a path that proves and falls again waits longer each time.
Recording an alias, the same one included, starts its route over under a new epoch and ends its sign-ins still running, while a connection it already carries stays; the record and turning a route off are saved under one lock, so an attempt older than the record writes nothing.
A carrier's proof of another key turns the route `Off` in `peers/known.json`, by compare-and-set on the alias the attempt dialed and only for the route's epoch, leaving `started`; a save that fails parks the route `not_saved`.
The row carries only why a route waits (`PeerMachine::ssh.blocked`), never the alias; what the far command and `ssh` wrote last goes to the log as `ssh.carrier_said`, and each attempt as `ssh.carrier_dial`.
Over SSH, the confidentiality and integrity of the bytes in transit rest on SSH and its host-key check; the machine keys authenticate the two ends.

**Diagnostics.**
The daemon records every log line of its own through `hide_core::diagnostic!`, and only the commands and entry points that print to a terminal use `eprintln!` (`hided/clippy.toml` disallows it, `scripts/verify-cargo.sh lint` enforces it): a write that fails (a full disk behind a login item's `Logs/core.log`) loses the line, where `eprintln!` panics, and a panic under a connection lock poisons it for every later caller. The holds in `hided/src/demand.rs` also take their locks through `PoisonError::into_inner`, so a callback that panics under one leaves it usable.
`hide-peer` writes its diagnostics through `hide_peer::log`, which `hided` points at the core's diagnostic log at start; a program that sets no sink gets them on stderr.

### Which connection may send what

Every client event kind declares the connections it is for in one table (`hided/src/server/event_class.rs`), and a kind the table does not name is refused: a test reads every kind hide-core's decoder knows, and the kinds hided answers itself, and fails on one with no class, as `wire_enum_tests` does for the wire's enums.
A connection is this machine's window (desktop or web), another machine's view (`remote`) or a tool's (the Workspace CLI, a pane's command); a class says which of them may send the kind:

| Class | Who may send it | For example |
|---|---|---|
| Screen | any window, a view, a tool | moving focus, typing, opening a file |
| Window | this machine's windows and a view | a phone's removal, a View's comment |
| Own window | this machine's windows only | pairing, a phone's pairing, external tools, `window_focus`, `window_screen`, `product_analytics_connected` |
| Desktop | the desktop app only | `desktop_activity`, `desktop_notices` |
| Local | this machine's windows and its tools | a core move, revealing a path, a device's sign-in |
| Daemon | no client: hided sends it itself | `ui_attached`, `peer_machines`, `guest_panes` |

A refused event never reaches the core, so no screen's `status.last_error` names it: only that connection is answered, with a `refused` frame `{kind, reason}` (`not_here`, or `unclassified`), which the page ignores, and the daemon logs `event.refused` with the kind, the reason, the connection and its kind.
A relayed screen (a node's screen the core draws through its link) is a window whose pairing asks `hided/src/pairing.rs` still refuses as another screen's.

### The two cores' stream

Each machine of a pair has a core of its own, and the `core` stream (kind 11) is the one stream the two cores talk on, apart from a guest's node and its management stream (PRD device-connect-iroh D-62, D-72).
A side that holds an active grant on the other opens it when the connection comes up or the grant turns active, at most one each way, and both sides write on whichever is open, so a machine that is only opened answers on the stream the other opened.
Its messages are one tagged list (`hide_peer_protocol::core::CoreMessage`, in `contracts/peer-link.json`): a letter with the sending core's id for it and its sender's registration id and name (`Agent`), `letter_taken` with the registration that took it or `letter_refused` with a reason, and a read or a start one core asks of the other (`call`) with its `call_answer`.
A later build adds a kind to the list, and a reader skips a type it does not know.

`hided/src/peer_core.rs` is the one place a daemon handles it, and it decides nothing: who may write, read or start is the core's to judge from the pairing it was told ([delivery.md: Another machine's agents](../delivery.md#another-machines-agents)), and the letters wait in the core's ledger, not in the daemon.
The daemon asks the core for what waits for a connected peer whenever the core says its outbox moved or a stream opens, and sends a letter again after 30 s without an answer and on the next stream; the receiving core keeps the same letter once.
A letter is handed to the core in the order it came and answered on the stream it came on; a call runs beside the letters, four at a time per peer, and one past that is answered `capacity` and logged (`peer_core.call_refused`).
The four places are the peer's, not a stream's (`PeerCore::place`): a call keeps its place until its work ended and its answer was handed over, whatever became of the stream it came on, so a peer that opens stream after stream has four calls at work and no more; the place list drops a peer's entry once it has no stream open and none of its places is held, and the daemon's end stops the calls still at work.
A read waits at most 15 s for the other core and a start 180 s (`delivery_timeout`), and a call whose stream ends first is answered `machine_unavailable`.
What the daemon remembers is of this run only: which letters wait for their answer and which calls for theirs, each dropped when its peer's last stream ends.
A peer of a build from before this stream refuses the kind (`unknown_kind`), which is logged and asked again at the next connection.
