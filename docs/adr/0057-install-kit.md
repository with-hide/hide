# 0057. The install kit

- Status: Accepted
- Date: 2026-09-29
- Code: `hide-kit/`, `hide-host/src/kit.rs`, `hide-core/src/kit.rs`, `hide-core/src/runtime/kit.rs`

## Decision

### The install kit

`hide-kit` is the one list of what Hide puts on a machine: the `hide` command in its command folder (a Unix link, or a Windows `hide.cmd` that names its `hide.exe` by a relative path), Hide's Claude Code and Codex hook entries through `hide-agent-hooks`, and one release of coordination retirement (`coordination_retirement`).
After the Codex hook part is in place, a pass also has Codex trust Hide's own entries, through `codex app-server` (`hide-kit/src/codex_trust.rs`; [agent-hooks.md](../agent-hooks.md#codex-trusts-hides-own-hooks) owns the target rule, what is recorded and how, the child's ownership and the failure line).
That check runs once, between `agent_kit::apply` (which puts in the agents' pieces) and `agent_kit::reports`, so the Codex hook part carries its failure into the agents' rows and a first install is trusted in the pass that made it; `status` starts no process and repeats the last pass's finding.
Each part answers `observe`, `install` and `remove` against a `KitTarget` naming the machine's home, kit and command folders and the programs it runs; a new part is one more entry in that list.
The kit folder is a path that outlives a build, because the hooks and the `hide` link name it: the running app bundle's `Contents/Resources` on macOS, the unpacked desktop package's `resources` on Windows/Linux, and the helper root's `current` on a device, which the helper points at its own version folder before it installs, as a core that runs from that root does (`hide_kit::current`).
The device helper then removes every other build folder no helper runs from: two Hide builds that reach one device account take turns at `current`, and a build whose helper still serves the other connection stays until a pass after it ends (`hide_host::kit::remove_other_builds`).
On macOS and Linux `current` is a link to the build folder.
On Windows it is a folder holding copies of the build's `hide.exe` and `hide-agent-hooks.exe` and a `.hide-current` file naming the build, and nothing under a helper root or in its command folder is a link: Windows' OpenSSH turns the redirection guard on for `sshd.exe` (its `install-sshd.ps1` sets the image's `MitigationOptions`), every process of the session inherits it, and it refuses with error 448, "The path cannot be traversed because it contains an untrusted mount point", any junction whose maker was no administrator, which is every junction a standard account's node makes and every one a desktop app makes (with-hide/hide-private#501); the desktop app's own command makes none either (with-hide/hide-private#596).
A pass copies the next build's programs beside the old ones and renames each over its name (`hide_platform::fs::atomic::replace_program`); a copy a pane, a hook or a `hide` still runs cannot be replaced on Windows, so it is renamed aside first, keeps running from the renamed file, and is removed by the first pass after it ends.
The first pass of this layout on a device whose `current` is still a junction fills a folder beside it and swaps it in, and its shim drops the `.hide-kit` junction it made.
One pass at a time changes `current`, under a lock on the helper root.
The Windows `current` holds no `hided.exe`, so a `hide` that would start or replace a daemon beside itself (`hide connect`, `hide serve`) answers there that it finds no `hided` beside it; a device's node runs from its build folder and never from `current`.
Every path a pane uses is the same before and after an update (`<root>\current\hide.exe` as `HIDE_INSTALL_CLI`, `<root>\current\hide-agent-hooks.exe` in each hook entry), so a pane started from the previous build keeps working and no hook file is rewritten.
A Windows device pane's `PATH` starts with that `current` folder (`hide_host::kit::PaneInstall::path_first`, put first by `hide-node`'s `engine_panes`), so its `hide` is its own installation's even when the desktop app's `hide.cmd` holds the account's command folder; a pane started before this build has no such folder on its `PATH` and finds the app's command until it is reopened.
`~/.hide/kit/installed.json` records the parts the kit installed; a recorded part that is gone was taken away by the operator and stays away until Reinstall (D-26), a record that cannot be read installs nothing on a guess, and `~/.hide/agent-hooks/installed-once` from before the kit is not such a record (B20).
An apply installs what was never installed and replaces what is outdated, one part's failure never stops the next, and a second apply of the same build writes nothing; Reinstall also restores the parts it names (B8).
Another tool's hook entries and a `hide` that is not Hide's link are never touched.
Every apply also retires the folders the agent labels Herdr plugin `hide.agent-context-labels` left, which the core's label worker replaced (PRD labels-in-hided D-12; `hide_kit::legacy::local`): `~/.local/state/hide-plugin-upgrade`, `~/.local/share/hide/agent-context-labels`, and `~/.local/share/hide` once nothing else is in it.
On this Mac the core imports the plugin's state before the kit first runs.
Every child the kit starts (`codex features`, `node --version`, the login shell asked for its `PATH`) runs with the account's login variables and nothing else inherited ([The platform layer](0005-platform-layer.md#the-platform-layer)), as an owned child that leads its own tree, under a deadline, and ends when the kit's owner raises its stop flag (`hide-kit/src/process.rs`, `hide-agent-hooks/src/codex_daemon.rs`, both over `hide_platform::process::run_to_end`).
The one-release retirement stage first performs bounded, read-only checks of the former coordinator and Hide ledgers, sasu registry and registered checkout run state.
An active run, open request, active watch, unreadable record or capacity failure leaves every installation and folder unchanged and reports why.
A device runs no such inspection: the operator ended the stage for devices on 2026-10-29 (PRD system-ssh-device-link D-16), so a device, like a WSL distribution, goes from its probe to its install.
The shared authority check refuses relocated legacy homes outside HOME or overlapping the active kit or state, and requires a registered owning checkout for indexed runs outside HOME, before either pass can write.
No old test server is stopped by name without an ownership receipt; the operator confirms earlier test servers before the transition and refuses automatic cleanup when ownership cannot be established.
After preflight it stops the former daemon, unloads the LaunchAgent and deletes its plist, removes only Hide-owned command/plugin links, deletes the kit copy, then renames `~/.hide/hcoord` and `~/.hcoord` to siblings ending in `.retired-YYYY-MM-DD`.
`~/.hide/kit/coordination-retirement.json` records the step, reason and completion for idempotent retry.
After a failed retirement step, ordinary parts continue and the retirement row keeps that failure; a preflight refusal precedes the account lock and stops the entire apply.
The old ledger is never imported or deleted and there is no rollback; the operator chooses the merge/install transition time with all work closed and chooses the later release that removes the stage.
Legacy labels and helper folders are retired separately by `hide-kit/src/legacy.rs`, only after account ownership and references are checked; results remain diagnostic records.
The kit runs nothing from and writes nothing into a folder another account can change: `~/.hide` and `~/.hide/kit` are created mode 0700, and a part whose folder is not owned by the account or is writable by its group or others reads failed with that folder named rather than used (`hide_kit::private_dirs`).
One kit at a time changes an account: an apply or a removal holds an exclusive `flock` on `~/.hide/kit/.lock` (`hide_kit::lock_account`), waits up to 90 seconds for another kit holding it, and reports every part unavailable when that wait runs out or Hide is quitting, because two registrations of one machine connect together at launch and a Mac that is another Mac's device also runs its own kit.

A Codex attached to its shared app-server daemon runs its hooks in the daemon's environment rather than the pane's, so the pane's session is never reported and no request, result or label can be read for it (openai/codex#48500).
The kit does not change that setting on its own (PRD settings-cleanup D-14): the earlier `Codex를 pane마다 실행` part (`codex_per_pane`) and its switch are gone, a record that still names it loads and drops it, and a machine where an earlier Hide turned the setting off keeps it off.
`hide_agent_hooks::codex_daemon` stays the one place that writes the setting or stops the daemon, only through Codex's own `codex features disable daemon_auto_start` and `codex app-server daemon stop`, run with the account's HOME and its `.codex` named as `CODEX_HOME`, for the turn-off the operator confirmed; the kit itself only reads the setting and whether a daemon answers, and Hide writes nothing of this setting into Codex's `config.toml`, whose only entries of Hide's are MCP servers ([agent-hooks.md](../agent-hooks.md#mcp-servers)).
The stop (`codex_daemon::stop`) asks `codex app-server daemon version` first and, unless it reads running, asks `codex app-server daemon stop` anyway and takes its typed `status`: `notRunning` means nothing was running, so nothing is stopped and a second request stops nothing again, unless `daemon version` read running, when it is checked again like `stopped`, and any other answer is a failure; the check after the stop is the pane's read, socket rule included, so a daemon whose socket lives elsewhere reads as down once `daemon stop` typed `stopped`; a daemon that still answers after the stop is a failure rather than a stop (PRD codex-daemon-apply D-04, D-11).
Hide supports seven agents, each a row of `hide_kit::agents::ADAPTERS` in this order: Claude Code, Codex, Grok, OpenCode, Pi, omp and Antigravity.
They began as the agents Herdr shipped an integration for, and what keeps one on the list is the support policy ([agent-hooks.md: Which agents Hide supports](../agent-hooks.md#which-agents-hide-supports)).
A per-agent layer (`hide-kit/src/agent_kit.rs`) sits beside the parts: `Scope` carries `agent_on` and `agent_off`, `KitReport.agents` answers one `AgentReport` per adapter, the record keeps the operator's choice and the pieces installed, and the core's `kit_agent_set` event, `KitSnapshot.agents` and the host protocol's `reinstall` (`agents_on`, `agents_off`) carry the same choice to a device.
An earlier build also put Herdr's integration for each agent in as a piece of its row (record code `herdr:<agent>`); the kit installs none now and takes out only what its record holds ([agent-hooks.md](../agent-hooks.md#herdrs-integration-an-earlier-hide-installed)).
The record decides what Hide may remove: an integration that was already there when Hide first looked is the operator's and stays, on and off and when the machine leaves Hide, and only one of Hide's own is brought up to date.
A failed install fails that agent's row alone.
Every integration call is one owned child with a deadline on the kit worker or the helper, never under `Mutex<Runtime>`.
The fifteen agents earlier builds supported and this one does not (Cursor, Copilot CLI, Amp, Factory Droid, Kiro, Qwen Code, Goose, Cline, Kilo Code, Crush, Junie, Augment, Kimi Code, Mistral Vibe and Gemini CLI) are retired once, by the record's ownership (`hide-kit/src/retired_agents.rs`): a piece the record names is taken out only where it carries Hide's own marker, a file the operator wrote or edited stays, and each piece leaves the record as it goes, so a second pass reads nothing and a piece that could not go is tried again.
Their results are `KitReport.legacy_retirement`, logged with the other retirement records and shown on no row.
Claude Code's and Codex's hook parts stay kit parts, because Memory, the pane diagnosis and `device_hook_status` read them, and their agent switch gates the part: off, the part is neither installed nor replaced, and switched off now it is taken out.
OpenCode's hook piece is Hide's plugin, and Pi's and omp's Hide's extension (`hide_agent_hooks::plugin::file` for the adapter's `PluginDialect`, `HookSupport::Plugin`, record codes `hook:opencode`, `hook:pi` and `hook:omp`), an agent piece rather than a kit part: its state is read from the file, and a pane's hook status for those agents reads that piece (`agent_hooks::kit_hook_status`) where Claude Code's and Codex's read the pane diagnosis.
The other agents' hooks are `hide_agent_hooks::guidance`, a smaller module with its own marker and per-agent file shape (Grok's, agy's named `hide` block, and retired agents' layouts kept only for their removal), so the six-event runtime code and its counters never take a meaningless arm for an agent that does not feed them.
Claude Code's, Codex's, agy's, Grok's and Pi's pieces each own the agent's folder trust for the folders Hide starts agents in (`hide_agent_hooks::folder_trust`, added on the folder's node before Hide starts the agent there, removed with the worktree, and removed whole when the agent is switched off), recorded so a removal takes out only Hide's ([agent-hooks.md: Folder trust for the folders Hide starts agents in](../agent-hooks.md#folder-trust-for-the-folders-hide-starts-agents-in)).
agy's piece also owns the trusted, tool-refusing folder Hide AI runs agy in ([AI_PROVIDERS.md: Antigravity](../AI_PROVIDERS.md#antigravity)); a pass that finds that folder missing or untrusted reads the piece as Stale and writes it again.
An agent is installed when one of its programs is found on the login shell's `PATH`, the daemon's own or the usual install folders; a folder it creates does not count, and an agent that is on and whose program is gone keeps its pieces, and its switch when the operator chose it, until the operator switches it off ([agent-hooks.md: Installed means the program is found](../agent-hooks.md#installed-means-the-program-is-found)).
Detection, and the login shell it asks (once, then again only when a startup file changed), run only on the kit worker, the helper and Hide AI's own worker threads (which use the same search, `hide_platform::programs`), never on the render path or under the runtime lock, and under test the search is the fixture's `~/.local/bin` and a stand-in shell's answer, so a developer's own agents cannot decide a result.
A `KitSnapshot.agents` row keeps four things apart: whether the program was found (`availability`: `available` when it was, `not_installed` when it was not; `unsupported_system`, found but with nothing Hide can put down on that system, is produced by older device builds only: this build's kit never reports it, since every supported agent reads its skill folder on every system, and it stays on the wire as the transition path for a connected device still running an older build), the operator's switch (`enabled`, the record's choice or the adapter's default), whether the record holds the operator's own choice for the agent (`chosen`, `AgentReport.chosen`, absent and so false in a report from a build that predates it), and the pieces' own states; an agent that is on and whose program is gone is `not_installed` with `enabled: true`, and a shell lists it under Installed with its switch only when `chosen` is true, so an agent that is on only by default and was never found is not listed as installed, and one the operator switched on keeps the switch that takes Hide's pieces out.
`KitSnapshot.checking` is true from the moment a read of the machine's kit is queued until it answers, and `KitSnapshot.check_failed` is `read_failed` after a read that could not be made (a device whose helper did not answer) and clears at the next answer; the last report stays in place beside either, and the cause stays in the diagnostic log (`Runtime::set_kit_checking`, `runtime::tests::device_kit`).
`hide_kit::Scope` carries the parts to restore, the two agent choices and the operator's one-shot request to turn Codex's shared server off (`codex_daemon_off`, which merges by OR), and two queued requests for one machine merge with the later choice winning for an agent both name; the device helper receives them in `kit` `reinstall` (since helper protocol 21, whose `codex_daemon_off` field is absent unless the request was made; a helper on another protocol is refused when it connects, so an older helper never receives a turn-off that would leave the running daemon up).
Removing a machine does not touch the Codex setting.
Every Codex start Hide makes passes `--no-daemon` first when that machine's kit read a Codex that has the setting: `wire::agent_start_params` takes the machine's `codex_launch::CodexDaemon`, which every start path (a task's agent, a reopen, a fork, a wake) carries from the runtime, so no path can leave it out; a missing, failed or pending capability refuses the start with an instruction to recheck the target machine’s kit in Settings.
The report carries that capability as `KitReport.codex_daemon` (`KitSnapshot.codex_daemon`), read from the target's Codex binary: `true` when it has the setting, `false` when it is a confirmed older Codex that starts no daemon and so gets no flag, and no answer when there is no Codex or the read failed.
The report also carries whether that Codex starts the shared daemon on now (`KitReport.codex_daemon_on`, read with the capability and never changed by a pass) and whether a daemon answers now (`KitReport.codex_daemon_running`, from `codex app-server daemon version`, which never starts one); either one is what a Codex pane reads as the reason it is not connected (`KitSnapshot::shares_codex_server`), so a machine whose setting an earlier Hide turned off while its daemon kept running still offers the turn-off (PRD codex-daemon-apply D-07, B9).
After a turn-off that answered `stop_failed`, a read that cannot tell whether a daemon answers keeps the machine on the shared server, so the retry stays on offer until a read says no daemon answers (B7).
The control socket decides only the read behind a Codex pane's reason (B9): a failed `codex app-server daemon version` reads as no daemon only while the daemon's control socket under the account's `CODEX_HOME` (`app-server-control/app-server-control.sock`, Codex's observed layout, named once in `codex_daemon.rs`) is gone, and with the socket still there, or an answer Hide cannot read, the read is unknown, so a stale socket a crashed daemon left reads as unknown to the pane until Codex removes it.
The confirmed turn-off never decides from the socket whether to stop, so a Codex whose socket lives elsewhere (another version or platform, a relocated `CODEX_HOME`) is still asked to stop; `daemon stop` answers `notRunning` for a crashed daemon and leaves its stale socket in place (measured on Codex 0.160).
An answer about the daemon Hide cannot read reads as no answer, and the core logs it as a `kit` `codex_daemon.unreadable` record when it appears or changes.
The operator's own request to turn it off (`codex_daemon_disable { device_id }`) is the only change: `Runtime::request_codex_daemon_disable` queues `Scope::codex_daemon_off()` on the machine's kit worker, `hide_kit::apply` runs `codex features disable daemon_auto_start` through `hide_agent_hooks::codex_daemon::turn_off` before anything else in the pass, reads the setting back, stops the daemon that is still running through `codex_daemon::stop`, and answers in `KitReport.codex_daemon_off` (done, or a failure code with Codex's words kept for the log), and `KitSnapshot.codex_daemon_off` is `pending` from the request until that report.
A disable Codex refuses or does not answer leaves the setting as it was and stops nothing; a stop that fails after the setting went off answers `stop_failed`, and the same request again finds the setting off and only stops; `unreachable` (Hide quit or the device's helper went away) can come before or after the setting went off, so its line claims neither.
A call that never ran to a report ends the request as `unreachable`.
A device takes the request only over the helper connection the operator confirmed it on: a request for a device whose helper is not connected is refused into the log (`codex_daemon_off.refused`), a connection that ends before its worker takes the request drops it from the queue as `unreachable` (`codex_daemon_off.dropped`), and each call that carries it is a numbered run whose answer settles the request only while that run is current, so a late answer from an ended connection changes nothing (`Runtime::drop_queued_codex_daemon_off`, `DeviceKitCall::daemon_off_run`).
A Reopen of a pane Hide cannot hear (`pane_reopen { pane_id }`) is core-owned too: `hide-core/src/pane_reopen.rs` refuses everything knowable first, ends the agent and starts it again in the same pane with its own resume arguments through the same two calls agent sleep uses, on a worker outside the runtime lock, and `Runtime::pane_reopens` holds one entry per pane so a second press while one runs starts nothing (`docs/status-model.md`, Not connected, and what fixes it).
The flag is a transition path that goes away once openai/codex#48500 runs a daemon's hooks in each window's environment.

This Mac's kit runs on `crate::kit::KitPump`, a core-owned thread rather than the session-sync coordinator, because the kit installs whether or not this Mac's engine answers: the launch pass first, then a Reinstall, then a re-read every five seconds while Settings is observed and once when a Settings tab showing the kit opens (`kit_check`); it takes its job under `Mutex<Runtime>` and, with the lock released, sends it to the core's own node as the same `kit` call a device answers, so every file write and child process happens on the node (`hide-host/src/kit.rs`, `KitPlace::Bundled`).
The node, not the core, knows where its kit's parts are: hided gives its own node the package's resources folder, and the hook diagnosis the kit and the coordinator publish is the node's `hook_diagnosis` call.
The core's own node, and the node of a machine that dials its core, read where their kit comes from off the program they run (`KitPlace::of_program`): a desktop package's resources (`hide_kit::bundled_kit_dir`), or a whole build Hide placed in one of the account's own install roots (`hide_kit::layout::placed_roots`: `~/.hide/core/<16 hex>/`, which a login item's core runs, and `~/.hide/host-helper/<16 hex>/`, which a core moved before 1.2.0 runs; each with `hide` and `hide-agent-hooks` beside `hided`; `hide_host::kit::placed_build`), on a machine that may have no app at all.
The kit then writes its hook entries under that root's installation name, and the panes the core starts name the installation of the same kit place, decided once at the core's start (`always_on::adopt_core_kit`, `hide_host::kit::adopt_kit`), so a pane's hooks are always ones its own Hide wrote; a core that installs nothing names none, as a development build does (`a_process_s_panes_name_the_installation_its_kit_writes_the_hooks_of`).
A machine connected as a server runs its core from `~/.hide/core` with no app; before that root counted, its panes named it while its kit installed nothing, and no agent it started ever reported its session (2026-11-26).
A build copied anywhere else, or a lone `hided` in such a folder, is no build Hide placed and installs nothing into the account, so a development build copied into a folder of that name, or a fixture's build while HOME is the operator's, cannot write the operator's hooks.
From a build folder the kit installs from `<root>/current`, which it first points at the running build, and removes no build, since the core update owns that and an update keeps the build it may go back to (`hide_host::kit::run_build`, `adopt_build`).
Any other `hided`, a Cargo build directory among them, has a standalone node, which refuses the kit; the row says why (B11).
The rule is where the program came from, not whether an app is installed: it keeps a development build, whose folder the next build deletes, from writing hooks that name it, and a login item's program is the build Hide placed for it, as a device's helper's is.
Stopping the core closes its own node, which raises the kit's stop flag before the worker is joined.
A device's kit runs on its helper through the helper protocol's `kit` call (`hide-host/src/kit.rs`: `apply`, `reinstall`, `status`, `remove`), always for the helper root the running helper was installed under; one worker per device makes those calls one at a time (`runtime/kit.rs`, `crate::kit::spawn_device_worker`): the connection pass after every `host.ready`, a Reinstall, and a read when Settings opens.
A machine that dials this core, the one a core was moved off before 1.2.0, has its kit kept the same way through its link, with no consent and no helper upload: the core asks with the command folder a device gets by default (`~/.local/bin` in that machine's home, which `HIDE_HOST_CLI_DIR` moves) so the node installs into that machine's own home, from the app it runs (`Services.kit`); removing its row takes nothing off it, since it registers again on its next link.
Each link's kit work ends with that link (`Env.stop`), so a node that dials again starts its kit with a stop of its own.
Two registrations of one account can connect at the same time: the helper upload stages each file under a name no other connection uses, keeps a final file that already holds the expected bytes, and takes a helper folder another connection created first, and the account lock orders the two applies.
An answer a worker brings back after its registration went or its removal started changes nothing (`ingest_device_kit_answer`), so a slow install never brings back a device the operator removed.
A device without consent, with an outdated one, or on a platform this build does not carry installs nothing and its row says why (B17, B21).
Removing a device with its helper connected takes Hide's parts and the helper root off it on that device's worker, after any kit call already running there, and closes the helper connection afterwards; a device added again waits to connect until that is done.
Without a connected helper, the registration goes and a `kit` `device.kit_left` record names what stayed (B24).
The hooks, the `hide` link and the helper root belong to the device account rather than to one registration, so while another registration's consent is bound to the same user and machine (by machine id when both consents carry one, else by the host key both carry, so a consent bound to its machine and one from before that still compare, else by host name and port), removing one of them leaves the kit for the other, records the same `device.kit_left`, and the device row's `kit.shares_account_with` names that registration for the confirmation.
Each machine's report reaches the shell as `DeviceSnapshot.kit` (`components` with `kit_component_id` and `kit_component_state` from `contracts/snapshot-wire-enums.json`, `busy`, `unavailable`, `offers_reinstall`), and every apply writes one `kit` `apply.completed` record naming each part's outcome.
A device's agent panes are judged by the same `hide_agent_hooks::diagnosis::instrumentation` as a local pane, from what the pane's hook reported to the core (`RemoteSessionSnapshot.pane_hook_tokens`, laid from `agent_hooks::facts` and not sent to the shell) and that device's kit (`agent_hooks::device_hook_status`), in `Runtime::derive_device_session` (D-21).
The kit part read is the one for the dialect that counts for the pane's agent (`agent_hooks::kit_hook_status`): Claude Code's or Codex's hook part, or, for an OpenCode or Grok pane, the hook piece of that agent's row (`KitSnapshot.agents`), on this machine as on a device; a change of that piece re-judges the local panes (`runtime/kit.rs`, `pane_judgement_inputs`).
`desktop/e2e/device-kit.spec.ts` proves a device's kit over a real SSH connection: the install, each part's row, the installed hook's SessionStart in a device pane, a part the operator took out staying out until Reinstall, and removal leaving another tool's entries and retained records.
The isolated sshd logs in as the account running the suite, so `desktop/e2e/device-home.ts` proves its private HOME before registering the device; otherwise kit writes would reach the operator's own files.

#### The store of skills and MCP items

The skills and MCP servers the operator adds live in one store per machine, `~/.hide/store` (`hide_kit::layout::store_dir`), with its record `store.json`, each item's files under `items/`, the undo list under `trash/` and fetches under `staging/` (`hide-kit/src/store.rs`, PRD skill-mcp-manager).
The store admits at most 256 live items (`ITEM_LIMIT`); a new install, take-over, restore or device receive past it is refused before writing the item, while updates and repeated receives of existing items still work and no live item is evicted.
An item is a kind (`skill` or `mcp`) and a name, `<kind>:<name>`, with its source, its body, whether it is on, the columns it is switched off for, and the latest version its source was found at.
What differs by kind is one `Applier` (`store/skill.rs`, `store/mcp.rs`): its columns, the places one column writes, and how one entry is read, written, taken out and taken in; the loop, the switches, the undo list, the take-over and the report are the store's and know no kind.
An MCP item's body is its server without key values (`hide_agent_hooks::mcp::Server`: its name, its command or address, the names of its variables or headers); the values are in `keys.json` in the item's own folder (`hide_kit::mcp_keys`), so they move to the undo list and back with the item and go with a permanent delete ([agent-hooks.md](../agent-hooks.md#mcp-keys)).
An MCP place is one agent's MCP file in its default account, waiting until the agent has made its own folder there (`[account.paths] state`), and the same file in each profile account; its key is `mcp:<agent>:<real path>`, so a profile's file that is a link to the default one is one place, and a place the record rebuilds after its account went still names the file's shape.
An MCP copy is the item, or the one Hide wrote, only when its keys agree too (`Entry::keys`; the record keeps an HMAC of the keys written under the store's secret in `keys.secret`, `Written::keys`), so the same server with another key, or a key typed into Hide's entry by hand, is the operator's; an MCP entry is whole while it holds only fields the converter reads, and taking a name over sets a copy that is not aside as the file spelled it, to be put back when the machine leaves Hide ([agent-hooks.md](../agent-hooks.md#mcp-servers)).
The screen adds a server in two changes: `ReadMcp` reads a paste (`hide_agent_hooks::mcp::paste`) into `StoreReport.mcp_previews`, each server with the names of the keys the paste gave a value, the values staged in the store until an add takes them, `CancelMcp` closes the answer or, unanswered, an hour passes, and `AddMcp` adds the server as the fields say, each key typed on the screen or else the paste's (`PastedPick`); `SetMcp` changes a server and its keys, a key not typed keeping its value.
The ownership digest holds no key value, so a key edit or a copy that brings a new key marks the places Hide wrote the item to as stale (`StoreRecord.stale`), and the reconcile writes them again; a place whose write fails stays stale and is tried on the next pass (B12, B26).
An MCP row carries its server (`ItemReport.server`) and the version its command pins (`Version::Pinned`, `NpmLatest`, `Unpinned`) or `Remote`, whatever its source.

A skill switches per folder, not per agent, because an agent reads a folder and several agents read the same one: three columns, `claude` (`~/.claude/skills`), `agents` (`~/.agents/skills`, read by Codex, Grok, OpenCode, Pi and omp) and `antigravity` (`~/.gemini/config/skills`), from each adapter's `SkillLocation`.
`Column.agents` names the agents that read the column's folder and `Column.also` the agents that read it besides their own (`AgentAdapter::skill_also_reads`: Grok and omp also read `~/.claude/skills`); the screen joins `Column.agents` with `KitSnapshot.agents` to show only the agents installed and switched on there, so the store makes no install check of its own.
A place is its folder's real path, links on the way followed as the agents follow them: with `~/.agents/skills` a link to `~/.claude/skills` the two columns are one place, which holds an item while either switch wants it, and a column switched off there reads `off` with the column that keeps it named.
An MCP server switches per agent, one column for each, since each agent keeps its own settings file.
A column's places are its default folder and the same folder in each profile account of its agents (`targets::accounts`, judged for links and ownership as the kit's profile pieces are), so a profile added later, or an agent switched on later, gets every item that is on with no input, and a profile that went has Hide's copies taken out of its folder.
A newly listed profile version queues a store pass on that machine through the existing kit worker, even when no source folder changed; repeated readings of the same version queue nothing (B25).
A folder an agent has not made yet is not made for it: the cell reads `waiting` and the item goes in once the agent makes it.

The store's record names every entry Hide wrote, with a digest of its files (`StoreRecord.written`); an entry of the same name that the record does not name, or whose content changed since Hide wrote it, is the operator's.
Hide never overwrites or deletes the operator's entry: its cell reads `hand_written`, and the entry is listed under what only an agent has until the operator takes it over (`Adopt`, naming the place a listed copy or the cell gives as `place`; every cell carries the key of the place its state speaks of, so the screen and the CLI never build one), which copies one copy into the store (the one the operator picks when they differ), records the matching copies as Hide's where they are, and moves the others whole into the undo list; a linked skill is taken over from the folder its link leads to, which becomes a followed source.
The screen binds every take-over to its own reading: a skill's preview digest or an MCP copy's server without key values (`AdoptConfirmation`).
The kit first reads the chosen copy into private staging and compares that staging with the confirmation before replacing a stored item or touching an agent entry; a changed copy refuses `Differs` and needs a new confirmation, and only matching staged content is installed.
An entry is Hide's only while it holds nothing a copy leaves out (a `.git` folder, a link inside), so a matching copy that does, such as a cloned repository, is moved whole into the undo list too, by rename, and Hide's copy goes in its place; an entry that cannot be read, such as one past the skill limits, is listed with why and the folder's other entries as ever.
A skill is written whole into a hidden incoming folder and renamed into place, so an agent never reads half a skill, and a pass that finds every copy current writes nothing.
Hide's own stubs (`hide`, `hide-mission`, `hide-issue`) are the kit's and never appear in the store.
A deleted item, or an operator's copy a take-over replaced, goes to the undo list, which keeps the newest twenty and purges the oldest past that (engineering rule 15).
Delete first removes the copies the ownership record identifies; a cleanup failure refuses the change and keeps the item and its original files, switched off so a later pass cannot put removed copies back, and another delete finishes the remaining cleanup.

A GitHub source, or any git address, is read with the account's own git as an owned child with a deadline, with `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never` so it never asks, and with the account's SSH agent; Hide stores no token.
The clone turns the account's line-ending conversion off, so a commit's files are the same bytes, and the same digest, on every system, and a `/tree/<commit>` address fetches that commit by itself.
A fetch runs before the account lock into `staging/.fetch-<id>` and is renamed in under it, so a slow host holds no other pass up; staging keeps the newest four previews and four update diffs, and a pass clears what none of them names, a fetch still under way only once it is an hour old.
The version beside an item's name is its tag, or the short commit with none; `CheckUpdates` asks each repository for its newest commit when the screen opens and once a day, which shows `update`, and an update is never taken on its own: `PreviewUpdate` fetches it and reports the old and new versions and the commits' subjects, and only `Update` with that commit applies it.
A folder source is followed: `hide_kit::follow_store` compares each followed folder's file sizes and times with what the store took in and runs a pass only when one changed, so it can run every few seconds; a folder that went keeps the last copy and marks the item.
The status read, which the core asks every five seconds while Settings is open, reads a skill folder's files only when its stat fingerprint (each file's name, size and time) moved since they were last read: the helper process remembers the digests of at most 512 folders (`skill::REMEMBERED_LIMIT`), the one read longest ago going first, so an unchanged read costs a stat of each file and no read; a pass that may change a folder always reads it.

The core carries the store as kit work of its own (`runtime/kit_store.rs`): the screen's `kit_store { device_id, request_id, changes }` queues the changes for that machine beside its kit job, never merged into it, since a kit read asks the machine's Codex, and the machine's one kit worker (`KitPump` here, the device's kit worker on a device) runs it once no kit job waits, as the helper protocol's `kit` `store` (`hide_kit::apply_store`) or `follow_store` (protocol 100).
The answer lands in `KitSnapshot.store` (columns with their agents, items with their source, version, update and one cell per column with its state and when it last changed, a failed cell's kind of failure (`failure`) and the path of the place it speaks of (`path`), a git item's GitHub owner (`owner`), the machine's home for the screen to spell paths under it with `~`, the kept pictures of the items' owners as data addresses (`avatars`), what only an agent has, the undo list, previews and update diffs, and when versions were last checked) and in `status.store_answers`, one answer per request (the request id, `pending`, `done` or `refused`, and each of its own changes' outcomes with its cause): requests the machine's one pass carries together are each answered from the outcomes of their own changes, which the core tags with the request as it queues them, and the list keeps the newest 32, dropping the oldest finished answer first and refusing a new request only while all 32 still wait; the same request id again is the same intent.
The kit pump's tick queues the follow every three seconds for each machine whose store follows a folder, and the daily check for each whose store holds a git item and was last checked a day ago, on this Mac and every connected device; a device that is not connected is not asked to connect for them, and neither joins work already queued for the machine, whose request is answered by the changes its pass ends with.
A request whose device's link or registration goes before its pass runs ends `refused`.
`KitSnapshot.store_new_session` lists the cells whose change landed while an agent session of their column ran, until each such session ends (B17).
[이 Mac에서 복사] is one copy job for both kinds (`kit_store_copy { device_id, request_id }`, B28, D-15): this Mac's kit worker reads its store through the helper protocol's `kit` `store_export` (`hide_kit::export_store`), each kind's `Applier::export` carrying a skill's files and an MCP server's spec with its key values, and the core hands each item to the device as a `Receive` change over the device link, which the device's `Applier::import` writes into its own store; a folder source arrives as a copy, the same item again changes nothing, and a differing one replaces the device's, which goes to its undo list.
A copy refused before any device change retains its cause and log sentence in `StoreAnswer.refused`, so an export limit reaches the copy button even when there is no item row or change outcome yet.
What a copy reads stays in the core's memory until the device's pass takes it, a copy is capped at 30 MiB of encoded content (`COPY_BYTE_LIMIT`), and the screen cannot send a `Receive` itself.
A change's outcome, `status.store_answers` and every log line hold the change as `StoreChange::redacted` gives it, with a carried file's bytes and a key's value emptied (D-11, B13); `redacted` names every variant, so a new one that carries a value has to say how it is emptied.
A full kit report carries the store too (`KitReport.store`), and removing a machine's kit takes out the copies Hide put into the folders, puts each folder a take-over moved to the undo list back where it was, leaves a copy of every other skill or MCP server the operator had and Hide took over where it was taken from (`StoreItem.adopted`, the key of that place, a fact of the item, so a switch that took Hide's copy out since has the store's written back, and an MCP file's agent is known even after its place left the record), and then removes the store, unless another installation of Hide on the account still uses it (`Record::others_installed`); a copy that cannot go back keeps the store, so it is not lost (B30).
A GitHub owner's picture, the screen's icon tile, is fetched once (`https://github.com/<owner>.png?size=64`, 10 s, at most 64 KiB, a PNG or JPEG by its first bytes) by the pass that reads or checks a source of that owner, outside the account lock with the other source work, kept in the store's `avatars` folder only while an item of the store or a source answer it still holds belongs to that owner (each pass drops the others, so a source read and never installed loses its picture with its answer), at most 64 pictures and 1 MiB with the oldest unused one dropped first (only the download runs outside the account lock; the pass decides room, drops and writes under it, against the folder and the store as they are then), and reported from there (`hide-kit/src/store/avatar.rs`); the screen never loads a picture from the web, so it shows offline, and a fetch that fails leaves the GitHub mark, is logged (`store.avatar_failed`) and is tried on the next read or check.
The store's string enums (`store_item_kind`, `store_cell_state`, `store_cell_failure`, `store_refusal_cause`) are in `contracts/snapshot-wire-enums.json`; a cell's `reason` is the kit's sentence for the log, never drawn, and the screen words `failure` in one line.

`hide skill` and `hide mcp` (`hided/src/store_cli.rs`, PRD skill-mcp-manager B31-B33) are the same store from a pane: `list` and `show` answer at once from the machine's last store report, and `on`, `off` (`--agent` for one column) and `remove` are one store request each, whose answer the command waits for (200 s), as a screen press would.
`add` and `update` wait on the operator instead: the core reads the source or the update first, then raises a confirm, `status.store_asks` `{id, device_id, pane_id, since_unix_ms, what}` with what will be installed (a preview's skills not in the store yet, an update's diff, or an MCP server's reach with the names of its keys), which stands as the asking agent's person's turn ([status-model.md](../status-model.md#a-persons-turn-an-agent-declares)), and only [설치] in Settings (`store_ask_answer`) sends the change; [취소] ends the command `store_declined`, and nothing on the command line skips the confirm.
A key's value is never an argument: `--env NAME` and `--header NAME` name a key, `NAME=value` is refused, and the operator types the value on the confirm, so it travels only as the screen's `Sealed` value.
The command waits off the lock (`hided` scoped request `store`, `Core::prepare_store`, `store_command::Prepared::run`) for at most 30 minutes, after which it ends `store_unanswered` and its confirm comes down; the same command again from the same pane while the first still waits joins that one's confirm and lets the first waiter go, so an agent whose tool gave up does not raise a second confirm (engineering rule 11); at most 16 commands wait at once (`RUN_LIMIT`), and a machine that goes ends those waiting on it.
Refusals carry their code (`store_refused` with the store's cause, `store_not_found`, `store_busy`, `store_invalid`, `store_unavailable`) and a next action, and `--machine <device>` runs the command on a connected device's store.
