# 0023. Bots

- Status: Accepted
- Date: 2026-11-21
- Code: `hide-core/src/access.rs`, `hided/src/access.rs`, `hided/src/access_cli.rs`, `hided/src/access_screen.rs`, `web/src/toolCells.ts`

## Decision

### Bots

A bot is a program outside Hide's panes on the core's machine, such as a scheduler or another assistant, that the operator lets use the `hide` commands (PRD hide-external-control, mission-87; earlier builds called it an external tool).
It is a fourth credential beside a pane's, a checkout's and Desk's, and four parts hold it, each with one job.
The operator gives each bot one of two modes: `all`, the whole Hide, where the bot works as the operator, or `own`, its own work, where it acts only on what it started.
A bot comes in one of two ways: the operator makes it in Settings › 봇 and sends its AI a one-time code, which the AI's `hide access join <code>` turns into the connection; or a program asks itself with `hide access request` and the operator approves it there.

- The core keeps the connections (`hide_core::access`, `runtime/access.rs`): a request waits in memory only, four at most, a fifth name dropping the oldest, which then reads as expired; an approved connection is saved in `access.json` of the state folder, owner-only and replaced whole off the lock, with its id, name, mode, program, times and the SHA-256 of its key, never the key; 16 may be approved, and the 64 newest ended keys are kept in memory so a refused or disconnected tool hears why.
  A request's id is random, drawn by hided when it asks, and the connection keeps it, so no id carries any of the key's hash.
  What a tool no longer connected keeps in the delivery store ends in the store's own upkeep, which reads the connection ids with its batch read and runs before every batch and in its idle pass (`coordination::end_gone_tools`): its origin records, the watches it keeps and the answer waits of its letters; derived from the list, it needs no request, so a full queue or a stop cannot lose it, while the agents the tool started run on and keep its name as their origin.
  The store names no machine, so it is no row of `node_migration::KEYS`.
  While a connection stands in own mode, the agents its bot started, their descendants and the missions they conduct are the bot's: they stay off the operator's device scopes and are published in the tool's own cell (`navigator.tools`, the scope cache's `ToolCell`), which the rail draws after the devices; that is read from the ledger and the connection list on each projection and stored nowhere, so a mode change, a disconnect or a leave moves it on that event, and which cell a window shows is read the same way from what its center shows, the tool's own page or a pane the cell's members hold (`frontTool` in `web/src/toolCells.ts`), as the device in front is, so no path that moves the center needs to know tools exist ([status-model.md: Work an external tool keeps](../status-model.md#work-an-external-tool-keeps)).
  The cell carries, per device, the checkouts its sessions work in, each with the tree of those sessions and its badge marks (`ToolCheckout`), built in the same pass that places the tool's rows for its 태스크 cards, over the refresh's one index of every device's rows, so the sidebar draws the cell's 프로젝트 tab with the operator's own rows (`toolSidebarProjects` in `web/src/toolCells.ts`); a tool that keeps no row costs no pass.
  The operator's approve, refuse, mode and disconnect are core events (`access_approve`, `access_refuse`, `access_mode`, `access_revoke`) that hided takes only from a window's connection; no `hide` command sends them, and the `access` snapshot section carries the waiting requests, the bots made and waiting for their AI, and the connections, each with its mode, last use (moved at most once a minute) and how many live agents and open missions it started.
  A bot the operator made waits in memory only, four at most, with its id, name, mode and a one-time code of 12 Crockford base32 characters (60 bits, shown `K7Q4-MZ2P-X3RD`) that ends ten minutes after it was drawn; hided draws the id and the code from the system's random source, the core keeps the code out of every snapshot, save and debug line, and a restart drops every bot still waiting.
  While its code is live a made bot holds one of the 16 places, as a connection does; once it ran out it keeps its name and holds no place, and a fifth made bot drops the oldest one whose code ran out, or is refused `access_invite_limit` when all four are live.
  A new name, made or requested, is compared without case against every connection, request and made bot, since `Hermes.key` and `hermes.key` are one file on macOS and Windows, and must be a file name on every system (no Windows device name, no trailing dot); connections saved before keep their names.
  Making a bot, a new code and reading a live code again are one window call, `access_call` (`hided/src/access_screen.rs`, the transport of the automations' `automation_call`), which hided takes only from this machine's own window (`OwnWindow`, and a linked machine's relayed screen is refused too) and answers to that window alone with `access_result`; taking a made bot back is the window event `access_invite_cancel`.
  A join (`Call::Join`) answers a key the core already knows where it stands, so a join whose answer was lost and is run again converges; otherwise the live made bot whose code matches becomes a connection with its id, name and mode, saved like an approval, and its code is spent; anything else is `access_code_invalid`.
- The tool keeps its key in its own home (`hide_kit::layout::access_keys`, `~/.hide/access`): `<name>.request` while the operator has not answered, `<name>.key` once approved, each private to its account (`hide_platform::fs`) and read only when it still is.
  `hide access join <code>` keeps a fresh key in `join.pending` (with the code, put in place with no-replace) before it asks, so a run that lost its answer asks again with the same key and a second join in the same home reuses it; a pending join of another code refuses with `access_join_pending`, naming the command that finishes it.
  Joined, the key is placed as `<name>.key` with no-replace: the same key there counts as done, and another key or a `.request` of that name refuses with `access_key_exists`, keeping both files and the pending join, so no key is ever overwritten; a code the core refused removes the pending join.
  `hide access request` waits for the operator's answer, asking the core once a second for up to ten minutes, and ends connected, refused, or with the request still waiting (`--no-wait` answers at once); a request whose wait ended becomes the key on the tool's next command outside a pane, once the core says it is approved, so no second request is needed (PRD hide-external-control D-56).
  A file that cannot be read refuses every command with `access_key_unreadable`; `hide access request` then removes it and asks anew, and while the old connection of that name stands the core answers `access_name_taken` until the operator disconnects it.
  `hided/src/access_cli.rs` is the tool's side of `hide access join|request|status|leave|list`, and picks the key a command outside a pane runs with: `HIDE_ACCESS` names one, a home with one key runs as it, and a pane's command runs as the pane whatever keys its home keeps.
  A tool that runs with a home of its own still asks the account's Hide: with no `HIDE_STATE_DIR` or `XDG_STATE_HOME`, its state folder is the one under the account's home from the user database.
- hided proves it on the bootstrap socket (`hided/src/access.rs`): a peer that names a pane, or descends from the program of any pane this core's engine keeps a record of, is refused `access_from_pane` before any key is read, so an agent that cleared its environment cannot become a tool, and its ordinary command runs as its folder, as before; otherwise the key's hash, and nothing else of it, goes to the core, and a command's credential is a one-shot reference (`Binding::Access`) whose every use asks the core the connection's current mode (`Registry::validate`), so a disconnect or a mode change reaches the bot's next command.
  The folder the tool's command runs in gives its Workspace commands a checkout when a registered one holds it, as a checkout caller's does; the tool names that folder in its ask (`AccessAsk::Use`), because Windows reports no other process's working folder, and its word reaches nothing a `cd` would not, since the key proves the tool. With no checkout there it has the connection's own context, and its Workspace command is refused `checkout_not_registered` with the way out: `hide file open`, `diff open` and `browser open` take `--repo <folder>`, which reads the target against the folder the command ran in and then moves the command into that folder before it asks (D-57); a pane's command opens in its own checkout and is refused the option (`repo_from_pane`).
- One table says what each command needs of a bot's mode (`hide_core::access`: `Need`, `admit` and one function per command family the core also runs, `delivery_need`, `pane_need`, `mission_need`, `device_need`): `Work` runs in both modes and, in own mode, only on the bot's own work; `All` runs in all mode only and is refused own mode `access_not_own_work`; `Operator` (adding or removing a device) is refused every bot `access_operator_only`; and what means an agent in a pane (mission and plan commands, `--beside`, `ask-human`, `agent show here`, registration, a hook's reads) or a parent is refused `access_needs_agent` or `access_spawn_parent`, each with its next action.
  The command boundary judges a bot's command by it (`ScopedRequest::access_need`, which adds only the commands the core does not run as a bot's), and the core again when the command runs (`Runtime::access_authority`), before anything of it is read; a bot's letters, spawns and watches act as its connection's code-owned identity `hide:access:<id>` ([delivery.md: Bots](../delivery.md#bots)).
  In own mode the core then holds the command to the bot's own work (`Runtime::own_work`): the registrations `hide_started.tool_work` gives it, the spawns it or they admitted, and the panes those run in now, a spawn still starting counted only while its pane runs the terminal the spawn recorded.
  A key that names an agent has one reader, shared by every caller and every command family (`agent show`, `end`, `sleep`, `agent read`, `request send` and its retry, `watch start` and `assign`, and what a watch's `--observer` or `--actor` must be): an exact registration id wins outright, then the caller's own spawn by its id or intent, then the one live name or pane, and nothing else (`coordination::resolve_key`, with an agent the engine shows before it registers added by `Runtime::resolve_target`).
  The address of another machine's agent (`core:<device>:agent:<id>`) is read there too, as `Target::Core`: only a letter reaches it, and an own-mode bot's is refused as not its own.
  The hold runs on what that reader returns, and the command carries that registration to what it runs on, never reading the key again (`Runtime::own_target` rewrites an id key, `prepare_as` keeps a letter's or a watch's target); so a name of its own work that repeats another agent's id names that agent, and a key that names nothing is refused as one that is not its own.
  A pane command is held by the pane it names (`Runtime::own_pane`), and `agent read` by the registration the reader returns.
  What it watches, hands a watch to and replies to is held the same way; a watch it kept from all mode on work not its own ends in the store's upkeep (`coordination::end_unowned_watches`), as a gone bot's do.
  Anything else is refused `access_not_own_work`, and a list answers only its own agents (`Prepared::listing_only`, `hide ps`) and the missions they conduct.
  A tool's identity is code-owned with a `hide:` pane id, so a gate only Hide itself may pass (a task on a spawn, a mission's takeover, typed input's reports) asks `Actor::hide_itself`, never `hide_owned`.

What each mode may do, by command family (`hide_core::access` and `ScopedRequest::access_need`; `hided/tests/it/access.rs` holds a case for each row):

| Command family | `all`: the whole Hide | `own`: its own work |
| --- | --- | --- |
| `hide agent list`, `show`, `end`, `sleep`, `archive`, `hide ps` | every agent on every connected device | its own agents and its own spawns still starting; a list shows only them, another agent is `access_not_own_work` |
| `hide agent spawn` without `--parent` | into any registered project on any connected device; the agent is the operator's work and its row keeps the bot as starter | the same places; the agent and its descendants are the bot's own work, in the bot's cell |
| `hide agent spawn --parent`, `--beside`, a plan node | refused `access_spawn_parent` / `access_needs_agent` | the same |
| `hide request send`, `reply`, `hide inbox`, `hide watch` | to any agent | to its own agents only, the observer a watch goes to among them; its inbox and watches are its own in both modes |
| `hide pane read`, `send`, `agent read` | any pane on any connected device | the panes of its own agents only, a device's included |
| `hide pane open`, `purpose`, mission and plan commands, `ask-human`, `agent show here` | refused `access_needs_agent` | the same |
| `hide mission list`, `show` | every mission | the missions its own agents conduct |
| `hide file`, `diff`, `browser open`, `hide view`, `hide links`, sessions, `hide worktree remove` | as the operator; `hide links` and sessions read every Project's from a bot outside every checkout | refused `access_not_own_work`; its agents open Views from their own panes |
| `hide device list`, `retry` | every device | refused `access_not_own_work` |
| `hide device add`, `remove`, `pause`, `resume`, pairing | refused `access_operator_only`; a pairing ask carries the bot's key, and the daemon judges it by its mode (`pairing::Ask::bot_need`) | the same |
| `hide phone list` | every phone paired with this computer | refused `access_not_own_work` |
| `hide phone pair`, `remove` | refused `access_operator_only`; the ask carries the bot's key as `hide device`'s does, judged by `mobile::command::Ask::bot_need` | the same |
| `hide access list`, `hide automation`, `hide store`, agent profiles, `hide project open` | as the operator | refused `access_not_own_work` |
| Approving bots and changing a bot's mode | never: a window's connection only | the same |

What a bot started is shown with its name whatever the mode: the row's and the mission's `tool` mark (`botStarter` in `contracts/hided-ws.schema.json`, `{connection, name, owns}`) names the starter, and `owns` is true only while the connection stands in own mode, which is what keeps the work in the bot's cell; in all mode the work is the operator's and the mark only says where it came from.
A mode change hands the work over on that event (`Runtime::tool_work_moved`): own to all gives it to the operator, all to own takes it back.
A list saved by an earlier build (schema 1, with a level) loads its Act connections in all mode and ends its View only ones `access_reapprove`, so such a bot asks again with `hide access request`; the file is rewritten at the next change.

Any program running as the same account can read a tool's key file and act as that tool; Hide keeps only the hash, a disconnect takes effect on the next command, and every request, answer, key issue, refusal and leave is a diagnostic record with the connection id and the reason, never the key or its file's path.
A tool under another account cannot reach this core at all: the bootstrap socket's record and the references it issues are private to the account that runs Hide.
What narrows the same-account limit today is the operator's: give a bot own mode unless it must act on the operator's work, give each tool its own name so one disconnect ends one tool, and disconnect a tool that is no longer used.
