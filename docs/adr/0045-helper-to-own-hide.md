# 0045. Switching a helper device to its machine's own Hide

- Status: Accepted
- Date: 2026-11-19
- Code: `hide-core/src/runtime/device_switch.rs`, `hided/src/core_install/`, `web/src/settings/DeviceSwitch.tsx`

## Decision

### Switching a helper device to its machine's own Hide

A device the core dials over SSH, or a WSL distribution of this PC, runs through a helper on that machine; a switch makes the same device its machine's own Hide's, on the connection two Hides keep, without a link or words (PRD device-connect-iroh D-27, D-45, D-49, D-75; B30, B36, B43; operator decision 2026-11-24).
hided runs it (`Ask::Switch` in `hided/src/pairing.rs`, asked by `hide device switch` and by the `서버로 연결` button of the device's opened row, `pairing_switch`), over one SSH login to the device's alias (`pairing_ssh::switch`), or through `wsl.exe` into the distribution, which asks nothing (`pairing_wsl::switch`); `Runtime::device_switch_source` says which (`SwitchVia`), and names the device by its id, its alias or its distribution.
Which device can be switched is the core's one rule (`LinkOrigin::switches`): an SSH device that has connected, or a WSL distribution of this PC.
The operator chooses it (operator decision 2026-11-24; the security boundary is `docs/device-connection-security.md` in with-hide/hide-private, sections 15 and 16): nothing in the core or the daemon asks for a switch, so an update, a start and a connection switch no device, and nothing about the choice is saved.
Where a machine stands on the one rule is read in one place, `pairing_ssh::may_move` (`pairing_wsl::may_move` for a distribution, `Pairing::may_move` for either), over a login of the device's own that asks nobody: the target's `hide always-on unattended --json` says the facts (`unattended`, `hide_platform`'s `UserAgents::unattended`, a Mac's automatic login or a Linux account's lingering; `desktop`, whether someone is logged in; `automatic_login_offered`, false while FileVault locks a Mac's disk; `user`, a Mac's login name) and `condition_of` reads them per system into `pairing_ssh::Condition`, whose `may()` is whether a switch runs and whose `payload()` is what the button and the command are told.
Every `hide` the read and the switch run there is the one beside the device's node, the program its connection put there and started (`DeviceSwitchSource::node_program`, from the device's ready link; `pairing_ssh::Reach::running`): this computer's own build, never the `hide` the account links, which follows a build only once that build's kit has run there, and on a Mac mini whose node ran 1.2.12 still named a 1.2.11 helper's, which refused every verb that pairs (with-hide/hide#3007).
A device whose node has not connected since the core started, and a machine a device was switched to, are read through the account's own `hide`, where a 1.2.11 build, which kept connections between two Hides behind a switch, answers as a Hide to update (`ssh_update_there`).
A Mac with nobody logged in to its desktop is refused (`signed_out`); a Mac that does not log the account in by itself is switched with a warning, not refused (`auto_login_off`, with `how` false when FileVault offers no automatic login); a Linux account needs systemd and lingering; Windows is not switched in 1.2.12; an account that keeps no login item (a HOME that is not the account's own) is `unknown` and not switched.
The read has two callers (`pairing_ssh::Asked`): `Look`, an opened row (`Ask::LookSwitch`, the window's `pairing_look_switch`), changes nothing on the machine and starts no distribution that is off; `Switch`, every `Ask::Switch` (`Pairing::switch_asked`), reads again and is the only one that asks a Linux account that does not linger to (`hide always-on linger --json`, where `Systemd::linger` runs `loginctl enable-linger` and reads the setting again), since whether the account may is known only by asking; an account whose switch then stops keeps lingering on, and nothing else is started or written there by a read.
A device whose SSH login needs a password, a passphrase or an answer about the server's key is not read, so it is not switched, and the ask answers `ssh_not_reached`; a login that stops carrying a step after that read signed in, as when its sshd ends while the target accepts the pairing, was cut midway, and the switch answers `switch_cut` (`cut_midway` in `hided/src/pairing.rs`), which the next press carries.
A machine the rule leaves answers `left` with its `condition` and `user`, which the terminal prints as its reason with the one thing to do (`left_line` in `hided/src/device_cli.rs`) and the opened row draws in the button's place; a switch that ran answers `done` with the same two, so a Mac switched without automatic login is told that once (`switched_lines`); a machine the login did not reach answers the channel's refusal, not `left`.
The core keeps none of a read: the row holds what it was told while it is open (`useDeviceSwitch` in `web/src/settings/switchWays.ts`).
A switch of a WSL distribution is the operator's, so it may start one that is off (`Carriers::may_wake`, as its Reconnect does, B43): the read runs in it through `wsl.exe`, which starts the distribution a command names.
A switched distribution keeps its `wsl-<name>-<digest>` id and its `WSL <name>` name, although its own Hide names itself by an id of its own and by the PC's host name: the machine a switch pairs with is found by the name the PC reaches it by, not by its device id.
It looks first (`hide device look-ssh` there): a machine whose own Hide runs is paired with; one that runs none is only named (`install_needed`), unless it is a Mac this machine may not start one on (`pairing_ssh::install_refusal`: from a system that is not macOS, or with nobody logged in to its desktop, which the look answers as `desktop` from `core_install::checks::desktop_session`; a look that does not say is not refused), and once the operator allowed it a Hide is started there with `hide connect`, run from the `hide` beside the device's node, so the account's core is this machine's build on the account's own state folder and keeps itself running from a login item once paired (A paired machine's core stays on).
A Hide there that is stopped and that no app opens (the look's `app`, `hide_kit::app::present` of that state folder, false) is started again by the next switch with the same `hide connect`, with nothing typed on that machine and nothing asked a second time: the consent is for installing a Hide there, and starting one already installed is within it.
That is the Hide a switch started and did not pair, as when the login was cut between the start and the pairing, and equally one its account stopped with `hide stop`; a Mac is held to `install_refusal` then as at a first start.
A stopped Hide an app opens, or one whose look does not say, is the operator's to start (`ssh_hide_not_running`).
The pairing is the target's `hide device accept-ssh --helper <root>`, which also asks for the helper's folder: the first paired machine to ask gets it, as a record beside the panes (`~/.hide/device-node/guest.json`, `hide_kit::layout::HelperGuest`, written by `Guests::take_helper`), and a later one is answered `held` with that machine's name and nothing saved.
A held device is not asked about and waits for nothing: `Pairing::switch_asked` reads from the core how many of this machine's terminals the device lists (`Core::device_terminals`, none while its session is unread), and with none asks for the switch again with a folder of this machine's own, or answers `held` with that computer's name (`by`) and the count (`terminals`), which the terminal and the row say as closing them and asking again.
Each step (`checking`, `starting`, `pairing`, `connecting`, `projects`, `ended`) is told to the core as a `device_switch` event only the daemon may send (`hide-core/src/runtime/device_switch.rs`); the core draws the one under way on the device's row (`DeviceSnapshot::switch_step`, kept in `Runtime::device_switch_steps` beside the link change and cleared by `ended` or with the device, never saved), so every window shows the same step, and none but `connecting` changes the device: until the paired machine's grant is active the registration is the helper's and its link is untouched, so a switch that stops leaves the device as it was.
When the grant is active the core rewrites the registration in place (`LinkOrigin::Peer { switched: true }`, `switch_device_link`) and saves it: the id, the name, the engine folder and every record that names the device stay.
The link changes only once that save is acknowledged (`acknowledge_device_switch`, beside the naming acknowledgement in both save paths): the helper's link is then closed and the machine's connection dialed under the same registration, and until then nothing dials the device (`device_name_hold`) and the paired machines' reconcile leaves it alone, so a core that stops in between starts again with the helper registration its store still holds; a save that fails puts the helper's origin back and is a diagnostic (`device_switch.not_moved`).
The same save holds that the device owes its first engine open on the new connection (`ui_state.device_switch_opens`): that open is made with `Place::switched`, and its restore closes every saved pane the new link holds no holder for, where any other restore starts it again, and names each with its saved agent (`ProjectionState::not_carried`).
The core then keeps each named agent's conversation under 보관됨 for 이어가기 (`Runtime::settle_switch_open`, `archive_not_carried`: no record is made before the engine named the pane, so nothing is kept and withdrawn and no older record is pushed out for a pane that was carried), counts the closed panes on the device's row (`DeviceSnapshot::not_carried`, B36) and saves that the open is no longer owed.
A later computer's switch (`own_folder`, D-75) is that same open on a folder that holds none of its holders, which would close every pane it had there, so it is made only with none: a terminal opened between the daemon's read and the pairing is caught by `switch_device_link`, which refuses a `connecting` step with `own_folder` while the device lists a terminal or its session is unread (`device_switch.not_moved`, `terminals_open`), and the command answers `switch_not_moved`; it ends nothing in the helper's folder, whose holders are the first computer's from its switch on (D-49, D-75).
A switch is done when the device holds its machine's connection, not when the two are paired: `Pairing::admit_switch` waits on `Core::device_switch_landed` (the registration is that machine's and saved), answers `switch_not_moved` when the core refused the connection and `switch_not_connected` when it did not open within 90 s, and hands the machine no project in either case.
The pairing such a switch leaves behind is taken up by the next one (the target answers that the two are paired already), and until then it is no second machine on the screen: `Runtime::name_helper_devices` writes on a paired machine the helper device of this computer that it is (`PeerMachine::helper_device`: the registration the core still dials under the machine's id, or as the WSL distribution it is), for a machine this computer opens and that does not open it, and Settings, the rail and `hide device list` draw no row, tile or line for a machine that carries one.
A device that was switched makes this computer a paired machine like any pairing does: its endpoint opens, and its own core keeps running from a login item after the window is closed ([A paired machine's core stays on](0008-updating-the-core.md#a-paired-machines-core-stays-on)); removing the pairing undoes both once it was the last one.
On the target the guest that holds the record gets the helper's node folder and install root as its place (`Guests::place`), and its node runs there as the helper did (`guest_node::Helper`: the account's state folder for its bridges and worktree facts, the helper's holders, the installed kit place), so the holders are taken up again as on any new link and the terminals carry on.
The account's state folder is the one that Hide's own daemon runs with, which it names to that node when it starts it (`GuestNode::process_state`): a node is started with the login's variables alone, and where the account's state folder is not the default the helper's panes would ask for their node in a folder the node never bound in, so their hooks and their `hide` would reach that machine's own Hide instead of the core that started them.
A guest taken off that holds the helper's folder is taken off as any guest is: its work stays, on that machine's screen, until its last pane ends or the operator ends it, and the folder and the helper root are removed with its work; one that only left a record loses the record alone.
The way back from a switch is to remove the machine that switched and add this one again over SSH, and the folder goes back when the helper that re-add starts asks for it: the SSH node (`hided node serve`) asks the account's own Hide once as it starts, when the folder holds a record (`release_helper`, `ask_for_the_helpers_folder` in `hided/src/node_cli.rs`).
That Hide gives the folder back only when the machine that took it holds no grant there any more and took it from a helper (`Guests::release_helper`; a split's folder, `HelperGuest::panes`, has no helper to come back): the guest's node ends and leaves the panes to their holders, its record in the folder and its own guest folder go, and the helper owns those holders and takes them up as on any new link, the same shells under the same panes (`Guests::give_helper_back`).
A machine still paired keeps the folder and the answer names it; the helper goes on and its core's restore waits for an owner as it always did.
A guest's node that stayed would keep the folder's ownership while the shells run, and the helper would be refused it (`the previous pane owner still has work in flight`).
An account whose Hide does not run runs no guest's node either, so the helper finds the ownership free and asks nothing; one whose Hide does not know the ask answers `invalid_request` and the helper goes on.
The projects this machine had registered on the device follow the pairing on the same SSH login, once the target admitted this machine (D-48): the core names their folders in what a switch starts from (`DeviceSwitchSource::projects`, at most 32), hided confirms the grant over the connection from the thread that holds the login (`Switch::admitted`, `Pairing::admit_switch`), and only then runs the target's `hide device projects-ssh --project <folder>...`, which asks its own daemon, with the token of the state file its account owns, to register each as a project of that machine's Hide (`{type: "project_add"}`, `project_open::run_add`).
The hand-over has its own bound (45 s on the target, each ask waiting for what is left; 60 s for the SSH answer) and its failure is a diagnostic only (`ssh.projects_left_out`): the switch stands whatever was listed, and a switch that never lands registers no project there.
That registration is the one a row of Add a project's importable list makes: judged on that daemon's own `$HOME` line, so a folder it would ask its operator about is left out, kept as a receipt, and bringing nothing forward; a folder that is a project there already adds nothing, and one that is refused leaves the pairing as it is.
A project added this way gets its first terminal on that machine, as every project added to a Hide does, so a switch starts at most one shell there for each project it hands over.
The window that watched a switch land says once, at the top of that machine's opened row in Settings › Devices, that Memory and standing instructions start fresh there (`useMoved` in `web/src/settings/DeviceSwitch.tsx`, `SwitchedNotice` in `DeviceWays.tsx`, kept in `ui.ts` until it is confirmed); a row is known to be a switched device's by `DeviceSnapshot::switched`, the registration's `LinkOrigin::Peer { switched: true }`.

What starts a core on a machine and reaches it over SSH is `hided/src/core_install/`, which no flow owns: the login item or fixture process that runs a core (`starter`), the flags of the commands run there (`flags`) and the one owned `ssh` (`remote`).
A core's update (`core_update`) and the start of a Hide over SSH build on it.
