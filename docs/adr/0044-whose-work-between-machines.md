# 0044. Whose work is whose between machines

- Status: Accepted
- Date: 2026-11-20
- Code: `hide-core/src/whose_work.rs`, `hide-core/src/peer_work.rs`, `hided/src/work_names.rs`, `hided/src/desktop_notices.rs`

## Decision

### Whose work is whose between machines

Two paired machines see some of each other's work, and one place decides what each of them does with a piece of it (PRD device-connect-iroh D-78).
`hide_core::whose_work::judge` reads two facts, the core that answers for the work and the machine it runs on, and `whose_work::reach` is the one table of what follows:

| The work | In this machine's Needs You and Done | To this machine's phones | Told to the machines that may open it | Drawn here marked as another machine's | This core judges its notification |
| --- | --- | --- | --- | --- | --- |
| This core's, running here | yes | yes | yes | no | yes |
| This core's, running on another machine | yes | yes | no | no | yes |
| Another core's, running here (a guest's pane) | no | no | no | yes | no |
| Another core's, on its own machine, told over the connection | yes | no | no | no | no |

Nothing received is sent on, so a row never travels to a third machine, and no row rings in two cores.
The phone projection (`agent_state::phone::project`) tags every row it builds with that answer, and the daemon, the phone bridge and the sender to other machines read the tag rather than decide for themselves.
What a machine tells the machines that may open it is `peer_work::told`: its own top rows in Needs You and Done that run on it, an external tool's work left out, as two counts and at most 64 rows with bounded text.
The receiving daemon keeps it only from a machine it opened a stream to, and hands its core the latest as the daemon-only `peer_work` event, one per machine and replaced whole, and an event with no list when that machine's last such stream ends; a list and its stream's end are kept under the streams' own lock and handed one at a time, so the core hears them in the order they happened.
A list lives in the core as long as that stream (at most 16 machines' lists, one more refused and recorded), and the paired machines' list only decides whether it shows: `navigator.peer_work` holds the lists of the connected machines this core opens, so a list that arrives before that list names the machine, confirms it or says it is connected shows when it does.
`notice_place::places` orders the places one notification is tried (D-60): this machine while someone uses it and a window shows notices, else the connected computers in use that may open it, the most recently used first, else the phone; the latest phone action any of the machines knows of takes every computer until the next computer input, and every input is a length of time, never a clock reading.
The daemon's desktop notices (`hided/src/desktop_notices.rs`) observe this machine's seat, a desktop host's reports of use and the receipt of a phone's action, hold the seat each computer that may open this machine told of itself, and take that answer: a new notice reaches the windows only while this computer is the place, a notice it did not take is never shown here later, a notice shown before is still cleared, and the phones rest exactly while a computer whose window shows the operator's turn is the place.

All of it between two machines rides the `core` stream the two cores already talk on (`hide_peer_protocol::core`, `hided/src/peer_core.rs`), as seven more message types an older build skips, and no stream of its own.
Which way a message may go is read from who opened a stream, which is who holds a grant: `work` goes to the machines that opened one to this machine and is kept only from a machine this one opened one to, and `seat` the other way.
`work` is `peer_work::told`, whole, sent when the list the follower read gives a different answer and to a machine as its stream opens.
`work` and `seat` each replace what was told before, so a stream holds one mark for each and not a message (`peer_core::Standing`): its writer reads the list and the seat as they stand when the stream can send, so neither waits behind the 64 messages a stream holds to be written nor is lost when those are full.
`work_names` goes the way `seat` does, from a machine to a machine it opens, and says what its core shows its work there by (B10): each pane by the id the receiving machine's tap lists it under, read from the snapshot as `work_names::told` (at most 128 panes).
`work` lists every such pane with its name when it has one (its agent's label or else the name its tab was given, 160 characters at most), the branch of the checkout it stands in (255 bytes at most) and the mark its row is drawn with there (its agent's, `quiet` for a terminal no agent runs in), and the agent kind that runs in it (`agent`, the id of an agent definition, 32 bytes of lower-case letters, digits, `-` and `_` at most, absent for a plain terminal and from a build before it, whose rows draw no logo; a kind outside that shape is left out by the sender rather than refused with the list); `names` repeats the named panes alone, for a build before `work`, which reads the message by it and skips `work`, and a receiver reads `names` only when `work` is absent, so an earlier sender's panes are named without a branch or a mark.
The sending daemon reads it from the core only while a stream it opened is open (`hided/src/work_names.rs`: one snapshot read per change burst, the names read again only when the devices or their sessions moved), and sends that machine's list whole as the stream opens and when it reads differently; a machine whose session the core does not hold now is told nothing, so it keeps what it was told.
The receiving daemon takes it only from a machine that opened a stream to it, and only a list within those bounds, and hands it to that guest's tap (`Guests::name_panes`), which keeps each name, branch and agent with its pane in `h/panes.json` and the mark in memory only, and tells the core the guests' panes again; when that machine's last stream to it ends, the tap drops the marks (`Guests::guest_away`), since only a connected machine can say where its work stands.
`seat` is this computer's seat as lengths of time (how long ago its last input was while in use, whether a window shows the operator's turn, how long ago a phone paired with it acted), sent as a stream opens, when it reads differently (in use, shows, phone later) and when a desktop host reports input resumed at least 5 s after it was last told (`SEAT_PAUSE`), never per input; the receiver ages each length by the time since it arrived.
The transitions run while a computer could show a notice (`DesktopNotices::judging`: a window here has the switch on, or a computer that may open this machine is connected), which also keeps the follower reading the core, and the first seat a machine tells seeds them, so nothing that already waited is announced to a computer that just connected.
When the first place is another computer, `DesktopNotices::place` hands it the notice as `notice` with an id, cut to the bounds the receiver checks (`core::Notice::valid`), and the phones rest.
That computer's daemon shows it by its own place rule, only while someone is at it with notifications on, as an `agent_notice` frame whose notice carries `peer` and the tag `peer:<connection id>|<the owner's tag>`, with a status code or a subject its window cannot word left out, and answers `notice_answer` with whether it did; a click on it hands that machine's screen the agent's pane (`openComputerAgent`, web/src/actions.ts), and selects that machine's tile in a window that draws no screen of it.
A computer that answers no, cannot be written to, or says nothing within `notice_place::TAKEN_WITHIN` (5 s, the follower's own timer) is at no seat until it tells its seat again, and the notice goes to the place that is first then: this machine if someone sat down, another computer, or the phones, where `PhoneNotices::fall` sends a wait that rested at once and nothing for one the phones were already sent (B71).
When the operator has seen the work, `notice_clear` closes the notice on the computer that showed it or was sent it.
A phone that pairs with this machine is told once to each computer that told it a seat, the connected ones that may open it, as `phone_paired` with the phone's name alone (at most 64 characters, `core::valid_phone_name`) and nothing of the code, the link or the phone's keys (`DesktopNotices::phone_paired`, PRD device-connect-iroh D-70); one that is not connected then is not told.
The receiver keeps it only from a machine it opens one to, and every window there that takes notifications shows it, whoever is at that computer, as an `agent_notice` frame's `phones` entry tagged `peer:<connection id>|phone|<name>`, which a click opens on that machine's tile.
A machine that may open this one no longer, or left, loses its seat here and what it had not answered goes on at once.
At most 16 computers' seats are held (`MAX_COMPUTERS`, one more is refused and recorded) and 256 handed notices remembered (`MAX_HANDED`, past it a new one goes to the phones).
A notice the place rule gave the phones this way, not taken by a computer or past that cap, is named by the follower's pass (`mobile::Judged::placed`) and sent though a computer is in use, since no computer shows it later; any other waiting notice is still dropped at the send when use of a computer resumed.
That placement travels with the notice (`mobile::Outgoing`: payload, serial, placed) from its job through a hold for the relay link to the flush, and both sends ask the one rule (`Mobile::rested`), so a placed notice held while the link was down is sent once when it comes up, and a close still withdraws it by its serial.
Every refusal and every notice that went elsewhere is a diagnostic (`desktop_notice.not_here` with its place, `desktop_notice.not_taken`, `peer_core.work_refused`).
A machine that keeps its own Settings is `LinkOrigin::keeps_own_settings`, a paired machine: this core's Hide AI reads none of its agents, refuses to be placed on it (`ai_settings.device_keeps_its_own`), and takes a saved placement off a device that became one, where the settings are read and where the machine is paired, writing the file to say so (Settings per machine).

A call proved only by the folder it was made in (a shell outside every pane) is a guest's when panes of that one guest live in the folder and no pane of this machine's own does (`guest_panes::folder_call`, D-55): a pane lives in a folder when the folder is the one it was started in or below it, and a pane of this core's lives there when a checkout of this machine that holds the folder has a pane.
With a pane of this machine's own there too, or panes of two guests, the call stays with this machine and the diagnostic `folder_call.kept_by_host` records which rule kept it.
For a guest's folder the daemon's bootstrap binds nothing and answers `handed_to` with the guest's installation by name (`guest:<short key>`, `hide_peer_protocol::launch::HandedTo`), never a path.
`hide` finds that installation's own `hide` by that name (`pane_install::hand_to_guest`), runs the same call there with the state folder its node is reached through and its installation named, and returns its exit code.
The guest a split left this account's device folder to (`HelperGuest::panes`, D-46) is not handed its own `hide`: its node there answers as the installation the folder's panes name, this machine's own, and under no name of the guest's, so the daemon refuses the call as another installation's (`other_install`, `pane_auth::split_guest`) and the calling `hide` asks that node's bridge itself, as the folder's panes do; the node proves the caller by its folder and its core answers.
Where a guest's node, builds and `hide` are is one answer, `hide_kit::layout::GuestPlace`: its own folders under the host's state folder, or the device helper's root and node folder with the host daemon's state folder when that guest took the helper's folder over (`HelperGuest`); the daemon that runs the node and places its builds (`Guests::place`) and the handed call both ask it, the first by key and the second by name.
The guest's node proves the caller by its folder as a device's node does, the guest's core binds it to its checkout or refuses, and that answer is final.
A call that already names an installation is a pane's or one already handed and is never handed on, and an installation whose `hide` is not on this machine answers `guest_install_missing`.
